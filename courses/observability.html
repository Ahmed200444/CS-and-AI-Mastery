02The three pillars: logs, metrics, traces

  • Connect logs with metrics and predict what changes when one assumption changes

Explanation

Logs are discrete, timestamped records of specific events -- rich detail, but expensive to store and search at volume. Metrics are numeric measurements aggregated over time -- cheap to store and query, but you lose the individual event detail behind an aggregate number.

Key concepts

logsmetricstracesthe three pillars

Example

# same underlying problem (a slow request), three different signals:
# logs: 'request 8827 took 3.9s, database query returned an error at 14:32:07'
# metrics: 'p99 latency for /checkout jumped from 200ms to 4000ms starting at 14:32'
# traces: 'this ONE specific request spent 3.8s of its 3.9s total waiting on the database span'
Common mistake: Assuming these three are the only possible observability signals that exist -- they're the traditional, practical model most tooling is built around, not an exhaustive, closed list.

Explanation

A counter only ever increases (except when reset, e.g. on a process restart) -- good for 'total requests served' or 'total errors,' where you care about a running total, not the current state.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: Prometheus metrics.

Key concepts

countergaugehistogrampercentilesPrometheus metrics

Example

# choosing the right type by what you actually need to know:
# 'how many requests have we served, ever?' -> counter (only grows)
# 'how many requests are in the queue right now?' -> gauge (goes up and down)
# 'what does our latency DISTRIBUTION look like?' -> histogram (buckets, not one number)
# a histogram lets you see 'most requests are fast, but 1% are very slow' -- an average alone hides this
Common mistake: Using a single average latency number instead of a histogram/percentiles -- an average can look perfectly healthy while hiding a real subset of slow requests a histogram would reveal.
05Distributed tracing in depth

What you will learn

  • Explain span relationships and trace context propagation beyond the basic trace-ID intro
  • Explain how span changes the behavior, result, or engineering decision in a concrete example
  • Connect span with parent/child spans and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A trace represents one request's full journey; it's made up of spans, each representing one unit of work (a service call, a database query) with its own start time and duration. Spans have parent-child relationships -- a parent span's duration should contain its children's time windows, letting you see exactly where time was spent within a larger operation.

Key concepts

spanparent/child spanstrace context propagation

Example

# a trace is a TREE of spans, not a flat list:
# root span: 'handle checkout request' (120ms total)
#   -> child span: 'call payment service' (80ms)
#   -> child span: 'call inventory service' (30ms)
# each child's time window must fit within its parent's -- that's what makes
# the waterfall view meaningful, not just a list of unrelated timings
Common mistake: Forgetting to propagate trace context across an async boundary (a queue, a background job) -- the trace silently breaks into two disconnected pieces exactly at that boundary, hiding the full.

SLISLOerror budgetSLO vs SLA

Example

12Telemetry aggregation & the cardinality problem

What you will learn

  • Distinguish log volume/indexing cost from metric label cardinality, and explain why both are cost problems but not the same mechanism
  • Explain how log volume vs metric cardinality changes the behavior, result, or engineering decision in a concrete example
  • Connect log volume vs metric cardinality with time-series explosion and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Log volume and metric cardinality are related cost problems, but they work through genuinely different technical mechanisms. Logs cost more as volume and the number of distinct indexed fields grow -- more raw data to store and search, and more indexed fields to maintain for fast querying.

Key concepts

log volume vs metric cardinalitytime-series explosionindexed fieldsrelated but distinct cost mechanisms

Example

# two DIFFERENT mechanisms, not the same problem in disguise:
# logs: cost grows with total log VOLUME and number of indexed fields
# metrics: cost grows because each unique LABEL-VALUE COMBINATION is a
# separate stored time series -- adding user_id (50,000 values) as a label
# multiplies your time-series count by 50,000, even if log volume didn't change at all
Common mistake: Assuming logs and metrics share the exact same cost mechanism just because both get expensive at scale -- they're related problems (unbounded dimensionality) but technically distinct: logs.

Exercises

Distinguish monitoring from observability

A colleague says 'observability makes monitoring obsolete.' How would you correct this framing?

Hint

they're complementary, not opposing -- monitoring checks known signals, observability supports investigating things you didn't predict; most real systems need both

Choose the right metric type

For (a) total requests served since startup, (b) current number of items in a queue, and (c) request latency distribution, which metric type fits each?

Hint

(a) counter, (b) gauge, (c) histogram

Diagnose a broken trace

A trace shows a request entering a message queue, but the trace disappears at that point and a new, unrelated-looking trace starts on the consumer side. What's the likely cause, and the fix?

Hint

trace context wasn't propagated across the async/queue boundary; the fix is explicitly passing the trace context (e.g. in message headers) so the consumer continues the same trace

Distinguish correlation ID from trace ID

A simple system logs a correlation_id on every request but has no distributed tracing infrastructure at all. Is this system doing distributed tracing? Explain.

Hint

no -- correlation IDs in logs are a simpler, separate concept from distributed tracing; they let you find related log lines without span/parent-child trace data

Fix a noisy dashboard

An on-call engineer says they can't find the relevant chart during incidents because the dashboard has 40 panels. What would you recommend?

Hint

redesign around the specific questions an on-call engineer needs answered during an incident, cutting down to the minimal set of charts that actually answer them

Calculate an error budget

An API has a 99.9% SLO, measured over 100,000 requests in a 30-day window, with 150 failures observed. Compute the allowed bad events, consumed budget, and whether the budget is exceeded.

Hint

allowed = 100,000 * 0.001 = 100 bad events; consumed = 150; budget is exceeded by 50 events (150% of budget consumed)

Distinguish SLO from SLA

A team says 'our SLO and SLA are always identical.' Is this necessarily true? Explain.

Hint

not necessarily -- an SLO is typically an internal target a team sets for itself; an SLA is often an external, contractual promise to customers, and the two don't have to match exactly

Diagnose an alert-fatigue problem

An on-call rotation reports they've started ignoring most pages because so many turn out to be non-issues. What's the likely root cause, and how would you address it?

Hint

likely alert fatigue from a threshold set too low or alerts with no clear response path; address by raising thresholds thoughtfully, requiring alerts to be actionable, and distinguishing page-worthy from dashboard-only signals

Choose an alert threshold trade-off

For a payment-processing system where missed incidents are very costly, would you lean toward a lower or higher alert threshold, accepting the corresponding trade-off? Justify.

Hint

likely a lower threshold, accepting more false positives, since the cost of missing a real payment incident outweighs the cost of extra false alerts here -- a defensible, context-specific choice, not a universal rule

Write a runbook outline

Given an alert 'checkout error rate > 5%,' outline a short runbook: what would you tell an on-call engineer to check first, second, and when to escalate?

Hint

e.g. 1) check recent deploys/config changes, 2) check the payment-service dashboard for anomalies, 3) if both are clear, escalate to the payment-service on-call

Distinguish health check from synthetic monitoring

A service's /health endpoint returns 200 OK, but users report checkout is broken. What's the gap, and what would have caught it?

Hint

a basic health check only confirms the process is alive/responding, not that a full user-facing flow works; synthetic monitoring (simulating an actual checkout) would have caught this

Explain why logs don't create metric time series

A colleague assumes adding more structured log fields will also increase their metric time-series count. Correct this understanding.

Hint

log volume/indexed-field cost and metric cardinality are related (both costly at scale) but technically distinct mechanisms -- logs don't create metric time series; that's driven specifically by unique label-value combinations on metrics

Calculate metric cardinality

A metric has labels: service (4 values), endpoint (12 values), status (5 values). What's the time-series count? What happens if you add user_id with 20,000 distinct values?

Hint

4*12*5 = 240 time series; adding user_id multiplies this to 240*20,000 = 4,800,000 -- a massive, often unintended cost increase

Choose retention vs sampling trade-offs

A team needs to reduce observability costs. Compare reducing trace retention from 90 to 14 days versus sampling traces at 10% -- what does each actually sacrifice?

Hint

reduced retention sacrifices ability to investigate OLDER incidents; sampling sacrifices having full detail on EVERY individual request, meaning a specific request you need later might not have been captured

Walk through a multi-pillar diagnosis
