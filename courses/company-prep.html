01Researching companies before you apply

What you will learn

  • Research a company's product, engineering culture, and recent context before interviewing
  • Explain how product familiarity changes the behavior, result, or engineering decision in a concrete example
  • Connect product familiarity with engineering blog signals and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Real company research goes beyond the homepage: understand the actual product (use it if possible), recent news (funding, layoffs, launches — these shape interview mood and questions), engineering blog posts (reveal real technical priorities and stack), and what the interview process is known to look like (from company engineering blogs.

Key concepts

product familiarityengineering blog signalsrecent company contextengineering blog

Example

# minimum useful research before any interview:
# 1. use the actual product if you can
# 2. read their engineering blog's most recent 2-3 posts
# 3. check recent news (funding, layoffs, major launches)
# 4. note what tech stack/keywords keep appearing
Common mistake: Walking into an interview only knowing the company's one-line pitch — interviewers routinely notice, and reward, genuine familiarity with what they actually build.

04The FAANG-style interview process

What you will learn

  • Describe the typical structure of a large tech company's interview process
  • Explain how structured, multi-round process changes the behavior, result, or engineering decision in a concrete example
  • Connect structured, multi-round process with standardized rubrics and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Large tech companies (and companies that model their process similarly, sometimes called FAANG-style) typically run: an initial recruiter screen, one or more technical phone/video screens (often a live coding platform), an onsite or virtual loop with multiple rounds (coding, system design for more senior roles, behavioral).

Key concepts

structured, multi-round processstandardized rubricscommittee decisionshiring decisions are typically made

Example

# typical loop shape:
# recruiter screen -> 1-2 technical phone screens -> onsite loop
# (coding x2, system design, behavioral) -> hiring committee decision
# -- each round is often scored independently against a rubric, not just a gut call
Common mistake: Assuming one strong round can compensate for a weak one, or that the interviewer alone makes the final call — many large companies use committee review across ALL round feedback, not a single interviewer's decision.

07Preparing projects that match the role

What you will learn

  • Select and prepare to discuss projects that map directly to a target role
  • Explain how role-relevant project selection changes the behavior, result, or engineering decision in a concrete example
  • Connect role-relevant project selection with structured project narratives and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Given limited interview time, the projects you bring up should map directly to what the target role and company actually need — a role emphasizing backend APIs is better served by discussing your Backend Development track projects in depth than a frontend side project, even if the latter is more polished.

Key concepts

role-relevant project selectionstructured project narrativesspecific contribution framinggroup project in an interviewselect projects that match

Example

# structure for discussing a project in an interview:
# 1. the problem/goal in one sentence
# 2. your specific role/contribution (not just 'the team')
# 3. one interesting technical decision or trade-off you made
# 4. the outcome, ideally with some concrete measure
Common mistake: Discussing a group project purely in terms of 'we did X' with no clarity on your own specific contribution — interviewers need to isolate YOUR actual skill and judgment from the team's.
08Coding assessment strategies

What you will learn

  • Apply a systematic strategy for timed online coding assessments
  • Explain how assessment triage changes the behavior, result, or engineering decision in a concrete example
  • Connect assessment triage with brute-force-first under time pressure and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Timed coding assessments (OAs) reward strategy alongside raw ability: read ALL problems first and triage by difficulty/point value before diving in, don't get stuck on one problem burning all your remaining time, write and test the brute-force solution first if you're unsure of the optimal approach (partial credit usually beats no submission).

Key concepts

assessment triagebrute-force-first under time pressureedge-case review passOA time-managementtriage problems

Example

# OA time-management strategy:
# 1. skim ALL problems first, note relative difficulty/points
# 2. start with the one you're most confident about
# 3. get a working brute-force submission before attempting to optimize
# 4. reserve the last 10-15% of time for edge-case review across all problems
Common mistake: Spending 70% of the available time perfecting the first problem and running out of time for the rest — triage and partial-credit strategy usually beats depth-first perfectionism on one.

  1. only describe what 'the team' did

  4. focus only on the tech stack used

  1. perfect the first problem before looking at the others

  3. skip reading the problems and start coding immediately
  4. always solve problems in the order given
