01Data Engineering for AI Systems

What you will learn

  • Distinguish data engineering from data analysis, database administration, backend development, CI/CD, and MLOps
  • Explain how data engineering changes the behavior, result, or engineering decision in a concrete example
  • Connect data engineering with adjacent disciplines and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Data engineering is the discipline of reliably moving and reshaping data from where it's produced to where it's consumed -- distinct from data analysis (which asks questions of data that's already arrived), database administration (which manages a single storage system's health), backend development (which serves request/response traffic, not data flow).

Key concepts

data engineeringadjacent disciplineswhy AI needs reliable data infrastructure

Example

# five adjacent disciplines, and what makes each DIFFERENT from data engineering:
# data analysis: asks questions of data already in hand -- data engineering gets it there reliably
# DBA: keeps ONE database healthy -- data engineering moves data BETWEEN systems
# backend: serves request/response traffic -- data engineering moves data in bulk/streams
# CI/CD: deploys CODE -- data engineering moves and validates DATA
# MLOps: manages the MODEL lifecycle -- data engineering is what feeds it reliably
Common mistake: Assuming a strong model makes a strong AI system regardless of the data pipeline behind it -- most real production AI failures trace back to a data problem, not a model problem.

Explanation

Batch processing runs on a schedule against a bounded set of data -- a full batch reprocesses everything from scratch (simple, but wasteful at scale); an incremental batch processes only what's new or changed since the last run (efficient, but requires reliably tracking what's already been processed).

Key concepts

Example

# full vs. incremental batch, the trade-off:
# full: reprocess EVERYTHING every run -- simple logic, but wastes time/cost reprocessing
# unchanged data every single time
# incremental: process only what's NEW since the last successful run -- efficient,
# but requires reliably tracking a watermark/checkpoint of what's already been done
Common mistake: Defaulting to full reprocessing 'to keep things simple' at real data volume -- this can turn a pipeline that should take minutes into one that takes hours, purely from redundant work.

08Partitioning and Query Efficiency

What you will learn

  • Explain partition pruning, and why partitioning is not the same concept as database indexing
  • Explain how partition pruning changes the behavior, result, or engineering decision in a concrete example
  • Connect partition pruning with partitioning vs. indexing and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Partitioning splits stored data into separate physical chunks based on a chosen key (e.g. date, region) -- when a query filters on that same key, the system can skip (prune) irrelevant partitions entirely, dramatically reducing how much data must be scanned.

Key concepts

partition pruningpartitioning vs. indexingover-partitioningsmall-file problem

Example

# partitioning vs. indexing -- genuinely different mechanisms:
# indexing: a separate structure that speeds up lookups WITHIN one table's existing storage
# partitioning: physically SEPARATES data into chunks so a query can SKIP entire
# chunks (pruning) without reading them at all
#
# why 'more granular partitioning' isn't automatically better:
# partitioning by customer_id (millions of distinct values) creates millions of
# tiny partitions -- the small-file problem -- which can hurt performance, not help it
Common mistake: Assuming a higher-cardinality partitioning key is always better for query performance -- an extremely high-cardinality key can create the small-file problem, actually degrading performance.

11Idempotency, Retries and Failure Recovery

What you will learn

  • Connect idempotent writes with deduplication keys and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An idempotent pipeline write produces the same end result whether it runs once or is retried multiple times after a partial failure -- typically achieved via deduplication keys (recognizing 'I've already processed this exact record') and checkpoints (tracking exactly how far a run got before failing).

Key concepts

idempotent writesdeduplication keyscheckpointspoison recordsdead-letter handling

Example

# the SAME word, 'retry,' means something structurally different here:
# CI/CD retry: re-run a DEPLOYMENT -- the code either deploys or it doesn't, cleanly
# data-pipeline retry: re-run PROCESSING of data -- without a dedup key/checkpoint,
# a naive retry can process the SAME records again, silently duplicating results
# rather than safely resuming from where the failure actually happened
Common mistake: Assuming a pipeline retry is automatically safe the same way a CI/CD deployment retry is -- without dedup keys or checkpoints, a data-pipeline retry can silently duplicate already-processed.

Exercises

Choose ETL or ELT for warehouse loading

A team needs strict governance -- only validated, clean data may ever land in the shared warehouse. Should they choose ETL or ELT?

Hint

ETL -- transformation happens before loading, so the warehouse only ever holds clean, validated data, matching the strict governance requirement

Choose batch or streaming for nightly training data

A recommendation model retrains once per night using the previous day's activity. What processing approach fits, and why?

Hint

scheduled batch -- the use case tolerates a full day of latency, and batch is simpler and cheaper than streaming when that tolerance exists

Choose batch or streaming for real-time fraud features

A fraud-detection model needs a feature reflecting a transaction within milliseconds of it occurring. What processing approach fits?

Hint

continuous streaming -- the sub-second latency requirement rules out batch or even micro-batch

Choose processing approach for an analytics dashboard

A dashboard needs to reflect activity within about 5 minutes, but doesn't need sub-second freshness. What approach fits, and why not full streaming?

Hint

micro-batch -- 5-minute tolerance doesn't require continuous streaming's added operational complexity, but is too tight for a once-daily batch

Diagnose a breaking schema change

A source system renames a field from `user_id` to `customer_id` with no notice. Several downstream pipelines start failing. What's the root cause, and what should have prevented it?

Hint

a breaking (non-additive) schema change with no coordination; a data contract between producer and consumer would have made the compatibility expectation explicit and required a coordinated rollout

Design a schema-evolution plan using a data contract

Design a plan to safely rename a field, keeping existing consumers working during the transition.

Hint

support both the old and new field names simultaneously for a transition period (an additive step), update consumers to use the new name, then remove the old name only after confirming no consumer still depends on it

Design a data-quality gate

Design a quality gate for an incoming customer dataset that checks nulls, types, uniqueness, and ranges. What should happen when a check fails?

Hint

the gate should block affected records (or the whole batch, depending on severity) from propagating downstream, log the specific violation, and route failing records to a review/dead-letter path rather than silently dropping or passing them through

Diagnose a non-idempotent pipeline

A pipeline fails partway through a run. It's retried, and downstream tables now show duplicate records. What's the likely cause, and the fix?

Hint

the pipeline lacks idempotent writes -- no deduplication key or checkpoint to recognize already-processed records; fix by adding a dedup key and/or checkpointing progress so a retry doesn't reprocess already-completed work

Design a safe backfill

A transformation bug affected the last 30 days of processed data. Design a safe backfill plan.

Hint

bound the backfill to the specific known 30-day range, use a versioned/fixed transformation so it's clear which logic produced the corrected results, throttle it to avoid competing with live production traffic, and communicate the correction to downstream consumers

Choose a partitioning key for a query pattern

Most queries against a large events table filter by a specific day. What partitioning key fits, and why?

Hint

event_date -- matching the actual query pattern lets the system prune to just the relevant day's partition instead of scanning the whole table

Diagnose an over-partitioning problem

A team partitions a table by customer_id (millions of distinct values) and query performance gets WORSE, not better. What's happening?

Hint

the small-file problem -- an extremely high-cardinality partitioning key creates millions of tiny partitions, and the overhead of managing/scanning that many small partitions can outweigh any pruning benefit

Diagnose training/serving skew

A model performs well in offline evaluation but poorly in production. Investigation shows the offline feature uses a 30-day average while the online feature (same name) uses a 30-hour average. What's this called, and what's the fix?

Hint

training/serving skew -- the two paths compute a differently-defined 'same' feature; fix by centralizing the feature definition (conceptually, a feature store) so both paths compute it identically

Identify point-in-time leakage

A training dataset for predicting March 1st churn accidentally includes a customer interaction from March 15th. What's wrong, and what does it cause?

Hint

point-in-time leakage -- the training example includes data that wouldn't have existed yet at the prediction time, artificially inflating apparent model performance during training that won't hold up in production

Distinguish a data-pipeline retry from a CI/CD deployment retry

Explain, in your own words, why retrying a failed data pipeline run is a fundamentally different concern than retrying a failed CI/CD deployment.

Hint

a CI/CD retry re-runs a code deployment, which either succeeds or fails cleanly; a data-pipeline retry re-runs data processing, which -- without idempotency (dedup keys/checkpoints) -- can silently duplicate already-processed records rather than safely resuming

Build a DAG dependency order

Given tasks ingest, validate, transform, feature_build, publish, and an independent audit_log task, build the correct dependency order and identify which task is unaffected if transform fails.

Hint

ingest -> validate -> transform -> feature_build -> publish, in that linear dependency chain; audit_log has no dependency on this chain and continues running normally even if transform fails

Choose CSV, JSON, or Parquet for a workload

An analytical query needs to average one column across 10 million rows, run repeatedly. Which format fits best, and why?

Hint

Parquet -- its columnar layout lets the query read only that one column across all rows, rather than reading every field of every row as a row-oriented format like CSV or JSON would require

Trace incorrect downstream data using lineage

A dashboard shows an incorrect total. Using a lineage description (source table -> transformation A -> transformation B -> dashboard), explain how you'd trace the root cause.

Hint

walk the lineage backward from the dashboard through transformation B, then A, then the source table, checking each stage's output against expectations until the point where the value first becomes wrong is identified

Define a freshness target for an AI consumer

A real-time fraud model consumes a feature pipeline. What freshness target would you set, and how would you justify it?

Hint

a tight freshness target (e.g. seconds, not hours) justified by the fraud model's need to act on near-real-time transaction data -- a stale feature could mean the model is scoring based on outdated information during an active fraud attempt
