01Unit testing

What you will learn

  • Write a unit test that isolates and verifies one piece of behavior
  • Explain how assert changes the behavior, result, or engineering decision in a concrete example
  • Connect assert with arrange-act-assert and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A unit test checks one small piece of behavior in isolation. Arrange inputs, act (call the function), assert the expected output.

Key concepts

assertarrange-act-assertisolationregressionunit test

Example

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
Common mistake: Writing a test with no real assertion -- the code runs but nothing is actually verified as correct.
02Integration tests

What you will learn

  • Distinguish integration tests from unit tests
  • Explain how integration test changes the behavior, result, or engineering decision in a concrete example
  • Connect integration test with component boundaries and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An integration test checks that multiple components work correctly TOGETHER -- a database, an API, and business logic interacting -- unlike a unit test, which isolates one function or class alone. Integration tests catch bugs that only appear at the boundaries between components, but they're typically slower and more complex to set up than unit tests.

Key concepts

integration testcomponent boundaries

Example

# unit test: does calculate_total() return the right number, in isolation?
# integration test: does the checkout FLOW correctly save an order to the
# real database AND correctly call the payment API AND return a receipt?
Common mistake: Only writing unit tests and assuming components will work correctly together -- integration bugs specifically happen AT the boundaries unit tests can't see.
03Mocking

What you will learn

  • Use mocks to isolate a unit test from its real dependencies
  • Explain how mock changes the behavior, result, or engineering decision in a concrete example
  • Connect mock with mocking and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A mock is a fake stand-in for a real dependency (a database, an external API) used in a unit test, so the test doesn't actually hit the network or a real database -- making it fast, reliable, and independent of the real service being available.

Key concepts

mockmockingfake dependency

Example

from unittest.mock import Mock
payment_api = Mock()
payment_api.charge.return_value = {'status': 'success'}

result = process_order(payment_api)
payment_api.charge.assert_called_once()
Common mistake: Over-mocking so heavily that the test no longer verifies anything meaningful about the real code's behavior.
04Writing clear tests & assertions

What you will learn

  • Write test names and assertions that are genuinely useful when they fail
  • Explain how test naming changes the behavior, result, or engineering decision in a concrete example
  • Connect test naming with clear assertions and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A good test name describes the SPECIFIC behavior being verified (test_returns_error_for_negative_input), not a vague name like test1. A good assertion checks the actual expected outcome specifically, so when it fails, the failure message tells you exactly what went wrong without needing to dig through the test's internals.

Key concepts

test namingclear assertions

Example

# vague, unhelpful:
def test1():
    assert process(x)

# clear and specific:
def test_process_returns_none_for_empty_input():
    assert process([]) is None
Common mistake: Writing vague test names and assertions that don't clearly state what's actually being verified, making failures hard to diagnose later.
05Test coverage

What you will learn

  • Interpret test coverage and its limits
  • Explain how coverage changes the behavior, result, or engineering decision in a concrete example
  • Connect coverage with test coverage and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Test coverage measures what percentage of your code actually runs during your test suite. High coverage is a useful signal, but it's not the same as correctness -- a line can be 'covered' by a test that runs it without actually checking the output is right.

Key concepts

coveragetest coverage

Example

# a test that calls a function but asserts nothing meaningful:
def test_process():
    process(data)   # covered! but nothing was actually verified

# a real test:
def test_process():
    result = process(data)
    assert result == expected
Common mistake: Chasing a high coverage percentage as the goal itself, rather than writing tests that actually verify correct behavior.
06Regression testing

What you will learn

  • Explain why regression tests matter as code changes over time
  • Explain how regression changes the behavior, result, or engineering decision in a concrete example
  • Connect regression with regression test and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A regression is when a previously-working feature breaks due to a later change. A regression test suite -- run before every change ships -- catches this by re-verifying old behavior still holds, not just the new feature being added.

Key concepts

regressionregression test

Example

# every time you fix a bug, add a test for that EXACT bug --
# this becomes a permanent regression test, ensuring it never
# silently comes back in a future change
Common mistake: Fixing a bug without adding a test for it -- the same bug can silently resurface in a later change with nothing to catch it.
07Test-Driven Development: an overview

What you will learn

  • Describe the TDD cycle: red, green, refactor
  • Explain how TDD changes the behavior, result, or engineering decision in a concrete example
  • Connect TDD with red green refactor and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Test-Driven Development writes a failing test FIRST (red), then writes the minimum code to make it pass (green), then improves the code's structure without changing its behavior (refactor) -- repeating this cycle for each small piece of functionality.

Key concepts

TDDred green refactortest-first

Example

# 1. RED: write a test for behavior that doesn't exist yet -- it fails
def test_add():
    assert add(2, 3) == 5   # fails -- add() doesn't exist yet

# 2. GREEN: write just enough code to pass
def add(a, b): return a + b

# 3. REFACTOR: clean up if needed, tests still pass
Common mistake: Writing all the implementation code first and adding tests as an afterthought -- this is the opposite of TDD's intended discipline.
08Debugging failing tests

What you will learn

  • Apply a systematic workflow when a test fails
  • Explain how fail changes the behavior, result, or engineering decision in a concrete example
  • Connect fail with actual vs expected and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

When a test fails, first check whether the TEST or the CODE is wrong -- a failing test isn't automatically proof of a code bug; the test itself might have a mistaken expectation. Read the actual vs expected output the test reports, and reproduce the failure in isolation before trying a fix.

Key concepts

failactual vs expectedreproduce in isolation

Example

# test failure workflow:
# 1. read the actual vs expected values in the failure output
# 2. is the code wrong, or is the test's expectation wrong?
# 3. reproduce in isolation (run just that one test)
# 4. fix, then re-run the FULL suite to check nothing else broke
Common mistake: Assuming a failing test always means the code is broken, without first checking whether the test's own expectation is actually correct.
09The testing pyramid & strategy

What you will learn

  • Balance unit, integration, and end-to-end tests
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: browser end-to-end automation (Playwright/Selenium).
  • Explain how testing pyramid changes the behavior, result, or engineering decision in a concrete example
  • Connect testing pyramid with end-to-end test and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The testing pyramid suggests having MANY fast unit tests, FEWER integration tests, and VERY FEW slow, expensive end-to-end tests (which drive the whole system through its real UI/API).

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: browser end-to-end automation (Playwright/Selenium).

Key concepts

testing pyramidend-to-end testtest strategyworthwhile investmentbrowser end-to-end automation (Playwright/Selenium)

Example

# testing pyramid shape (bottom to top):
# many unit tests (fast, cheap, isolated)
# fewer integration tests (slower, test real components together)
# very few end-to-end tests (slowest, test the whole system like a real user)
Common mistake: Building an 'inverted pyramid' -- mostly slow end-to-end tests and few unit tests -- which makes the whole suite slow and fragile.
10TDD in practice: Red → Green → Refactor

What you will learn

  • Apply TDD to business logic by writing a failing behavior test before implementation
  • Explain how Red-Green-Refactor changes the behavior, result, or engineering decision in a concrete example
  • Connect Red-Green-Refactor with edge cases and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Test-driven development is a short feedback loop: write one small test that fails for the right reason, implement the simplest behavior that makes it pass, then refactor while keeping all tests green. Good TDD tests describe observable behavior rather than private implementation details.

Key concepts

Red-Green-Refactoredge casestest-firstsmall increments

Example

Example sequence for transfer(): 1) test a normal transfer; 2) make it pass; 3) test insufficient funds; 4) make it pass; 5) test same-account or invalid amount; 6) refactor shared validation while every test remains green.
Common mistake: Writing the entire implementation first and then calling the later test suite TDD.
11Testing concurrent & transactional behavior

What you will learn

  • Design tests for race conditions, transaction boundaries, retries, and invariants
  • Explain how concurrency test changes the behavior, result, or engineering decision in a concrete example
  • Connect concurrency test with invariant and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Concurrency tests should check invariants rather than depend on lucky timing. For a money-transfer service, useful invariants include total money remaining constant, no negative balance when forbidden, and a failed transaction leaving both accounts unchanged.

Key concepts

concurrency testinvarianttransaction rollbackdeterministic testretry

Example

Instead of sleep-based tests, coordinate two workers so both reach a known point before releasing them. After both finish, assert the invariant on final balances and verify that retries do not double-apply the transfer.
Common mistake: Using arbitrary sleep() calls and assuming a race happened.
