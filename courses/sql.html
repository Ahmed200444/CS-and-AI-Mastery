01SELECT basics

  • Explain how SELECT changes the behavior, result, or engineering decision in a concrete example
  • Connect SELECT with WHERE and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

SELECT picks columns; FROM names the table; WHERE filters rows; ORDER BY sorts. This is the backbone of every query.

Key concepts

SELECTWHEREORDER BY

Example

SELECT name, age FROM students
WHERE age > 18
ORDER BY age DESC;
Common mistake: Forgetting that SQL clauses have a required order (SELECT...FROM...WHERE...ORDER BY), not the order they're logically explained in.

Explanation

WHERE filters individual rows before any grouping happens. ORDER BY sorts the result -- add DESC for descending order.

Key concepts

WHEREORDER BYDESCDISTINCTLIMIT

Example

SELECT DISTINCT city FROM customers
WHERE country = 'UAE'
ORDER BY city DESC
LIMIT 5;
Common mistake: Forgetting that WHERE runs before GROUP BY, so it can't reference an aggregate like COUNT(*) -- that needs HAVING instead.
03Keys & constraints

What you will learn

  • Explain how primary key changes the behavior, result, or engineering decision in a concrete example

Explanation

A primary key is a column (or set of columns) that uniquely identifies each row in a table -- no two rows can share one. A foreign key links a row to a row in another table, enforcing that the reference actually exists.

Key concepts

primary keyforeign keyNOT NULLUNIQUEINTEGER

Example

CREATE TABLE orders (
  order_id INTEGER PRIMARY KEY,
  customer_id INTEGER,   -- a foreign key referencing customers(id)
  email TEXT NOT NULL UNIQUE
);
Common mistake: Adding a foreign key column without actually enforcing (or checking) that the referenced row exists -- this silently allows orphaned references.
04Joins

What you will learn

  • Explain how INNER JOIN changes the behavior, result, or engineering decision in a concrete example
  • Connect INNER JOIN with LEFT JOIN and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A JOIN combines rows from two tables on a matching key. INNER keeps only matches; LEFT keeps all left rows even without a match.

Key concepts

INNER JOINLEFT JOINON

Example

SELECT o.id, c.name
FROM orders o
JOIN customers c ON o.customer_id = c.id;
Common mistake: Joining tables with no ON condition, producing a cartesian product instead of matched pairs.
05Working with NULL

What you will learn

  • Compare against NULL correctly
  • Explain how NULL changes the behavior, result, or engineering decision in a concrete example
  • Connect NULL with IS NULL and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

NULL means 'no value,' and it doesn't equal anything -- not even another NULL. Comparing with = or != against NULL never matches, even for rows that ARE NULL; you must use IS NULL or IS NOT NULL instead.

Key concepts

NULLIS NULLIS NOT NULL

Example

SELECT * FROM users WHERE deleted_at IS NULL;      -- correct: finds active users
SELECT * FROM users WHERE deleted_at = NULL;        -- WRONG: matches nothing, ever
Common mistake: Writing `column = NULL` or `column != NULL` -- these silently match zero rows, which is a very easy mistake to miss.
06Types of joins & join pitfalls

What you will learn

  • Distinguish INNER and LEFT JOIN, and avoid accidental cartesian products
  • Explain how INNER JOIN changes the behavior, result, or engineering decision in a concrete example
  • Connect INNER JOIN with LEFT JOIN and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

INNER JOIN returns only rows that match in both tables. LEFT JOIN returns every row from the left table, with NULLs filling in for any unmatched right-table columns.

Key concepts

INNER JOINLEFT JOINcartesian productaliasingrow multiplication

Example

SELECT o.id, c.name
FROM orders o
INNER JOIN customers c ON o.customer_id = c.id;

-- LEFT JOIN keeps unmatched orders too, with c.name as NULL:
SELECT o.id, c.name FROM orders o LEFT JOIN customers c ON o.customer_id = c.id;
Common mistake: Writing FROM a, b with no WHERE/ON condition linking them -- this produces a cartesian product, not the intended matched pairs.
07GROUP BY & HAVING in depth

What you will learn

  • Aggregate data with GROUP BY and filter groups with HAVING
  • Explain how GROUP BY changes the behavior, result, or engineering decision in a concrete example
  • Connect GROUP BY with HAVING and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

GROUP BY collapses rows sharing the same value in a column into groups, letting you compute one aggregate (COUNT, SUM, AVG) per group. HAVING filters those GROUPS after aggregation -- it's evaluated later than WHERE, which is why HAVING can reference an aggregate like COUNT(*) but WHERE can't.

Key concepts

GROUP BYHAVINGAVG()

Example

SELECT category, COUNT(*) AS num_items, AVG(price) AS avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 5;
Common mistake: Using HAVING for a condition that doesn't need aggregation (it belongs in WHERE, which runs earlier and is usually more efficient).

09Aggregation

What you will learn

  • Summarize groups of rows using GROUP BY and aggregate functions
  • Explain how GROUP BY changes the behavior, result, or engineering decision in a concrete example
  • Connect GROUP BY with HAVING and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

GROUP BY collapses rows into groups; aggregate functions (COUNT, SUM, AVG) summarize each group. HAVING filters groups after aggregation.

Key concepts

GROUP BYHAVINGCOUNT/SUM/AVG

Example

SELECT category, COUNT(*)
FROM products
GROUP BY category
HAVING COUNT(*) > 5;
Common mistake: Using WHERE instead of HAVING to filter on an aggregate value -- WHERE runs before aggregation happens.
10Indexes & performance basics

What you will learn

  • Explain what an index does and its trade-offs
  • Explain how index changes the behavior, result, or engineering decision in a concrete example
  • Connect index with CREATE INDEX and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An index is a data structure that speeds up lookups on a column, similar to a book's index -- the database can jump directly to matching rows instead of scanning the whole table. The trade-off: indexes use extra storage and slightly slow down writes (INSERT/UPDATE/DELETE), since the index has to be updated too.

Key concepts

indexCREATE INDEX

Example

CREATE INDEX idx_users_email ON users(email);
-- now WHERE email = '...' can use the index instead of scanning every row
Common mistake: Adding an index to every column 'just in case' -- each index adds real write overhead, so they should target columns actually used often in WHERE/JOIN/ORDER BY.
11Pattern matching & subqueries

  • Explain how LIKE changes the behavior, result, or engineering decision in a concrete example
  • Connect LIKE with subquery and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

LIKE '%text%' matches any value containing 'text' anywhere -- % is a wildcard for any sequence of characters. A subquery is a query nested inside another, often used in a WHERE clause to filter against a dynamically computed set of values.

Key concepts

LIKEsubquery

Example

SELECT * FROM customers WHERE name LIKE '%smith%';

SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 100);
Common mistake: Assuming LIKE 'smith%' and LIKE '%smith%' behave the same -- the % placement changes whether it matches the start, end, or anywhere in the text.
12Window Functions & CTEs

What you will learn

  • Use CTEs to structure complex queries and window functions to compute running totals and rankings without collapsing rows
  • Explain how CTE changes the behavior, result, or engineering decision in a concrete example
  • Connect CTE with common table expression and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A CTE (Common Table Expression, written with WITH) names a subquery so you can reference it like a temporary table, making a complex multi-step query readable instead of deeply nested.

Key concepts

CTEcommon table expressionWITH clausewindow functionOVERPARTITION BYROW_NUMBERRANKrunning total

Example

WITH monthly_totals AS (
  SELECT customer_id, DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total
  FROM orders GROUP BY customer_id, month
)
SELECT customer_id, month, total,
  SUM(total) OVER (PARTITION BY customer_id ORDER BY month) AS running_total
FROM monthly_totals;
-- running_total accumulates per customer, resetting for each new customer,
-- while every row (one per customer per month) stays visible -- unlike GROUP BY,
-- which would have collapsed this into one row per customer
Common mistake: Reaching for GROUP BY when what's actually needed is a running total or per-row ranking -- GROUP BY collapses rows into one per group, which loses the per-row detail a window function (SUM() OVER, ROW_NUMBER()) preserves while still computing the aggregate.
