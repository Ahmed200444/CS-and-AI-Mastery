01Scaling basics

What you will learn

  • Distinguish vertical from horizontal scaling and explain caching's role
  • Explain how load balancing changes the behavior, result, or engineering decision in a concrete example
  • Connect load balancing with caching and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Scaling begins with concrete requirements: request rate, data size, latency target, availability target, and the operations users actually perform. Load balancing and horizontal scaling add capacity, caching removes repeated work, and queues absorb work that does not need to finish inside the request.

Key concepts

load balancingcachinghorizontal scalingqueuesrate limitingidempotency

Example

users -> load balancer -> [server, server, server]
              cache <-> database
Common mistake: Scaling vertically (a bigger machine) indefinitely instead of horizontally, hitting a hard ceiling on how big one machine can get.
02Load balancing

What you will learn

  • Explain what a load balancer does and why
  • Explain how load balancer changes the behavior, result, or engineering decision in a concrete example
  • Connect load balancer with horizontal scaling and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A load balancer distributes incoming requests across multiple servers, so no single server gets overwhelmed while others sit idle. This also enables horizontal scaling -- adding more servers to handle more traffic -- and improves availability, since traffic can be redirected away from a server that goes down.

Key concepts

load balancerhorizontal scalingdistribute traffic

Example

# without a load balancer: all traffic hits ONE server
# with a load balancer: requests are distributed across server1, server2, server3
# if server2 goes down, the load balancer stops sending it traffic
Common mistake: Scaling by making a single server bigger (vertical scaling) indefinitely, instead of distributing load across multiple servers -- there's a hard ceiling to how big one machine can get.
03Caching

What you will learn

  • Explain what caching is and its trade-offs
  • Explain how cache changes the behavior, result, or engineering decision in a concrete example
  • Connect cache with cache invalidation and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Caching trades freshness and complexity for lower latency and less repeated backend work. You must define the cache key, what is stored, how long it remains valid, and what happens when the source data changes.

Key concepts

cachecache invalidationstalenessconsistent hashingcache stampede

Example

# without caching: every request re-queries the database, even for the same data
# with caching: the first request queries the database and caches the result;
# subsequent identical requests are served instantly from the cache
Common mistake: Caching data that changes frequently without a clear invalidation strategy -- users can see stale, incorrect data without realizing it.
04Databases at scale

What you will learn

  • Explain database replication and sharding
  • Explain how replication changes the behavior, result, or engineering decision in a concrete example
  • Connect replication with sharding and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Databases at scale require deciding where data lives and how copies remain useful. Replication creates additional copies for availability or read capacity, while sharding or partitioning divides data across nodes.

Key concepts

replicationshardingprimaryreplicaread replicaspartition keyhot partition

Example

# replication: primary DB handles writes, replicas handle reads,
# spreading read load and providing failover if primary goes down

# sharding: users A-M on shard 1, users N-Z on shard 2 --
# each shard holds only part of the total data
Common mistake: Sharding a database before it's actually necessary -- sharding adds real complexity (cross-shard queries become harder), so it's usually a later-stage decision, not a starting default.
05Messaging & queues

What you will learn

  • Explain asynchronous messaging between services
  • Explain how message queue changes the behavior, result, or engineering decision in a concrete example
  • Connect message queue with asynchronous and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A message queue decouples producers from consumers so work can be processed asynchronously and bursts can be absorbed. Delivery is not automatically “exactly once”: many practical systems provide at-least-once delivery, meaning a consumer may see the same message again after a timeout or retry.

Key concepts

message queueasynchronousdecouplingbackpressureat-least-once deliveryidempotent consumerdead-letter queue

Example

# synchronous: place_order() waits for send_email() to fully complete
# asynchronous with a queue: place_order() pushes a 'send email' message
# to a queue and returns immediately; a separate worker processes it whenever ready
Common mistake: Making every operation synchronous even when the caller doesn't actually need to wait for the result -- this needlessly slows down the user-facing request.
06CDNs (Content Delivery Networks)

What you will learn

  • Explain what a CDN does and why it improves performance
  • Explain how CDN changes the behavior, result, or engineering decision in a concrete example
  • Connect CDN with edge server and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A CDN caches and serves static content (images, videos, JS/CSS files) from servers geographically distributed close to actual users, rather than all requests traveling back to one origin server. This reduces latency (physical distance directly affects network round-trip time) and reduces load on the origin server itself.

Key concepts

CDNedge serverlatency

Example

# without a CDN: a user in Dubai fetches an image from a server in the US --
# long round trip every time
# with a CDN: that image is cached at a nearby edge server,
# served with much lower latency
Common mistake: Serving large static assets (images, videos) directly from the origin server for a global user base, instead of using a CDN to reduce latency and origin load.
07Consistency vs availability: making the design choice

What you will learn

  • Translate product requirements into consistency/availability choices
  • Explain what the system should do during a partition
  • Explain how consistency requirement changes the behavior, result, or engineering decision in a concrete example
  • Connect consistency requirement with availability requirement and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The CAP theorem itself is taught in Distributed Systems. In System Design, the useful skill is turning consistency and availability requirements into an architecture decision.

Key concepts

consistency requirementavailability requirementpartition behaviorproduct invarianttrade-off decision

Example

Design comparison:
- Payment ledger: reject/queue uncertain writes rather than accept conflicting balances.
- Social activity feed: serving a slightly stale feed may be preferable to becoming unavailable.
The decision starts from the product invariant, not from memorizing CAP labels.
Common mistake: Saying “choose consistency or availability” without stating the actual product invariant or what happens during a partition.
08Availability & reliability

What you will learn

  • Reason about redundancy and single points of failure
  • Explain how availability changes the behavior, result, or engineering decision in a concrete example
  • Connect availability with single point of failure and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Availability is the fraction of time a service successfully provides its required behavior, but engineering teams need a concrete target rather than the vague goal of “high availability.” An SLO states a measurable reliability target such as successful requests or latency over a time window.

Key concepts

availabilitysingle point of failureredundancySLOerror budgetfailure mode analysis

Example

# a single database server with no replica is a single point of failure --
# if it goes down, the whole system goes down
# adding a replica (and automatic failover) removes that single point of failure
Common mistake: Building a critical system component with no redundancy at all, creating an unnecessary single point of failure.
09Estimating scale in system design

What you will learn

  • Do back-of-envelope estimation to guide design decisions
  • Explain how scale estimation changes the behavior, result, or engineering decision in a concrete example
  • Connect scale estimation with back-of-envelope and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Before designing a system, roughly estimating scale (how many users, requests per second, how much data) determines which decisions even matter -- a design that's fine for 100 users may fall apart at 10 million. This estimation doesn't need to be precise, just roughly right, to rule out approaches that clearly won't work at the real expected scale.

Key concepts

scale estimationback-of-enveloperequests per second

Example

# rough estimation example:
# 1 million daily active users, each making ~10 requests/day
# = 10 million requests/day = ~115 requests/second on average
# (with peak traffic likely several times higher than the average)
Common mistake: Designing a system without any rough sense of expected scale, then discovering an approach fundamentally doesn't work once real traffic arrives.
10Designing a distributed data storage service

What you will learn

  • Structure a system-design answer around requirements, partitioning, replication, consistency, caching, and failure recovery
  • Explain how partitioning changes the behavior, result, or engineering decision in a concrete example
  • Connect partitioning with replication and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A distributed-storage design interview should start with requirements: data size, read/write volume, latency, durability, and consistency needs. Then choose an API and data model, partition keys, replication strategy, consistency behavior, caching, and failure handling.

Key concepts

partitioningreplicationconsistencycachefailure recoveryhot key

Example

Example key-value store: hash key to partition -> replicate each partition across failure domains -> route through a service layer -> use quorum/leader rules for writes -> cache hot reads -> monitor imbalance and rebalance partitions when nodes are added.
Common mistake: Starting with a technology list before clarifying requirements.
