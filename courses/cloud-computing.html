01What 'the cloud' actually is

What you will learn

  • Explain cloud computing without buzzwords
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: cloud cost estimation and budgets.
  • Explain how cloud provider changes the behavior, result, or engineering decision in a concrete example
  • Connect cloud provider with on-demand and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

'The cloud' is just someone else's data center, rented by the hour (or the second), accessed over the internet through an API instead of you racking physical servers. Instead of buying a machine, you request compute/storage/networking on demand from a provider (AWS, GCP, Azure), and pay only for what you use.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: cloud cost estimation and budgets.

Key concepts

cloud provideron-demandpay-as-you-gocloud cost estimation and budgets

Example

# Traditional: buy a server, wait weeks, run it 24/7 whether you use it or not
# Cloud: request a VM via an API call, pay per second, delete it when done
Common mistake: Thinking 'the cloud' is one magic thing rather than a rentable version of the same servers/storage/networking you'd otherwise buy yourself.
02Compute: VMs vs containers vs serverless

What you will learn

  • Contrast the three main compute options
  • Explain how VM changes the behavior, result, or engineering decision in a concrete example
  • Connect VM with managed containers and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A VM (virtual machine) gives you a full virtual computer you manage yourself (OS, patches, everything). A managed container service runs your Docker containers without you managing the underlying OS.

Key concepts

VMmanaged containersserverlesscold start

Example

# VM: 'give me a Linux box, I'll install and manage everything'
# Container service: 'run my Docker image, I don't want to manage the OS'
# Serverless: 'run this function when a request comes in, and nothing otherwise'
Common mistake: Choosing serverless for a workload with constant, predictable traffic — you lose the cost benefit (built for spiky/idle patterns) and pay a 'cold start' latency tax for no reason.
03Storage: object vs block vs file

What you will learn

  • Distinguish the three storage types and when each fits
  • Explain how object storage changes the behavior, result, or engineering decision in a concrete example
  • Connect object storage with block storage and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Object storage (like S3) stores whole files/blobs with a flat key-based lookup — great for images, backups, static assets, at massive scale, but not for a running database. Block storage is a raw disk attached to a VM (like a hard drive) — what a database needs.

Key concepts

object storageblock storagefile storage

Example

# Object storage: store 10 million user-uploaded images -> S3
# Block storage: the disk backing your Postgres VM -> EBS
# File storage: a shared folder read by 5 app servers -> EFS
Common mistake: Trying to run a database directly on object storage — it's not designed for the random, low-latency reads/writes a database needs.

Explanation

A cloud network usually lives inside a virtual private network such as a VPC. Public and private subnets separate resources that need direct internet reachability from resources that should stay behind controlled boundaries.

Key concepts

VPCsecurity groupfirewall rulesDNSpublic vs private subnetNAT gateway

Example

# security group on the database: allow inbound port 5432
# ONLY from the app server's security group -- not from 0.0.0.0/0
Common mistake: Opening a database's port to 0.0.0.0/0 (the whole internet) 'just to get it working' — a leading cause of real data breaches.
05Identity & Access Management (IAM)

What you will learn

  • Explain IAM's core model (principals, permissions, roles) and apply least privilege in a cloud environment
  • Explain how IAM changes the behavior, result, or engineering decision in a concrete example
  • Connect IAM with principal and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Security groups (covered earlier) control WHAT TRAFFIC can reach a resource over the network; IAM controls WHO -- or what service -- is allowed to perform WHICH ACTIONS on your cloud resources, regardless of network access.

Key concepts

IAMprincipalrolepermissionpolicyleast privilegeidentity and access management

Example

# Overly broad (avoid): grants full access to every S3 bucket and action
{"Effect": "Allow", "Action": "s3:*", "Resource": "*"}

# Least privilege: this service can only read from one specific bucket
{"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::my-app-uploads/*"}
Common mistake: Granting a service or user broad admin-level permissions because it's faster than scoping a precise policy -- this turns any single leaked credential or buggy script into a much larger blast.
06Load balancers & managed databases

What you will learn

  • Explain what a load balancer does and why managed databases exist
  • Explain how load balancer changes the behavior, result, or engineering decision in a concrete example
  • Connect load balancer with managed database and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A load balancer sits in front of multiple app servers and distributes incoming traffic across them, so no single server is overwhelmed and traffic keeps flowing if one server fails. A managed database (RDS, Cloud SQL) handles backups, patching, and failover for you, so your team doesn't operate the database software itself.

Key concepts

load balancermanaged databasehigh availability

Example

users -> load balancer -> [server1, server2, server3] -> managed database
Common mistake: Running a single app server with no load balancer 'because traffic is low now' — it works until the one server needed a restart during peak hours.

Knowledge checks

Serverless compute is best suited for:
  1. constant, predictable 24/7 load
  2. spiky or infrequent workloads
  3. raw database storage
  4. networking configuration
Object storage (like S3) is best for:
  1. a running database's disk
  2. large numbers of files/blobs at scale
  3. a shared network drive for VMs
  4. firewall rules
A security group is best described as:
  1. a billing report
  2. a firewall for your cloud resources
  3. a load balancer
  4. a type of database
A load balancer's main job is to:
  1. encrypt traffic
  2. distribute traffic across multiple servers
  3. store files
  4. run scheduled jobs
'Designing for failure' mainly means:
  1. assuming failures won't happen
  2. assuming components will eventually fail and architecting around it
  3. avoiding the cloud entirely
  4. using only one availability zone
