01HTML structure & semantics

What you will learn

  • Structure a page with semantic tags instead of generic divs
  • Explain how semantic HTML changes the behavior, result, or engineering decision in a concrete example
  • Connect semantic HTML with document structure and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

HTML gives content structure and meaning. Semantic tags — <header>, <nav>, <main>, <article>, <footer> — describe WHAT something is, not just how it looks, which helps screen readers, search engines, and other developers understand your page at a glance.

Key concepts

semantic HTMLdocument structureaccessibility basics

Example

<body>
  <header><h1>My Site</h1><nav>...</nav></header>
  <main>
    <article><h2>Post title</h2><p>...</p></article>
  </main>
  <footer>© 2026</footer>
</body>
Common mistake: 'Div soup' — building an entire layout from unlabeled <div>s when a semantic tag already exists for that role.
02CSS fundamentals: the box model & selectors

What you will learn

  • Explain the CSS box model
  • Write selectors with the right specificity
  • Explain how box model changes the behavior, result, or engineering decision in a concrete example
  • Connect box model with specificity and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Every element is a box: content, then padding, then border, then margin, from the inside out. CSS selectors target elements to style — by tag, class, id, or relationship (descendant, child) — and specificity determines which rule wins when several apply to the same element (id beats class beats tag).

Key concepts

box modelspecificityselectors

Example

.card {
  padding: 16px;      /* inside the border */
  border: 1px solid #ddd;
  margin: 12px;        /* outside the border */
}
.card.featured { border-color: gold; } /* more specific than .card */
Common mistake: Fighting CSS with !important instead of understanding why a more specific selector is winning — it treats the symptom, not the cause.
03Responsive design: Flexbox, Grid, media queries

What you will learn

  • Build a layout that adapts to different screen sizes
  • Explain how Flexbox changes the behavior, result, or engineering decision in a concrete example
  • Connect Flexbox with Grid and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Responsive design means one page works well from a phone to a desktop. Flexbox arranges items along one axis (great for navbars, button rows); Grid arranges in two dimensions (great for full page layouts).

Key concepts

FlexboxGridmedia queriesmobile-first

Example

.row { display: flex; gap: 12px; }
.layout { display: grid; grid-template-columns: 1fr 1fr 1fr; }
@media (max-width: 600px) {
  .layout { grid-template-columns: 1fr; }
}
Common mistake: Designing desktop-first and bolting on mobile support later — it's far easier to design mobile-first and add complexity as the screen grows.
04JavaScript & the DOM

What you will learn

  • Select, read, and modify DOM elements from JavaScript
  • Respond to user events
  • Explain how DOM changes the behavior, result, or engineering decision in a concrete example
  • Connect DOM with event listeners and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The DOM (Document Object Model) is the live, in-memory tree of your page that JavaScript can read and change. `querySelector` finds elements; `addEventListener` reacts to clicks/input/etc; changing an element's `.textContent` or classes updates what the user sees, instantly, with no page reload.

Key concepts

DOMevent listenersquerySelectorDOM mutation

Example

const btn = document.querySelector('#submit');
btn.addEventListener('click', () => {
  document.querySelector('#status').textContent = 'Submitted!';
});
Common mistake: Directly manipulating dozens of elements ad hoc as an app grows — this is exactly the pain component frameworks (React etc.) exist to solve.
05React fundamentals: components, props & state

What you will learn

  • Build a small React component that manages its own state and reacts to a user event
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: useEffect for side effects, API data fetching, loading and error states.
  • Explain how components changes the behavior, result, or engineering decision in a concrete example
  • Connect components with JSX and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

React builds interfaces from components whose output depends on props and state. State changes trigger re-rendering, while effects are for synchronizing with work outside rendering such as network requests or browser APIs.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: useEffect for side effects, API data fetching, loading and error states.

Key concepts

componentsJSXpropsstateuseStatere-renderinguseEffect for side effectsAPI data fetchingloading and error statesform stateclient-side validationTypeScript props and interfacesfrontend component testingerror boundary

Example

function Greeting({ name }) {
  const [clicked, setClicked] = useState(false);
  return <button onClick={() => setClicked(true)}>
    {clicked ? 'Hi ' + name : 'Click me'}
  </button>;
}
Common mistake: Mutating state directly (state.value = x) instead of calling the setter function (setValue(x)) -- React only re-renders when it detects an update through its own setter, not a raw mutation.
06Accessibility (a11y) fundamentals

What you will learn

  • Connect alt text with labels and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Accessibility means your site works for people using screen readers, keyboard-only navigation, or with visual impairments — not an afterthought, a requirement.

Key concepts

alt textlabelskeyboard navigationcolor contrastdiv onclicksemantic button

Example

<label for="email">Email</label>
<input id="email" type="email">
<img src="chart.png" alt="Revenue grew 40% year over year">
Common mistake: Using a <div onclick=...> as a button — it looks like a button but is invisible to keyboard and screen-reader users, who have no way to activate it.
07Modern frontend architecture: components & state

What you will learn

  • Explain component-based architecture and where state should live
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: client-side routing.
  • Explain how components changes the behavior, result, or engineering decision in a concrete example
  • Connect components with state and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Frontend architecture is about separating responsibilities so a growing UI stays understandable. Components own focused presentation or interaction responsibilities, props move information into components, composition builds larger views, and client-side routing maps URLs to application screens.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: client-side routing.

Key concepts

componentsstatepropscompositionclient-side routingserver state vs UI stateproduction error handlingroute-level loading state

Example

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count+1)}>{count}</button>;
}
// state is LOCAL to this component -- no other component needs it
Common mistake: Putting all state in one giant top-level component 'to be safe' — it works but makes every small change trigger unnecessary re-renders and coupling across the whole app.

Knowledge checks

The CSS box model, from inside out, is:
  1. margin, border, padding, content
  2. content, padding, border, margin
  3. content, border, padding, margin
  4. padding, content, margin, border
Flexbox arranges items along:
  1. two dimensions at once
  2. one axis at a time
  3. a fixed pixel grid only
  4. z-index layers
A <div onclick=...> used as a button is problematic mainly because:
  1. it's slower
  2. it's invisible to keyboard/screen-reader users
  3. it can't have CSS applied
  4. browsers block it
In component architecture, state should generally live:
  1. always in the very top-level component
  2. as close as possible to where it's needed, lifted up only when shared
  3. in global variables
  4. in CSS
Media queries let you:
  1. change JavaScript behavior only
  2. apply different CSS at different viewport widths
  3. query a database
  4. validate forms
