Key concepts

# manual deploys are risky -> teams deploy less often -> each deploy bundles more changes

Explanation

A CI/CD pipeline is a sequence of automated stages a code change passes through: typically build (compile/package the code), test (run automated tests), and deploy (ship it somewhere) -- often with additional stages like lint (style/quality checks) or security scanning in between.

Key concepts

pipeline stagesbuildtestdeployfail-fast ordering

Example

# typical stage order, cheapest/fastest checks first:
# lint (seconds) -> build (compile/package) -> test (run automated tests) -> deploy
# if lint fails, the pipeline stops immediately -- no time wasted running build/test/deploy
# on code that already has an obvious style violation
Common mistake: Running expensive stages before cheap ones -- ordering cheap, fast checks FIRST means failures are caught (and the pipeline stops) as early and cheaply as possible, saving real time on every.

  • Connect test pyramid with unit tests and predict what changes when one assumption changes

Explanation

Pipelines typically run several LAYERS of automated tests: unit tests (fast, test one small piece in isolation, run on every commit), integration tests (slower, test how pieces work together, e.g. with a real database), and end-to-end tests (slowest, test the whole system as a user would experience it, often run less frequently).

Key concepts

test pyramidunit testsintegration testsend-to-end teststest flakiness

Example

# the test pyramid, by SPEED and QUANTITY:
# many unit tests (seconds each, run on every commit)
# fewer integration tests (tens of seconds, run on every commit or merge)
# very few end-to-end tests (minutes each, often run before a deploy, not every commit)
Common mistake: Relying mostly on slow, flaky end-to-end tests instead of a broad base of fast unit tests -- this inverts the test pyramid, making the pipeline slow and unreliable, and is a common.
05Build artifacts & versioning

What you will learn

  • Explain why you build an artifact ONCE and promote the SAME artifact through environments, rather than rebuilding for each
  • Explain how build artifact changes the behavior, result, or engineering decision in a concrete example
  • Connect build artifact with build once, promote everywhere and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A build artifact is the packaged, deployable output of the build stage -- a Docker image, a compiled binary, a zip of built assets. A critical, easy-to-miss principle: build the artifact ONCE, then promote that EXACT SAME artifact through dev, staging, and production -- never rebuild separately for each environment.

Key concepts

build artifactbuild once, promote everywhereartifact versioningenvironment parity

Example

# the risk of rebuilding per environment:
# build for staging -> tests pass -> build AGAIN for production (different day, maybe a
# dependency version shifted) -> production artifact is SUBTLY DIFFERENT from what was tested
#
# the fix: build ONCE, tag it (e.g. app:a1b2c3), and promote that EXACT tagged artifact
# through every environment -- what you tested is EXACTLY what ships
Common mistake: Rebuilding the application separately for each environment -- this breaks the guarantee that what was tested is exactly what gets deployed, reintroducing the very risk automated testing was.

Explanation

Most pipelines move a build through a chain of environments with increasing similarity to production and increasing caution: development (fast feedback, may be unstable), staging (a close mirror of production, used for final verification), and production (real users, real consequences).

Key concepts

environment chainstagingpromotionmanual approval gate

Example

# a typical promotion chain:
# dev (fast feedback, engineers verify basic functionality)
# -> staging (mirrors production config/scale, final automated + manual checks)
# -> production (real users -- often gated by an explicit human approval step)
# the SAME artifact moves through all three -- never rebuilt along the way
Common mistake: Assuming a fully automated pipeline means NO human ever approves a production deploy -- many real, mature CI/CD setups deliberately keep a manual gate before production specifically.
07Deployment strategies

What you will learn

  • Distinguish rolling, blue-green, and canary deployment by HOW and WHEN traffic shifts to the new version
  • Explain how rolling deployment changes the behavior, result, or engineering decision in a concrete example
  • Connect rolling deployment with blue-green deployment and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Rolling deployment updates servers gradually, a batch at a time, so both old and new versions run simultaneously during the rollout -- simple and resource-efficient, but a bug only affects the specific servers already updated.

Key concepts

rolling deploymentblue-green deploymentcanary deploymenttraffic shifting

Example

# the key difference: HOW MUCH traffic sees the new version, and HOW it shifts
# rolling:     gradual server-by-server replacement, no traffic-percentage control
# blue-green:   instant all-or-nothing switch between two full environments
# canary:       fine-grained, gradually-increasing PERCENTAGE of real traffic, watched closely
Common mistake: Treating all three strategies as interchangeable -- they trade off differently between infrastructure cost, rollback speed, and blast-radius control; the right choice depends on which of.

09Pipeline as code

What you will learn

  • Explain why defining a pipeline in a version-controlled config file is preferable to configuring it through a UI
  • Explain how pipeline as code changes the behavior, result, or engineering decision in a concrete example
  • Connect pipeline as code with declarative configuration and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Modern CI/CD pipelines are typically defined in a configuration file (YAML, in tools like GitHub Actions or GitLab CI) that lives in the SAME repository as the code it builds -- 'pipeline as code.' This means pipeline changes go through the same review process as code changes (a pull request).

Key concepts

pipeline as codedeclarative configurationversion-controlled pipeline

Example

# pipeline as code, conceptually (structure varies by tool):
# .github/workflows/ci.yml (or .gitlab-ci.yml) defines:
# stages: [lint, build, test, deploy]
# each stage: what command runs, what triggers it, what it depends on
# this file is REVIEWED and VERSIONED exactly like any other code change
Common mistake: Configuring a pipeline entirely through a CI tool's UI, with no config file in the repository -- this leaves the pipeline definition un-reviewed, unversioned, and disconnected from the code.

13GitOps

What you will learn

  • Explain the core GitOps idea: Git as the single source of truth for desired system state
  • Explain how GitOps changes the behavior, result, or engineering decision in a concrete example
  • Connect GitOps with declarative desired state and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

GitOps takes the 'pipeline as code' idea further: the DESIRED STATE of an entire deployed system (which version is running, how many replicas, configuration values) is described declaratively in a Git repository, and an automated controller continuously works to make the ACTUAL running system match what's in Git.

Key concepts

GitOpsdeclarative desired statereconciliation controllerauditable deployment history

Example

# the GitOps loop, conceptually:
# 1. Git repo says: 'app should be running version v3, with 5 replicas'
# 2. a controller (e.g. ArgoCD, Flux) continuously compares this to the ACTUAL running state
# 3. if they differ, the controller automatically applies changes to match Git
# every production change traces back to a specific, reviewed Git commit
Common mistake: Confusing GitOps with 'just using Git for CI/CD pipeline config' -- GitOps specifically means Git describes the DESIRED RUNNING STATE of the system, with an automated controller actively.

Explanation

Pipeline failures tend to fall into recognizable categories: a genuine code or test failure (the pipeline is correctly catching a real problem -- read the actual error message first); an environment mismatch (works locally, fails in CI, often due to a missing dependency or different tool version between environments).

Key concepts

pipeline failure categoriesenvironment mismatchflaky testsinfrastructure vs code issues

Example

# 'fails every single time, same error' -> likely a real code/test failure -- read the actual message
# 'works on my machine, fails in CI' -> likely an environment mismatch (versions, missing deps)
# 'fails sometimes, no code changed, different failure each time' -> likely a flaky test
# 'CI itself won't even start, or times out with no useful output' -> likely infrastructure
Common mistake: Assuming every pipeline failure is a real bug in the code being tested -- correctly recognizing flaky tests and environment/infrastructure issues as DIFFERENT categories, with different.

Exercises

Order pipeline stages by cost

Given lint (5s), unit tests (30s), integration tests (3min), and deploy -- what's the correct fail-fast order, and why?

Hint

lint -> unit tests -> integration tests -> deploy; cheapest and fastest checks run first so a failure is caught before wasting time on expensive later stages

Diagnose integration hell

A team merges feature branches only once every 3 weeks, and merges routinely take a full day to resolve. What CI practice would most directly address this, and why?

Hint

trunk-based development / frequent small merges (Continuous Integration) -- integrating in small, frequent increments keeps conflicts small and recent instead of large and stale

Rebalance an inverted test pyramid

A pipeline has 500 slow, flaky end-to-end tests and only 20 unit tests. What's wrong with this shape, and what would you recommend?

Hint

this is an inverted test pyramid -- recommend building out a much larger base of fast, reliable unit tests, and trimming e2e tests down to cover only genuinely critical user flows

Spot a build-once violation

A team rebuilds their Docker image separately for staging and production, using the same Dockerfile but run on different days. What real risk does this introduce?

Hint

the artifact tested in staging may not be byte-for-byte identical to what deploys to production (e.g. a dependency version could shift between builds) -- violates build-once-promote-everywhere

Decide where a manual gate belongs

In a dev -> staging -> production pipeline, where would you place a manual approval gate, and why there specifically?

Hint

before production specifically -- a deliberate human decision point right before affecting real users, even in an otherwise fully automated pipeline

Choose a deployment strategy

A team wants to catch a bad deploy while it affects only a small fraction of real users, gradually increasing exposure. Which strategy fits, and why not blue-green?

Hint

canary deployment -- fine-grained, gradually-increasing traffic percentage; blue-green switches ALL traffic at once, so it wouldn't limit exposure to a small fraction first

Trace a rolling deployment

4 servers, batch size 2. After the first batch completes, what does the server-version state look like?

Hint

2 servers on the new version, 2 still on the old version -- both versions serving traffic simultaneously mid-rollout

Design a feature-flag rollout

You want to ship a risky new checkout flow. Describe how you'd use a feature flag to deploy it safely well before it's fully tested.

Hint

deploy the code with the flag OFF for everyone (dark launch) -- it's in production but inactive; later flip it on for a small percentage, watch metrics, then gradually increase, all without another deploy

Explain pipeline-as-code's review benefit

A pipeline is configured entirely through a CI tool's UI, with no YAML file in the repo. What real problem does this create?

Hint

pipeline changes aren't reviewed like code changes and aren't versioned alongside the code history -- there's no pull request, no diff, no way to see what the pipeline looked like for an old commit

Fix a secrets leak

A pipeline YAML file contains the line `api_key: 'sk_live_abc123'` directly. What's wrong, and what's the fix?

Hint

the secret is hard-coded in a version-controlled file, permanently in git history and visible to anyone with repo access; fix by moving it to the CI platform's secrets store and referencing it as an injected environment variable

Explain a caching win

A build takes 2 minutes without caching (re-downloading all dependencies) and 5 seconds with a warm cache. Why does this matter beyond convenience?

Hint

a slow pipeline discourages the frequent, small commits Continuous Integration depends on -- caching keeps the feedback loop fast enough that engineers don't avoid running the pipeline often

Diagnose a rollback that isn't actually safe

A deploy renamed a database column from `name` to `full_name`. The new code has a bug, so the team rolls back to the OLD code. What goes wrong?

Hint

the old code expects a column called `name`, which no longer exists after the migration -- a code-only rollback breaks against the already-migrated schema; migrations need to be backward-compatible for this to work safely

Explain the GitOps reconciliation loop

In a GitOps setup, a team wants to scale a service from 3 to 5 replicas. What do they actually change, and what happens next?

Hint

they change the desired replica count in the Git repository (not the live cluster directly); a controller detects the difference between desired (5) and actual (3) state and applies the change automatically

Categorize a pipeline failure

A test fails intermittently, with a different error each time, and no code has changed recently. What category of failure is this most likely, and what would you check?

Hint

likely a flaky test -- check for timing assumptions, shared state between tests, or reliance on external services that aren't properly mocked/isolated

Diagnose 'works on my machine'

A test passes locally but fails in CI with no code changes. What category of issue is this, and what's a likely specific cause?

Hint

an environment mismatch -- likely causes include a different dependency or language/tool version installed in CI versus locally, or a missing environment variable/config that exists locally but not in CI

Combine deployment strategy with feature flags

Hint

canary controls WHICH SERVERS run the new code; the feature flag controls WHETHER the new behavior is even active once running -- combining both means you can deploy broadly but activate the risky behavior even more narrowly and independently

Justify a manual gate against 'full automation'

Hint

a deliberate manual approval gate before production is a common, intentional safety practice even in mature pipelines -- full automation and human oversight aren't opposed; the goal is safe frequent shipping, not the complete absence of any human judgment

Trace the full 'ship safely and often' chain

Hint

CI keeps each change small; automated testing catches problems before users see them; the deployment strategy limits how many users a bad change affects if it slips through; feature flags let you decouple deploying from activating a risky change -- each layer catches what the others might miss
