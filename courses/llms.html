Example

# rough intuition (varies by tokenizer):
# 'the' -> 1 token
# 'photosynthesis' -> maybe 2-3 tokens
# a rare technical term or non-English word -> often even more tokens per word

04Inference & decoding: greedy, sampling & temperature

What you will learn

  • Explain how a trained LLM turns probabilities into an actual generated response
  • Explain how greedy decoding changes the behavior, result, or engineering decision in a concrete example
  • Connect greedy decoding with sampling and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

At each step, an LLM computes a probability distribution over its entire vocabulary for the next token. Greedy decoding always picks the single highest-probability token (deterministic, but can be repetitive/boring).

Key concepts

greedy decodingsamplingtemperature

Example

# temperature intuition:
# temperature -> 0: almost always picks the top token (deterministic, focused)
# temperature = 1: samples proportional to the model's real learned probabilities
# temperature > 1: flattens the distribution further, more random/surprising choices
Common mistake: Using high temperature for tasks needing precise, factual, repeatable output (like structured data extraction) — that's exactly where LOW temperature (or greedy decoding) is the right.
05Context windows in practice

What you will learn

  • Make practical trade-offs around a model's context window limit
  • Explain how context budget management changes the behavior, result, or engineering decision in a concrete example
  • Connect context budget management with truncation vs summarization and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Building on the Transformers track's explanation of WHY context windows are computationally expensive, this lesson is about the PRACTICAL side: everything you want the model to consider — system instructions, conversation history, retrieved documents, the user's question — must fit within one finite token budget, competing with each other.

Key concepts

context budget managementtruncation vs summarizationretrieval as a context-budget strategycontext budget

Example

# a context budget is a competition for space:
# system prompt (500 tokens) + conversation history (variable) + retrieved docs (variable) + user question
# -- all must fit inside, say, an 8,000 token limit -- something has to be prioritized/trimmed
Common mistake: Naively appending the full conversation history to every request with no trimming strategy — long conversations will eventually exceed the context limit or silently push out important.
06Hallucinations

What you will learn

  • Explain why LLMs hallucinate and describe practical mitigation strategies
  • Explain how hallucination changes the behavior, result, or engineering decision in a concrete example
  • Connect hallucination with fabricated confidence and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

LLMs generate plausible-sounding text based on learned patterns, with no built-in mechanism to verify factual truth — a confident, fluent, completely fabricated citation or statistic is not a rare glitch, it's an expected failure mode of how these models fundamentally work.

Key concepts

hallucinationfabricated confidencegrounding as mitigation

Example

# a hallucination looks EXACTLY as confident and fluent as a correct answer --
# there's no built-in 'uncertainty flag' the model reliably surfaces on its own
# this is precisely the problem RAG (grounding in real retrieved documents) is designed to reduce
Common mistake: Trusting an LLM's confident tone as a signal of factual accuracy — confidence and correctness are not correlated the way they are in human communication; fluency is not evidence of truth.

09Safety, responsible use & open vs closed models

What you will learn

  • Contrast open and closed model access models, and describe responsible-use basics
  • Explain how open vs closed models changes the behavior, result, or engineering decision in a concrete example
  • Connect open vs closed models with self-hosting trade-offs and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Closed models (accessed via an API, weights not available) are typically easier to use and stay current, but you depend entirely on the provider for availability, pricing, and policy changes. Open-weight models can be self-hosted, audited, and fine-tuned freely, at the cost of needing your own infrastructure and expertise to run well.

Key concepts

open vs closed modelsself-hosting trade-offsresponsible-use basicsdistinguishes an open modelself-hosting

Example

# closed (API-based): fast to start, provider handles infra, but you don't control the weights or guarantee availability
# open-weight: full control, can self-host and fine-tune freely, but you own the operational burden
Common mistake: Assuming this choice is purely technical — it also has real business implications (vendor lock-in, cost predictability, data privacy requirements) that should factor into the decision.

Diagnose a response that ignores earlier context

Hint

  1. classifying entire documents

  1. the total training dataset size

  1. it doesn't affect real costs
