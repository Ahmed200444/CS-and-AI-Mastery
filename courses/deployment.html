Explanation

Deployment turns local code into a reliable service other people or systems can call. Define a stable service interface, package the runtime, externalize configuration, expose health signals, and verify startup/shutdown behavior.

Key concepts

service interfaceruntime packagingconfigurationhealth signalproduction process

Example

# conceptual FastAPI service boundary
from fastapi import FastAPI
app = FastAPI()

@app.get('/health')
def health():
    return {'status': 'ok'}
Common mistake: Deploying code that works locally without accounting for environment differences (dependencies, config) between local and production.
02Service contracts, health checks & readiness

What you will learn

  • Separate liveness from readiness
  • Design health endpoints that do not lie about dependencies
  • Explain how liveness changes the behavior, result, or engineering decision in a concrete example
  • Connect liveness with readiness and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A deployed service needs a clear contract and health signals. Liveness answers whether the process is alive; readiness answers whether it can safely receive traffic.

Key concepts

livenessreadinesshealth endpointstartup statedependency readiness

Example

ready = False

def health():
    return {'alive': True}

def readiness():
    return {'ready': ready}
Common mistake: Returning “healthy” before required startup work is complete can send real traffic to a service that cannot serve it.

04Environment variables & configuration

What you will learn

  • Use environment variables to separate configuration from code
  • Explain how environment variables changes the behavior, result, or engineering decision in a concrete example
  • Connect environment variables with configuration and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Environment variables store configuration (API keys, database URLs, feature flags) OUTSIDE the codebase itself, so the same code can run differently in development, staging, and production just by changing the environment it runs in -- without ever hardcoding secrets or environment-specific values directly into source code.

Key concepts

environment variablesconfigurationhardcoding secrets

Example

import os
database_url = os.environ.get('DATABASE_URL')
api_key = os.environ.get('API_KEY')
# the SAME code runs against different databases/keys per environment
Common mistake: Hardcoding a secret or environment-specific value (like a production database URL) directly into source code -- this leaks into version control and can't differ across environments.
05Artifacts, model loading & startup lifecycle

What you will learn

  • Version runtime artifacts
  • Load large artifacts once at startup
  • Fail fast when required artifacts are invalid

Explanation

Production services often depend on model weights, indexes, templates, or other versioned artifacts. Load expensive immutable artifacts during startup rather than once per request, validate their version/checksum, and make startup fail clearly if a required artifact is missing or incompatible.

Key concepts

artifact versionmodel loadingstartup lifecyclechecksumfail fast

Example

from pathlib import Path
MODEL = Path('model.bin')
if not MODEL.exists():
    raise RuntimeError('required model artifact missing')
# load once during startup, then reuse for requests
Common mistake: Loading a large model or index on every request destroys latency and can exhaust memory under concurrency.
06Logging in production

What you will learn

  • Connect logging with log levels and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Once code is running in production, you can't attach a debugger to it the way you can locally -- logging is often your only window into what actually happened.

Key concepts

logginglog levelsstructured logging

Example

import logging
logging.info('Order %s processed successfully', order_id)
logging.error('Payment failed for order %s: %s', order_id, error_message)
Common mistake: Relying only on print statements in a deployed production system -- these aren't leveled, searchable, or aggregable the way real logging is.

08Scaling workers, concurrency & resource limits

What you will learn

  • Choose a worker/concurrency model
  • Set explicit resource limits
  • Recognize CPU-bound vs I/O-bound serving constraints

Explanation

Scaling is not just adding replicas. Decide how many requests one process can safely handle, whether work is CPU-bound or I/O-bound, how much memory each worker consumes, and when horizontal replicas are safer than increasing concurrency inside one process.

Key concepts

workerconcurrencyhorizontal scalingCPU boundI/O boundmemory limit

Example

workers = 4
memory_per_worker_mb = 700
print('estimated memory MB:', workers * memory_per_worker_mb)
Common mistake: Increasing worker count without measuring memory or CPU can make a service slower or cause out-of-memory restarts.
09Timeouts, graceful shutdown & runtime failure

What you will learn

  • Use timeouts around external calls
  • Stop accepting new work during shutdown
  • Let in-flight work finish or cancel safely

Explanation

Production processes are restarted, rescheduled, and terminated. External calls need timeouts so requests cannot hang forever, and shutdown should stop new work before releasing resources.

Key concepts

timeoutgraceful shutdownin-flight requesttermination signalcleanup

Example

# shutdown sequence, conceptually:
# 1. mark readiness = false
# 2. stop accepting new requests
# 3. wait briefly for in-flight work
# 4. close clients/files and exit
Common mistake: Ignoring termination signals can drop in-flight requests and leave external resources in an uncertain state.
10Post-deploy smoke tests & runtime validation

What you will learn

  • Verify a deployed service through its public boundary
  • Check critical dependencies and one realistic request
  • Separate deployment validation from the CI pipeline itself

Explanation

After a service starts, validate the actual deployed runtime: call the health/readiness endpoints, send one realistic request through the public interface, verify a critical dependency, and confirm logs/metrics appear. CI/CD decides how a release is delivered; smoke validation proves the running instance actually works.

Key concepts

smoke testruntime validationhealth checkdependency checkobservability signal

Example

# conceptual smoke checks
checks = ['GET /health -> 200', 'GET /ready -> 200', 'POST /predict sample -> valid schema', 'metric emitted']
for check in checks:
    print('verify:', check)
Common mistake: Treating “the deployment command succeeded” as proof the application is usable misses startup, dependency, and routing failures.

Diagnose a canary that let a bad release through

Hint
