01What prompting is & instruction clarity

What you will learn

  • Write a clear, unambiguous instruction for an LLM
  • Explain how prompting as control surface changes the behavior, result, or engineering decision in a concrete example
  • Connect prompting as control surface with instruction specificity and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Prompting is controlling a model's behavior purely through the input text you give it, with no code or weight changes.

Key concepts

prompting as control surfaceinstruction specificityambiguity in = ambiguity out

Example

# vague: 'Summarize this article'
# clear: 'Summarize this article in exactly 3 bullet points, each under 15 words, focused on the financial impact only'
Common mistake: Assuming a model will 'figure out what I meant' the way a human colleague might — being explicit about format, length, and focus consistently produces more reliable, repeatable results than vague requests.
02Context, constraints & zero/few-shot prompting

What you will learn

  • Apply zero-shot and few-shot prompting, and supply the right context/constraints
  • Explain how zero-shot changes the behavior, result, or engineering decision in a concrete example
  • Connect zero-shot with few-shot prompting and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Zero-shot prompting asks the model to perform a task with no examples, relying purely on instructions. Few-shot prompting includes a small number of example input/output pairs directly in the prompt, which often dramatically improves consistency for tasks with a specific format or style that's hard to describe in words alone.

Key concepts

zero-shotfew-shot promptingcontextconstraints

Example

# few-shot example pattern:
# 'Classify sentiment.\nText: I love this! -> positive\nText: This is terrible. -> negative\nText: {new_input} -> '
# the two examples teach the FORMAT and STYLE expected, not just the instruction
Common mistake: Providing few-shot examples that are inconsistent with each other in format or style — the model will often pick up on and reproduce that inconsistency rather than converging on one clean.
03Role prompting & structured output

What you will learn

  • Use role prompting to set behavior, and request reliably parseable structured output
  • Explain how role prompting changes the behavior, result, or engineering decision in a concrete example
  • Connect role prompting with structured output and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Role prompting ('You are a senior code reviewer..') sets a frame that shapes tone, vocabulary, and focus without needing to spell out every expectation explicitly.

Key concepts

role promptingstructured outputschema-constrained generation

Example

# role: 'You are a strict security auditor. Review this code for vulnerabilities only.'
# structured output: 'Respond with ONLY valid JSON: {"vulnerabilities": [...], "severity": "low|medium|high"}'
Common mistake: Asking for JSON output but not explicitly forbidding extra prose ('Here's your JSON:') around it — this breaks naive parsing; be explicit that the response must be ONLY the JSON, nothing else.
04Prompt decomposition & step-by-step reasoning prompts

What you will learn

  • Break a complex task into smaller prompted steps, and use step-by-step reasoning prompts
  • Explain how prompt decomposition changes the behavior, result, or engineering decision in a concrete example
  • Connect prompt decomposition with step-by-step reasoning prompts and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Complex tasks often work better broken into smaller prompted steps (decomposition) than attempted in one giant prompt — each step is easier to verify and debug independently.

Key concepts

prompt decompositionstep-by-step reasoning promptsoutput verifiability

Example

# decomposition: instead of one prompt doing 'extract data AND validate it AND format a report',
# do 3 separate prompts, each with a narrow, checkable job

# step-by-step reasoning prompt:
# 'Think through this step by step, then give your final answer on the last line.'
Common mistake: Assuming a single mega-prompt can reliably do everything at once — decomposed steps are each individually easier to test, debug, and improve than one large, hard-to-diagnose prompt.
05Prompt templates, testing & versioning

What you will learn

  • Build a reusable prompt template and treat prompts as versioned, tested artifacts
  • Explain how prompt templates changes the behavior, result, or engineering decision in a concrete example
  • Connect prompt templates with prompt testing and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A prompt template has fixed instructions with variable slots filled in per request (e.g. `f"Summarize this in {n} sentences: {text}"`), letting you reuse a tested pattern reliably across many inputs.

Key concepts

prompt templatesprompt testingprompt versioningprompt templatecontrol surfacereduce the need for post-processing

Example

PROMPT_TEMPLATE_V3 = "Summarize the following in {n} sentences, focusing on {focus}:\n\n{text}"
# test this template against 10 representative real inputs BEFORE deploying a wording change
# keep V2 available to roll back to if V3 regresses on the test set
Common mistake: Editing a production prompt directly with no test set to check against — a seemingly small wording tweak can quietly break behavior for edge cases you didn't think to check by hand.
06Iterating on prompts systematically

What you will learn

  • Improve a prompt through deliberate, testable iteration
  • Explain how prompt iteration changes the behavior, result, or engineering decision in a concrete example
  • Connect prompt iteration with systematic testing and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Prompt engineering is rarely right on the first try -- it's an iterative process: write a prompt, test it against real/representative inputs, identify exactly where it fails, adjust one thing, and retest. Treating this like debugging (isolate the failure, change one variable) is far more effective than rewriting the whole prompt randomly hoping it improves.

Key concepts

prompt iterationsystematic testingone change at a timechange only one variable

Example

# iteration loop:
# 1. write prompt v1, test on 5 real examples
# 2. note exactly which examples failed and how
# 3. change ONE thing (e.g. add a constraint) -> v2
# 4. retest the SAME 5 examples, compare
Common mistake: Rewriting an entire prompt from scratch after one failure, instead of isolating and changing just the part that's actually causing the problem.
07Evaluation criteria for prompts

What you will learn

  • Define concrete criteria to judge whether a prompt is working well
  • Explain how prompt evaluation criteria changes the behavior, result, or engineering decision in a concrete example
  • Connect prompt evaluation criteria with test sets and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A prompt is 'good' only relative to explicit criteria: does it reliably produce the right FORMAT (parseable, complete), the right CONTENT (accurate, relevant, appropriately scoped), and consistent behavior across a range of realistic inputs (not just the one example you tried first)?

Key concepts

prompt evaluation criteriatest setsformat vs content checksformat checks and content checks

Example

# evaluation checklist for a prompt, run against 15-20 representative test inputs:
# - format: valid, parseable, matches schema? (checkable automatically)
# - content: accurate, on-topic, appropriately scoped? (often needs human/LLM-graded review)
# - consistency: does behavior hold across edge cases (empty input, very long input, adversarial input)?
Common mistake: Judging a prompt as 'working' after trying it on one or two inputs — real prompt evaluation needs a representative test set covering typical AND edge cases before you trust it in production.

Multimodal prompting extends these same principles (clarity, structure, few-shot examples) to inputs that include images or audio alongside text — describing what to look for or listen for just as specifically as you would for text.

Knowledge checks

Few-shot prompting primarily helps by:
  1. training new model weights
  2. showing example input/output pairs to stabilize format and style
  3. increasing the context window
  4. replacing the need for instructions
Structured output prompting is most important when:
  1. a human will read the response directly
  2. your code needs to reliably parse the response
  3. the prompt is very short
  4. using role prompting
Prompt injection risk mainly comes from:
  1. the model's training data size
  2. untrusted input containing text designed to hijack instructions
  3. using too few examples
  4. using a small context window
Prompting alone CANNOT reliably:
  1. set a tone or role
  2. teach the model new facts it wasn't trained on
  3. request a specific output format
  4. provide examples of desired behavior
A prompt template is best described as:
  1. a one-time-use prompt
  2. fixed instructions with variable slots, reused across requests
  3. a type of guardrail only
  4. a model architecture

  1. prompting has no real effect on model behavior
  2. it's the primary way to steer a model's behavior and output without changing its underlying weights
  3. control surface refers only to physical hardware
  4. prompting only works for image models
What does 'ambiguity in = ambiguity out' mean?
  1. ambiguous prompts always produce better creative output
  2. a vague or unclear prompt tends to produce a vague or unpredictable response
  3. ambiguity has no effect on output quality
  4. this only applies to few-shot prompting

  1. providing many labeled examples before the actual task
  2. asking the model to perform a task with no examples provided, relying on its general capability
  3. training the model from scratch
  4. a synonym for temperature
What is few-shot prompting?
  1. providing zero examples
  2. including a small number of examples in the prompt to demonstrate the desired pattern or format
  3. fine-tuning the model's weights
  4. a synonym for zero-shot

  1. constraints always confuse the model
  2. constraints shape the output format/scope directly, rather than hoping the model infers your implicit expectations
  3. constraints are ignored by all models
  4. constraints only work with few-shot prompting

  1. asking the model to remember your name
  2. instructing the model to adopt a specific persona or perspective (e.g. 'act as a security reviewer') to shape its response style
  3. a synonym for temperature
  4. only usable with images

  1. it slows down generation with no benefit
  2. it produces output in a predictable, parseable format that downstream code can reliably process
  3. structured output requests are always ignored
  4. this only works for numeric data

  2. breaking a complex task into smaller, sequential sub-prompts or steps
  3. a synonym for temperature
  4. deleting parts of a prompt randomly

  3. reasoning prompts only work for math problems
  4. this technique only applies to zero-shot prompting

  1. the output can never be checked
  2. being able to inspect the model's intermediate reasoning steps, not just the final answer, to judge whether the logic holds up
  3. verifiability only applies to structured output
  4. this concept doesn't apply to language models

  1. a fixed, unchangeable prompt

  4. only used for image generation prompts

  1. prompt versioning is unnecessary busywork

  4. a required part of every prompt

  1. there's no meaningful distinction

  1. validation is never necessary
