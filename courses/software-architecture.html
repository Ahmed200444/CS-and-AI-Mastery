01Why architecture matters

What you will learn

  • Explain what 'good architecture' actually buys a team, in concrete terms
  • Explain how software architecture changes the behavior, result, or engineering decision in a concrete example
  • Connect software architecture with cost of change and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Architecture isn't about following rules for their own sake -- it's about making a codebase cheaper to CHANGE over time. A poorly structured system might work fine on day one, but every new feature gets slower to add, every bug fix risks breaking something unrelated, and onboarding a new engineer takes weeks instead of days.

Key concepts

software architecturecost of changemaintainability

Example

# the real question architecture answers:
# NOT: 'does this code work right now?'
# BUT: 'when the requirements change next month (they will), how much of
# this code has to change, and how confident can we be that we didn't break something else?'
Common mistake: Judging architecture purely by 'does it work today' -- the real test is how the codebase behaves when requirements inevitably shift, not its state at initial launch.

Explanation

Coupling measures how much one piece of code depends on the internal details of another -- high coupling means changing one module frequently breaks or requires changing another. Cohesion measures how closely related the responsibilities WITHIN a single module are -- high cohesion means a module does one clear job, not several unrelated ones.

Key concepts

# LOW cohesion: a single 'Utils' class handles date formatting, network calls, AND email sending
# the goal: modules with ONE clear job (high cohesion), that don't reach into each other's internals (low coupling)

03The Single Responsibility Principle

What you will learn

  • State the Single Responsibility Principle precisely, and distinguish it from 'a class should be small'
  • Explain how Single Responsibility Principle changes the behavior, result, or engineering decision in a concrete example
  • Connect Single Responsibility Principle with reason to change and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The Single Responsibility Principle states that a class should have only ONE reason to change -- not that it should be short, and not that it should do only one literal action.

Key concepts

Single Responsibility Principlereason to changecohesion in practice

Example

# NOT about size -- about REASONS TO CHANGE:
# UserRepository: reason to change = how users are stored (database schema, ORM version)
# UserEmailFormatter: reason to change = how emails are worded/templated
# these are genuinely DIFFERENT reasons -- which is exactly why they belong in separate classes
Common mistake: Treating SRP as 'keep classes small' -- a class can be small and still violate SRP (if its few lines serve two unrelated purposes), and a class can be somewhat large while still honoring SRP.

05Liskov Substitution & Interface Segregation

What you will learn

  • Explain both principles with the classic Square/Rectangle example and a 'fat interface' example
  • Explain how Liskov Substitution Principle changes the behavior, result, or engineering decision in a concrete example
  • Connect Liskov Substitution Principle with Interface Segregation Principle and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The Liskov Substitution Principle says a subclass should be usable anywhere its parent is expected, without breaking correctness -- the classic violation is a Square inheriting from Rectangle but breaking any code that sets width and height independently (since a square can't honor that).

Key concepts

Liskov Substitution PrincipleInterface Segregation Principlefat interfaceis-a vs has-a

Example

# LSP violation: Square(Rectangle) breaks code that expects independent width/height setting
# ISP violation: a 'Worker' interface with work(), eat(), sleep() forces a Robot
# implementation to awkwardly implement eat() and sleep(), which make no sense for it
# fix (ISP): split into separate, focused interfaces -- Workable, Eatable, Sleepable
Common mistake: Forcing an inheritance relationship because it 'seems similar' (like Square/Rectangle) -- similarity isn't the same as a genuine is-a relationship that holds for EVERY operation the parent.

Explanation

The Strategy pattern lets you swap an ALGORITHM at runtime by wrapping each variant in its own class implementing a shared interface -- e.g. different discount calculations, different sorting approaches, different payment-processing rules, selected based on context.

Key concepts

Strategy patternFactory patternruntime behavior swappingcentralized object creation

Example

# Strategy: swap the ALGORITHM
# cart.strategy = PercentOff(20)  # or NoDiscount(), or BuyOneGetOne()
# cart.total(100)  # uses whichever strategy is currently set
#
# Factory: centralize OBJECT CREATION
# shape = shape_factory('circle', radius=2)  # caller doesn't need to know it's a Circle class
Common mistake: Reaching for Strategy or Factory when a simple if/else with 2 stable cases would do -- patterns solve GROWTH and CHANGE problems; applying one to something that will never grow just adds.

09Adapter & Facade patterns

What you will learn

  • Distinguish Adapter (make incompatible interfaces work together) from Facade (simplify a complex interface)
  • Explain how Adapter pattern changes the behavior, result, or engineering decision in a concrete example
  • Connect Adapter pattern with Facade pattern and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The Adapter pattern lets two pieces of code with INCOMPATIBLE interfaces work together, by wrapping one so it exposes the interface the other expects -- e.g. a third-party payment library with its own method names, wrapped so your code can call it through your OWN standard payment interface.

Key concepts

Adapter patternFacade patterninterface compatibilitysubsystem simplification

Example

# Adapter: bridge an INCOMPATIBLE interface
# ThirdPartyPayment has charge_customer(amount, token) -- your code expects pay(amount)
# PaymentAdapter.pay(amount) internally calls third_party.charge_customer(amount, self.token)
#
# Facade: SIMPLIFY a complex subsystem
# checkout.complete(cart)  # internally coordinates inventory, payment, shipping, notification --
# calling code only ever sees this one simple method
Common mistake: Confusing Adapter with Facade because both 'wrap' something -- Adapter exists because two interfaces are INCOMPATIBLE and need bridging; Facade exists because an interface is too COMPLEX and.

11Clean architecture & layering

What you will learn

  • Explain the core idea behind clean/layered architecture: dependencies point inward, toward business logic
  • Explain how clean architecture changes the behavior, result, or engineering decision in a concrete example
  • Connect clean architecture with layered architecture and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Clean (or layered, or hexagonal) architecture organizes code so business logic sits at the CENTER, with no dependency on outer layers like the database, the web framework, or the UI -- those outer layers depend ON the business logic, never the reverse.

Key concepts

clean architecturelayered architecturehexagonal architecturedependency direction

Example

# dependency direction is the whole idea:
# Web framework -> Business logic -> Database interface <- Database implementation
# (arrows point TOWARD business logic, never away from it)
# business logic never imports or knows about Flask, Postgres, or React specifically --
# it just knows about its OWN interfaces, which outer layers implement
Common mistake: Assuming clean architecture means 'more files and more folders' -- the actual test is the DIRECTION dependencies point; adding layers without enforcing that direction doesn't achieve any of.

Explanation

Key concepts

code smelllong methodduplicated codefeature envyrefactoring

Example

# recognizing smells by their SYMPTOM, then applying the matching refactor:
# 'this method is 200 lines and does five different things' -> extract smaller methods

Exercises

Diagnose an SRP violation

A class named `UserManager` saves users to a database, sends welcome emails, AND generates PDF reports. Explain which principle this violates and how you'd split it.

Hint

violates SRP -- three unrelated reasons to change (storage, email, PDF generation); split into UserRepository, WelcomeEmailSender, and UserReportGenerator

Spot an Open/Closed violation

A function has a long if/elif chain checking `shape_type` to calculate area. A new shape type is being added. What would you refactor toward, and why?

Hint

refactor toward polymorphism -- each shape as its own class implementing area(); adding a new shape means writing a new class, not editing the existing if/elif chain

Identify a Liskov violation

A `ReadOnlyList` inherits from `List` but throws an exception on `append()`. Code that works correctly with any `List` (calling append freely) breaks when given a `ReadOnlyList`. What's happening, and what's the real fix?

Hint

a genuine LSP violation -- ReadOnlyList can't honor everything List promises; the real fix is not making ReadOnlyList inherit from List at all (composition or a separate, smaller interface instead)

Fix a fat interface

A `Worker` interface requires `work()`, `eat()`, and `sleep()`. A `RobotWorker` class must implement all three, but `eat()` and `sleep()` make no sense for it. What ISP-based fix would you apply?

Hint

split into separate, focused interfaces (e.g. Workable, Eatable, Sleepable); RobotWorker only implements Workable, without being forced into meaningless eat()/sleep() implementations

Apply dependency injection

A class hard-codes `self.db = PostgresDB()` inside its constructor. Rewrite this using dependency injection, and explain the specific testing benefit.

Hint

change the constructor to accept db as a parameter (self.db = db); tests can now inject a FakeDB() instead of needing a real Postgres connection

Choose Strategy or Factory

You need to (a) select which shipping-cost algorithm applies based on region, and (b) create the correct Shape subclass based on a string name. Which pattern fits each, and why?

Hint

(a) Strategy -- swapping the ALGORITHM used at runtime; (b) Factory -- centralizing which concrete class gets CREATED

Design an Observer scenario

When an order is placed, three unrelated things must happen: send a confirmation email, update analytics, and adjust inventory. Design this with the Observer pattern -- what's the subject, and what are the observers?

Hint

the order-placement event is the subject; email sender, analytics tracker, and inventory updater are three independent observers, each notified without the subject needing to know about them specifically

Avoid a Decorator subclass explosion

A coffee-ordering system has Coffee, MilkCoffee, SugarCoffee, MilkSugarCoffee, MilkSugarCreamCoffee... explain why this is a problem and how Decorator fixes it.

Hint

this is a combinatorial explosion -- N optional add-ons require up to 2^N subclasses; Decorator fixes it by wrapping a base Coffee with independent decorator layers (MilkDecorator, SugarDecorator) that combine freely without needing a subclass per combination

Distinguish Adapter from Facade

You're integrating a third-party payment library with different method names than your codebase uses. Separately, you also want one simple method that coordinates inventory, payment, and shipping for checkout. Which pattern is which?

Hint

the payment-library integration is Adapter (bridging incompatible interfaces); the coordinated checkout method is Facade (simplifying a complex multi-part subsystem)

Critique a Singleton use case

A team uses a Singleton for their application's database connection pool, accessed globally throughout the codebase. What's a concrete testing problem this creates, and what alternative would you suggest?

Hint

tests can't easily substitute a fake connection pool, since code reaches for the one global Singleton instance directly; suggest passing the pool explicitly via dependency injection instead

Trace a dependency direction

In a clean-architecture design, does the business logic layer import the specific database library (e.g. psycopg2), or does the database layer import an interface defined by the business logic? Explain why.

Hint

the database layer implements an interface DEFINED by the business logic (e.g. an OrderRepository interface); business logic never imports the specific database library directly -- dependencies point inward, toward the business logic

Identify a code smell

A method is 220 lines long and handles validation, database saving, email sending, and logging all in one function. Name the smell and the refactor.

Hint

a 'long method' smell (likely also an SRP violation); refactor by extracting each concern (validation, saving, emailing, logging) into its own well-named method or class

Spot feature envy

A method on `OrderPrinter` reads five different fields directly from a `Customer` object to format an address, and doesn't use any of OrderPrinter's own data. What smell is this, and where should the logic likely move?

Hint

feature envy -- the method uses Customer's data far more than OrderPrinter's own; the address-formatting logic likely belongs on Customer (or a dedicated AddressFormatter) instead

Weigh monolith vs microservices honestly

A 5-person startup with one small product is considering microservices from day one. What would you advise, and why?

Hint

likely advise starting with a monolith -- microservices' operational complexity and distributed-systems costs (network calls, partial failure) usually aren't worth paying at this size; the trade-off makes more sense at larger scale/team size

Run a design-focused review checklist

Given a class that both validates user input AND persists it to a database, walk through at least 2 of the design-review checklist questions from this course against it.

Hint

e.g. 'does this have one reason to change?' -- no, validation rules and storage details are two separate reasons; 'is there duplicated logic nearby?' -- worth checking if similar validation exists elsewhere and should be extracted

Recognize premature abstraction

A developer adds a Strategy interface with a plugin-style architecture for a discount calculation that will only ever have one implementation, 'in case we need more later.' Evaluate this decision.

Hint

likely premature abstraction (over-engineering) -- with no concrete evidence of multiple real implementations needed, a plain function would be simpler and equally correct; the pattern should follow demonstrated variation, not speculation

Diagnose an Open/Closed AND SRP violation together

A `ReportGenerator` class has a `generate(format)` method with an if/elif chain for 'pdf', 'csv', and 'html', and ALSO handles saving the file and emailing it. Identify both violations and propose a fix.

Hint

OCP violation: adding a new format means editing the existing if/elif; SRP violation: format generation, saving, and emailing are three separate reasons to change. Fix: separate format-specific generator classes (OCP), plus separate FileSaver and EmailSender classes (SRP)

Choose composition over inheritance for a DI-friendly design

Design a `NotificationService` that can send via email OR SMS, decided at construction time, and is easy to unit test. Sketch the class relationships (in words, not code) using concepts from this course.

Hint

use dependency injection: NotificationService accepts a Sender interface (Strategy pattern) in its constructor; EmailSender and SMSSender each implement Sender; tests inject a FakeSender to verify behavior without real email/SMS calls
