01Engineering lifecycle: problem → production

What you will learn

  • Trace a feature from problem statement through production feedback.
  • Explain how software lifecycle changes the behavior, result, or engineering decision in a concrete example
  • Connect software lifecycle with delivery loop and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Professional software engineering is a feedback loop, not just coding. A feature begins with a problem and constraints, becomes an agreed requirement, gets designed and implemented in small reviewable changes, is verified, released, observed in production, and then improved using real feedback.

Key concepts

software lifecycledelivery loopfeedback

Example

feature = {"problem":"duplicate orders","acceptance":"retrying a request creates one order","release":"canary"}
for stage in ["clarify","design","implement","test","review","release","observe"]:
    print(stage, "->", feature["problem"])
Common mistake: Starting implementation before the problem, constraints, and acceptance criteria are clear creates rework that good engineering process could have prevented.
02Requirements, user stories & acceptance criteria

What you will learn

  • Turn a vague request into testable acceptance criteria.
  • Explain how requirements changes the behavior, result, or engineering decision in a concrete example
  • Connect requirements with user story and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A useful requirement describes observable behavior, not a preferred implementation. User stories can capture who needs what and why, but acceptance criteria make the request testable by defining examples, boundaries, and failure behavior.

Key concepts

requirementsuser storyacceptance criteria

Example

criteria = ["valid user can reset password", "expired token is rejected", "token can be used once"]
print("ready to implement:", all(bool(x.strip()) for x in criteria))
Common mistake: Writing “build password reset” as the whole requirement leaves security, expiry, error behavior, and completion criteria undefined.
03Functional vs non-functional requirements

What you will learn

  • Separate what a system does from the qualities it must maintain.
  • Explain how functional requirements changes the behavior, result, or engineering decision in a concrete example
  • Connect functional requirements with latency and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Functional requirements describe behavior such as creating an order or searching a catalog. Non-functional requirements describe qualities and constraints such as latency, availability, privacy, capacity, auditability, and accessibility.

Key concepts

functional requirementslatencyreliabilitysecurity

Example

requirements = {"function":"search products","p95_ms":250,"availability":0.999,"max_results":50}
print(requirements)
Common mistake: Treating “fast” or “reliable” as vague wishes instead of measurable constraints makes design decisions impossible to evaluate.
04Design docs, ADRs & practical UML

What you will learn

  • Write a concise design decision with context, alternatives, and consequences.
  • Choose the lightest diagram that answers the team’s actual design question.
  • Use class, sequence, component, activity, and state diagrams to communicate structure, interactions, workflows, and lifecycle behavior.

Explanation

Start from the question the diagram needs to answer. Use a class diagram for structure, a sequence diagram for interactions over time, a component diagram for major system parts, an activity diagram for workflow, and a state diagram for an object's states and transitions. Keep only the detail needed to explain the design.

Key concepts

design documentADRtrade-offdecision recordUMLClass diagramSequence diagramComponent diagramActivity diagramState diagram

Example

sequence = [("Customer", "Web", "Place order"), ("Web", "Checkout API", "POST /orders"), ("Checkout API", "Payment", "Authorize"), ("Checkout API", "Database", "Save order")]
states = {"Pending": ["Paid", "Cancelled"], "Paid": ["Shipped", "Refunded"], "Shipped": ["Delivered"]}
print("Request interactions:")
for sender, receiver, message in sequence: print(sender, "->", receiver + ":", message)
print("Valid order transitions:", states)
Common mistake: Treating UML as paperwork or trying to draw every possible detail makes diagrams noisy and stale.
05Repository structure & module boundaries

What you will learn

  • Verify the idea with a normal case and an important edge, failure, or scale case

A repository should make the system easier to navigate. Good boundaries group code by responsibility and keep unstable details behind stable interfaces.

Key concepts

repository structuremodule boundaryseparation of concerns

Example

layers = {"domain":[], "service":[], "adapters":[], "tests":[]}
for name in layers: print(name)
Common mistake: Creating many tiny folders without a meaningful dependency boundary adds ceremony without reducing coupling.
06Dependencies, environments & reproducible setup

What you will learn

  • Make a project installable and reproducible on another machine.
  • Explain how dependency management changes the behavior, result, or engineering decision in a concrete example
  • Connect dependency management with lockfile and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Dependencies are part of the program. A professional project records supported runtime versions, direct dependencies, locked versions where appropriate, configuration expectations, and setup commands.

Key concepts

dependency managementlockfileenvironmentreproducibility

Example

requirements = {"python":"3.12", "fastapi":"0.115", "pytest":"8.x"}
print("documented runtime:", requirements["python"])
Common mistake: “It works on my machine” is often a dependency or configuration specification failure, not a mysterious platform problem.
07Coding standards, formatting & static analysis

What you will learn

  • Use automated checks to enforce cheap, repeatable quality rules.
  • Explain how style guide changes the behavior, result, or engineering decision in a concrete example
  • Connect style guide with formatter and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Formatting, linting, type checking, and static analysis catch different classes of problems. Automating these checks removes low-value style debates from review and finds issues before runtime.

Key concepts

style guideformatterlinterstatic analysis

Example

checks = ["format", "lint", "type-check", "unit-tests"]
print("pre-review checks:", " -> ".join(checks))
Common mistake: Adding a tool with hundreds of warnings and no agreed policy often trains the team to ignore the tool entirely.
08Git workflow: branches, commits & change size

What you will learn

  • Structure changes so history and review remain understandable.
  • Explain how branching changes the behavior, result, or engineering decision in a concrete example
  • Connect branching with atomic commit and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Professional Git usage is about change management. A branch isolates work, an atomic commit captures one coherent change, and a small pull request reduces review risk.

Key concepts

branchingatomic commitsmall changes

Example

commits = ["add idempotency validation", "test duplicate retry", "document API behavior"]
for c in commits: print("commit:", c)
Common mistake: A giant commit that mixes a feature, formatting, dependency upgrades, and unrelated refactors is difficult to review and dangerous to revert.
09Pull requests & effective code review

What you will learn

  • Review correctness, design, tests, risks, and maintainability rather than only syntax.
  • Explain how pull request changes the behavior, result, or engineering decision in a concrete example
  • Connect pull request with code review and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Code review is a technical risk-control and knowledge-sharing process. The author should make the change easy to understand with a focused description, testing evidence, and notes about risky decisions.

Key concepts

pull requestcode reviewreview checklist

Example

review = {"correctness":True,"tests":True,"security":"checked","rollback":"documented"}
print("merge ready:", all(v is True or isinstance(v,str) for v in review.values()))
Common mistake: Reviewing only naming and formatting can miss a logically wrong or operationally unsafe change that looks clean.
10Refactoring & technical debt

What you will learn

  • Improve structure without silently changing required behavior.
  • Explain how refactoring changes the behavior, result, or engineering decision in a concrete example
  • Connect refactoring with technical debt and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Refactoring changes internal design while preserving externally required behavior. Safe refactoring starts with tests or another behavior oracle, makes small transformations, and checks after each step.

Key concepts

refactoringtechnical debtbehavior preservation

Example

def price_with_tax(price, rate):
    return price * (1 + rate)
assert round(price_with_tax(100, .05),2) == 105.00
print("behavior protected before refactor")
Common mistake: Rewriting a module from scratch and calling it refactoring removes the small-step safety that makes refactoring low risk.
11Interface contracts & backward compatibility

What you will learn

  • Change an interface without unexpectedly breaking its consumers.
  • Explain how API contract changes the behavior, result, or engineering decision in a concrete example
  • Connect API contract with schema and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An interface contract includes inputs, outputs, errors, side effects, ordering, and compatibility expectations. Once other code or users depend on that contract, changing it becomes a coordination problem.

Key concepts

API contractschemabackward compatibilitydeprecation

Example

old = {"id":7,"name":"Ada"}
new = {**old,"display_name":"Ada Lovelace"}
print("old client still sees:", new["name"])
Common mistake: Renaming or removing a response field because “the new name is better” can break every consumer that still expects the old contract.
12Test strategy & quality gates

What you will learn

  • Choose tests based on risk and place them at the right layer.
  • Explain how test strategy changes the behavior, result, or engineering decision in a concrete example
  • Connect test strategy with quality gate and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A test strategy connects risks to evidence. Unit tests give fast feedback on isolated logic, integration tests verify boundaries such as databases and APIs, and end-to-end tests cover a few critical user journeys.

Key concepts

test strategyquality gaterisk-based testing

Example

risk = {"payment":"end-to-end + integration", "discount_math":"unit", "schema":"contract"}
for area,test in risk.items(): print(area, "=>", test)
Common mistake: Chasing 100% coverage can produce many low-value tests while important integration or failure behavior remains unverified.
13Debugging with evidence & observability

What you will learn

  • Debug from evidence using hypotheses instead of random changes.
  • Explain how debugging changes the behavior, result, or engineering decision in a concrete example
  • Connect debugging with logs and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Effective debugging is a scientific loop: reproduce, gather evidence, form a hypothesis, run the smallest experiment that can disprove it, and narrow the search. Logs explain discrete events, metrics show trends and rates, and traces connect work across boundaries.

Key concepts

debugginglogsmetricstracehypothesis

Example

events = [{"request":"r1","step":"validate"},{"request":"r1","step":"db-timeout"}]
print([e["step"] for e in events if e["request"]=="r1"])
Common mistake: Changing several things at once may make the symptom disappear while teaching you nothing about the actual cause.
14Performance profiling & load testing

What you will learn

  • Measure before optimizing and distinguish latency, throughput, and resource bottlenecks.
  • Explain how profiling changes the behavior, result, or engineering decision in a concrete example
  • Connect profiling with benchmark and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Performance work starts with a target and measurement. Profiling identifies where time or memory is actually spent; microbenchmarks compare small operations; load tests reveal behavior under concurrency and sustained traffic.

Key concepts

profilingbenchmarkload testbottleneck

Example

latencies=[80,90,95,110,400]
latencies.sort()
print("max sample latency:",latencies[-1],"ms")
Common mistake: Optimizing the prettiest-looking loop without a profile can leave the real bottleneck—often I/O, database work, or contention—untouched.
15Security & privacy in everyday engineering

What you will learn

  • Include basic security and privacy checks in ordinary feature work.
  • Explain how input validation changes the behavior, result, or engineering decision in a concrete example
  • Connect input validation with least privilege and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Security is a property of normal engineering decisions: validating untrusted input, authenticating identities, authorizing actions, limiting permissions, protecting secrets, and minimizing sensitive data. Engineers should ask what the trust boundary is, what an attacker or accidental misuse could do, and what evidence will be recorded.

Key concepts

input validationleast privilegesecretsprivacy

Example

allowed={"read:profile"}
requested="delete:user"
print("allowed?", requested in allowed)
Common mistake: Checking that a user is logged in is not the same as checking that the user is authorized to perform a specific action.
16Semantic versioning, changelogs & releases

What you will learn

  • Communicate the scope and compatibility of a release.
  • Explain how semantic versioning changes the behavior, result, or engineering decision in a concrete example
  • Connect semantic versioning with changelog and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Version numbers and release notes are coordination tools. Semantic versioning expresses whether a public interface change is compatible, while a changelog explains what actually matters to users and operators.

Key concepts

semantic versioningchangelogrelease notes

Example

release={"version":"2.1.0","change":"add optional export endpoint","breaking":False}
print(release)
Common mistake: Incrementing versions mechanically without documenting behavior changes gives downstream users no useful migration signal.
17Documentation, runbooks & onboarding

What you will learn

  • Write documentation that helps someone perform a real task without tribal knowledge.
  • Explain how README changes the behavior, result, or engineering decision in a concrete example
  • Connect README with runbook and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Useful documentation is task-oriented. A README should explain purpose, setup, common commands, architecture entry points, tests, and contribution workflow.

Key concepts

READMErunbookonboardingoperational documentation

Example

readme_sections=["Purpose","Setup","Run","Test","Architecture","Troubleshooting"]
print("README checklist:", ", ".join(readme_sections))
Common mistake: A README that only says the project name and how to install dependencies does not help a new engineer understand or operate the system.
18Agile slicing, estimation & team collaboration

What you will learn

  • Break large work into small deliverable slices and communicate uncertainty.
  • Explain how vertical slice changes the behavior, result, or engineering decision in a concrete example
  • Connect vertical slice with estimation and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Agile engineering is about short feedback cycles, not performing ceremonies. A vertical slice delivers a thin piece of end-to-end value that can be reviewed or tested.

Key concepts

vertical sliceestimationiterationteam communication

Example

epic=["read-only endpoint","validation","write path","audit log"]
for slice_ in epic: print("deliverable slice:",slice_)
Common mistake: Splitting work by technical layer—“do all database work, then all backend work, then all UI”—can delay usable feedback until the end.
19Incidents, postmortems & continuous improvement

What you will learn

  • Respond to failures and turn them into specific system improvements.
  • Explain how incident response changes the behavior, result, or engineering decision in a concrete example
  • Connect incident response with postmortem and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Incident response prioritizes user impact: detect, contain, communicate, recover, and then learn. A good postmortem reconstructs the timeline, contributing factors, detection gaps, and why safeguards did not catch the issue.

Key concepts

incident responsepostmortemroot causeaction item

Example

postmortem={"impact":"12 min outage","contributing":["missing timeout","no canary"],"actions":["add timeout","canary deploy"]}
print(postmortem["actions"])
Common mistake: Writing “engineer deployed bad code” as the root cause ignores the process and system controls that allowed one mistake to become an outage.
20End-to-end delivery capstone workflow

What you will learn

  • Combine requirements, design, implementation, review, release, and operations into one coherent workflow.
  • Explain how delivery changes the behavior, result, or engineering decision in a concrete example
  • Connect delivery with traceability and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Near-mastery means integrating the practices rather than memorizing them separately. For a real change, you should be able to show the requirement, acceptance criteria, design decision, implementation, automated evidence, review reasoning, release plan, production signals, and follow-up.

Key concepts

deliverytraceabilityengineering judgment

Example

artifacts=["issue","design","branch","tests","PR","release","dashboard","post-release note"]
print(" -> ".join(artifacts))
Common mistake: Treating process artifacts as unrelated paperwork creates duplication; each artifact should answer a different engineering question and connect to the next stage.
