01Why AI workloads stop fitting on one device

What you will learn

  • Diagnose whether a workload is limited by model memory, activations, compute, data, or communication.
  • Explain how scaling bottleneck changes the behavior, result, or engineering decision in a concrete example
  • Connect scaling bottleneck with memory and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Large-scale AI starts with resource accounting. Model parameters, optimizer states, gradients, activations, KV cache, input batches, and temporary buffers all consume memory; training also requires much more compute and communication than inference.

Key concepts

scaling bottleneckmemorycomputecommunication

Example

gb={"parameters":28,"optimizer":56,"gradients":28,"activations":20}
print("estimated training memory",sum(gb.values()),"GB")
Common mistake: Adding more GPUs without identifying the bottleneck can increase communication overhead while leaving data loading or a serial stage unchanged.
02GPU topology, memory hierarchy & bandwidth

What you will learn

  • Explain why device placement and interconnect topology affect scaling performance.
  • Explain how GPU memory changes the behavior, result, or engineering decision in a concrete example
  • Connect GPU memory with PCIe and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Accelerators have fast local memory and arithmetic, but data movement through HBM, PCIe, NVLink, NICs, and host memory has different bandwidth and latency. Multi-GPU performance depends on which devices communicate and how they are connected.

Key concepts

GPU memoryPCIeNVLinkbandwidthtopology

Example

links={"HBM":"very high","NVLink":"high","PCIe":"lower","network":"cluster dependent"}
for k,v in links.items(): print(k,v)
Common mistake: Assuming every pair of GPUs communicates at the same speed can produce severe imbalance on multi-socket or multi-node systems.
03Data parallelism & PyTorch DDP

What you will learn

  • Scale training by replicating the model and splitting each global batch across workers.
  • Explain how data parallelism changes the behavior, result, or engineering decision in a concrete example
  • Connect data parallelism with DDP and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Data parallelism gives each worker a model replica, processes different samples, and synchronizes gradients before the optimizer step. PyTorch DistributedDataParallel overlaps gradient all-reduce with backpropagation and is the standard baseline for multi-GPU training when the model fits on each device.

Key concepts

data parallelismDDPgradient synchronization

Example

world_size=8; per_gpu=4; accumulation=2
print("global batch",world_size*per_gpu*accumulation)
Common mistake: Increasing world size while accidentally increasing global batch size can change optimization behavior, so a speed comparison may no longer be apples-to-apples.
04Collective communication & synchronization

What you will learn

  • Understand the communication primitives behind distributed training.
  • Explain how all-reduce changes the behavior, result, or engineering decision in a concrete example
  • Connect all-reduce with all-gather and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Distributed training composes a few collective operations. All-reduce combines values such as gradients across workers; all-gather collects sharded tensors; reduce-scatter combines and redistributes pieces.

Key concepts

all-reduceall-gatherreduce-scatterNCCL

Example

workers=[[1,2],[3,4],[5,6]]
summed=[sum(x) for x in zip(*workers)]
print("all-reduce conceptual sum",summed)
Common mistake: Adding frequent synchronization inside small operations can make communication latency dominate even when total data volume is not large.
05FSDP / ZeRO-style parameter sharding

What you will learn

  • Train models that do not fit as full replicas on every GPU.
  • Explain how FSDP changes the behavior, result, or engineering decision in a concrete example
  • Connect FSDP with ZeRO and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Fully sharded approaches partition model parameters, gradients, and/or optimizer states across workers instead of storing complete copies everywhere. Parameters can be gathered just in time for computation and released or reshared afterward.

Key concepts

FSDPZeROparameter shardingoptimizer sharding

Example

model_gb=80; workers=8
print("idealized parameter shard",model_gb/workers,"GB per worker before overhead")
Common mistake: Assuming memory divides perfectly by world size ignores activations, temporary all-gathers, fragmentation, buffers, and uneven module sizes.
06Tensor parallelism

What you will learn

  • Split the computation of large layers across devices.
  • Explain how tensor parallelism changes the behavior, result, or engineering decision in a concrete example
  • Connect tensor parallelism with sharded matmul and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Tensor parallelism partitions weight matrices or attention/MLP dimensions so several GPUs cooperate on one layer. Each device computes a shard and exchanges partial results through collectives.

Key concepts

tensor parallelismsharded matmulmodel parallelism

Example

hidden=8192; tp=8
print("hidden features per idealized shard",hidden//tp)
Common mistake: Using tensor parallelism across slow network boundaries can spend more time exchanging partial activations than performing matrix multiplications.
07Pipeline parallelism & microbatches

What you will learn

  • Split model layers into stages and keep them busy with microbatches.
  • Explain how pipeline parallelism changes the behavior, result, or engineering decision in a concrete example
  • Connect pipeline parallelism with microbatch and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Pipeline parallelism places different layer ranges on different devices. Microbatches flow through stages like an assembly line so several batches can be in flight.

Key concepts

pipeline parallelismmicrobatchpipeline bubble

Example

stage_ms=[12,12,25,11]
print("bottleneck stage ms",max(stage_ms))
Common mistake: Splitting layers evenly by count can produce badly imbalanced stages because layers differ in compute and memory cost.
08Sequence/context parallelism for long inputs

What you will learn

  • Partition long-sequence computation and activations across devices.
  • Explain how sequence parallelism changes the behavior, result, or engineering decision in a concrete example
  • Connect sequence parallelism with context parallelism and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Long-context workloads can be activation- and attention-memory heavy even when parameters fit. Sequence/context parallel techniques partition token dimensions or attention computation so multiple devices share the work.

Key concepts

sequence parallelismcontext parallelismlong context

Example

tokens=128000; workers=8
print("tokens per idealized context shard",tokens//workers)
Common mistake: Only sharding parameters does not solve activation and attention-memory growth caused by very long sequences.
09Expert parallelism & mixture-of-experts

What you will learn

  • Understand sparse expert routing and why load balancing becomes a systems problem.
  • Explain how MoE changes the behavior, result, or engineering decision in a concrete example
  • Connect MoE with expert parallelism and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Mixture-of-Experts models activate only a subset of expert networks for each token. Expert parallelism distributes experts across devices and routes token representations to the selected experts.

Key concepts

MoEexpert parallelismroutingload balance

Example

routes=[0,0,1,3,0,2,3,3]
from collections import Counter
print(Counter(routes))
Common mistake: A router that sends too many tokens to a few experts creates hotspots and can waste the theoretical efficiency of sparse computation.
10Mixed precision: FP32, BF16, FP16 & loss scaling

What you will learn

  • Reduce memory and accelerate tensor-core compute without losing numerical stability.
  • Explain how mixed precision changes the behavior, result, or engineering decision in a concrete example
  • Connect mixed precision with BF16 and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Mixed-precision training stores or computes many tensors in lower precision while preserving sensitive operations or master states as needed. BF16 has a wide exponent range and is often easier to train with than FP16; FP16 may require dynamic loss scaling to avoid gradient underflow.

Key concepts

mixed precisionBF16FP16loss scaling

Example

bytes_per_param={"fp32":4,"bf16":2,"fp16":2,"int8":1}
for p,b in bytes_per_param.items(): print(p,b)
Common mistake: A run that is faster but silently diverges or changes model quality is not a successful mixed-precision optimization.
11Gradient accumulation & effective batch size

What you will learn

  • Reach a larger effective batch when a full batch cannot fit in memory.
  • Explain how gradient accumulation changes the behavior, result, or engineering decision in a concrete example
  • Connect gradient accumulation with microbatch and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Gradient accumulation performs several forward/backward microbatches before the optimizer step. It reduces peak activation memory relative to one large batch and can emulate a larger global batch, but it increases step latency and changes how often optimizer schedules advance.

Key concepts

gradient accumulationmicrobatcheffective batch size

Example

micro=2; accumulation=16; dp=8
print("effective batch",micro*accumulation*dp)
Common mistake: Dividing loss incorrectly or stepping the optimizer on every microbatch changes the optimization problem instead of merely accumulating gradients.
12Activation checkpointing / recomputation

What you will learn

  • Trade extra compute for lower activation memory.
  • Explain how activation checkpointing changes the behavior, result, or engineering decision in a concrete example
  • Connect activation checkpointing with recomputation and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Backpropagation normally needs intermediate activations from the forward pass. Activation checkpointing saves selected checkpoints and recomputes missing intermediates during backward, lowering memory usage at the cost of additional compute.

Key concepts

activation checkpointingrecomputationmemory-compute tradeoff

Example

layers=48; checkpoints=8
print("layers per checkpoint region",layers//checkpoints)
Common mistake: Checkpointing every tiny operation may save memory but add so much recomputation and framework overhead that training slows dramatically.
13Distributed data loading & input pipelines

What you will learn

  • Feed accelerators fast enough without duplicating or skipping training data.
  • Explain how data sharding changes the behavior, result, or engineering decision in a concrete example
  • Connect data sharding with sampler and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Every data-parallel worker should process an appropriate shard of the dataset while maintaining the intended randomness and epoch semantics. Input decoding, tokenization, augmentation, storage bandwidth, worker count, prefetching, and host-to-device transfer can all starve GPUs.

Key concepts

data shardingsamplerprefetchinput bottleneck

Example

indices=list(range(20)); rank=2; world=4
print("rank shard",indices[rank::world])
Common mistake: Letting every worker iterate the complete dataset without a distributed sampler duplicates examples and changes the effective training distribution.
14Distributed checkpoints & resuming jobs

What you will learn

  • Save model, optimizer, scheduler, RNG, and data position so a large job can resume correctly.
  • Explain how checkpoint changes the behavior, result, or engineering decision in a concrete example
  • Connect checkpoint with state dict and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A useful training checkpoint includes enough state to continue the same optimization process: model parameters, optimizer state, scheduler/scaler, random-number state, global step, and often data-loader progress. Sharded training may use distributed checkpoint formats to avoid gathering the full model on one host.

Key concepts

checkpointstate dictdistributed checkpointresume

Example

checkpoint={"step":12000,"model":"sharded","optimizer":"sharded","rng":"saved"}
print(checkpoint)
Common mistake: Saving only model weights allows inference but does not reproduce a true training resume because optimizer and scheduler state are missing.
15Fault tolerance, preemption & elastic recovery

What you will learn

  • Design long-running training jobs to survive expected infrastructure failures.
  • Explain how fault tolerance changes the behavior, result, or engineering decision in a concrete example
  • Connect fault tolerance with preemption and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Large distributed jobs have a larger failure surface: any worker, node, storage path, or network link can fail. Periodic checkpoints, idempotent launch scripts, retry policies, health monitoring, and preemption-aware scheduling reduce lost work.

Key concepts

fault tolerancepreemptionelastic trainingrestart

Example

hours_per_ckpt=1; job_hours=200
print("maximum compute lost after one failure about",hours_per_ckpt,"hour")
Common mistake: Checkpointing only once a day on an expensive preemptible cluster can turn an ordinary node failure into many hours of lost compute.
16Profiling distributed training & utilization

What you will learn

  • Measure where distributed time is spent and optimize the dominant bottleneck.
  • Explain how profiling changes the behavior, result, or engineering decision in a concrete example
  • Connect profiling with MFU and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Distributed profiling separates useful accelerator compute from input wait, communication, synchronization, kernel launch overhead, memory stalls, and idle pipeline time. GPU utilization alone can be misleading because a device may be busy with inefficient operations.

Key concepts

profilingMFUutilizationcommunication overlap

Example

single=100; eight_gpu=610
print("speedup",eight_gpu/single,"efficiency",(eight_gpu/single)/8)
Common mistake: Calling an 8-GPU run “8× scaled” without comparing throughput against the single-GPU baseline hides poor scaling efficiency.
17Inference memory: weights, activations & serving state

What you will learn

  • Account for model weights, temporary activations, runtime buffers, and concurrent requests.
  • Explain how inference memory changes the behavior, result, or engineering decision in a concrete example
  • Connect inference memory with serving and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Inference removes optimizer and training-gradient memory, but serving adds concurrency and request-specific state. Weight precision determines static model memory; activations and workspace depend on batch and sequence shapes; autoregressive LLMs add KV cache that grows with active tokens.

Key concepts

inference memoryservingmemory budget

Example

budget={"weights":28,"kv_cache":18,"workspace":6,"headroom":8}
print("serving memory budget",sum(budget.values()),"GB")
Common mistake: Testing only one short prompt at a time does not prove the model will fit under concurrent long-context production traffic.
18KV cache & long-context serving

What you will learn

  • Explain how KV caching speeds autoregressive generation and why it consumes serving memory.
  • Explain how KV cache changes the behavior, result, or engineering decision in a concrete example
  • Connect KV cache with attention and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Autoregressive transformers reuse keys and values from previous tokens instead of recomputing the full prefix at every generation step. The KV cache makes decoding much faster but grows with active sequence length, layer count, head dimensions, batch/concurrency, and cache precision.

Key concepts

KV cacheattentioncontext lengthmemory pressure

Example

requests={"short":1000,"long":64000}
print("long context is",requests["long"]//requests["short"],"x tokens")
Common mistake: Sizing a server by weight memory alone can leave no room for KV cache once several long requests become active.
19Batching & continuous batching

What you will learn

  • Increase accelerator utilization while controlling per-request latency.
  • Explain how batching changes the behavior, result, or engineering decision in a concrete example
  • Connect batching with continuous batching and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Static batching waits to form a group of requests and processes them together, improving throughput but potentially increasing queue delay. Autoregressive requests finish at different times, so continuous batching admits new work as slots become available instead of waiting for the whole batch to finish.

Key concepts

batchingcontinuous batchingthroughputlatency

Example

arrival_ms=[0,4,8,30]; batch_window=10
first_batch=[t for t in arrival_ms if t<=batch_window]
print(first_batch)
Common mistake: Maximizing batch size without a latency SLO can improve tokens/sec while making individual users wait unacceptably long.
20Quantization, sharding & speculative decoding

What you will learn

  • Compare complementary methods for reducing memory or decoding cost.
  • Explain how quantization changes the behavior, result, or engineering decision in a concrete example
  • Connect quantization with inference sharding and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Quantization stores or computes weights/activations with fewer bits to reduce memory bandwidth and capacity requirements, with possible quality or kernel trade-offs. Inference sharding distributes a model that is too large or latency-sensitive for one device.

Key concepts

quantizationinference shardingspeculative decoding

Example

params_b=70
for bits in [16,8,4]: print(bits,"bit ideal weight GB",params_b*bits/8)
Common mistake: Choosing 4-bit quantization solely from memory savings without evaluating task quality and runtime kernel support can produce a slower or less accurate deployment.
21Inference runtimes: vLLM, TensorRT-LLM & serving engines

What you will learn

  • Understand what specialized runtimes optimize beyond a plain model.forward loop.
  • Explain how inference runtime changes the behavior, result, or engineering decision in a concrete example
  • Connect inference runtime with vLLM and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Production inference engines coordinate memory management, optimized kernels, batching/scheduling, model parallelism, quantization, cache handling, and request APIs. Engines such as vLLM and TensorRT-LLM make different hardware and deployment trade-offs, so benchmarking on the target model and request distribution is more useful than choosing by reputation.

Key concepts

inference runtimevLLMTensorRT-LLMkernel optimization

Example

engines={"baseline":"framework eager","engine_A":"paged cache + continuous batching","engine_B":"compiled optimized kernels"}
print(engines)
Common mistake: Comparing runtimes with different batch sizes, precision, context lengths, or output-token limits can create misleading benchmark conclusions.
22Serving topology, autoscaling & inference benchmarking

What you will learn

  • Design and measure an inference service under realistic traffic.
  • Explain how autoscaling changes the behavior, result, or engineering decision in a concrete example
  • Connect autoscaling with SLO and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A production topology includes routing, replicas, model workers, queues, health checks, autoscaling signals, observability, and failure handling. Benchmark both prefill and decode behavior across realistic prompt/output lengths and concurrency.

Key concepts

autoscalingSLOthroughputlatencybenchmark

Example

report={"p50_ms":180,"p95_ms":520,"tokens_per_s":9200,"error_rate":0.001,"concurrency":64}
print(report)
Common mistake: A single-request latency benchmark cannot predict throughput, queueing, or memory behavior under real concurrent traffic.
