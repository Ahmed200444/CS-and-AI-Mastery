Explanation

Prompting alone fits when the model's existing knowledge and reasoning are sufficient and no current or proprietary facts are needed. RAG fits when the task needs current or proprietary information the model wasn't trained on, without needing to change the model's underlying behavior.

Key concepts

approach selection criteriaRAG vs. fine-tuningwhen traditional ML beats an LLM

Example

# decision criteria, not a preference ranking:

Model selection isn't simply 'pick the most capable model' -- it's matching a model's capability, latency, cost, and context window to the SPECIFIC task's actual requirements. A simple classification or extraction task rarely needs the most expensive, highest-capability model available; a complex, ambiguous reasoning task might need it.

Key concepts

model selectioncapability vs. cost/latency trade-offmixing models by sub-task

Common mistake: Defaulting to the single most capable (and most expensive) available model for every part of a system -- matching model choice to each sub-task's actual difficulty is a genuine cost and latency optimization most teams underuse.

14Scaling AI workloads

What you will learn

  • Explain the batching and queueing economics specific to expensive AI inference, distinct from general System Design scaling
  • Explain how batching economics changes the behavior, result, or engineering decision in a concrete example
  • Connect batching economics with queueing under load and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

General System Design's scaling lessons (load balancing, auto-scaling) apply, but AI inference has its own specific economics: requests are often batched together before being sent to a model (since batched inference is typically more cost-efficient per-request), but batching means waiting for a batch to fill, adding latency.

Key concepts

batching economicsqueueing under loadload shedding for AI workloads

Example

# the SPECIFIC trade-off AI inference scaling introduces, beyond general scaling:
# larger batch size: more cost-efficient per request, but each request waits
# longer for its batch to fill before being processed at all
# when demand exceeds current capacity: add instances (cost), accept a growing
# queue (latency), or shed load (some requests explicitly degraded/rejected) --
# an explicit choice, not something to discover only when it happens live
Common mistake: Assuming general auto-scaling (adding instances when load increases) is sufficient without considering batching's latency trade-off specifically -- AI inference's batching economics add a dimension general web-service scaling doesn't have to account for.

genuinely conflicting factors -- high data sensitivity pushes toward self-hosted, but no MLOps team makes self-hosting operationally risky; a reasonable answer might be a hosted provider with strong data-processing agreements, or investing in MLOps capability first

Design a caching strategy for a repeated FAQ query

Design a caching strategy for a RAG-backed FAQ bot, addressing both staleness and personalization risk.

Hint

key the cache on the query plus a document-version identifier (invalidating when source docs change) and ensure the cache key includes anything that made the response user-specific, or don't cache personalized responses at all

Diagnose a token-budget overflow

A chat system silently truncates the user's most recent message when conversation history is long, causing confusing responses. What's the design flaw, and the fix?

Hint

the truncation strategy isn't protecting the user's current query; fix by explicitly reserving budget for the system prompt and current query first, truncating conversation history (or summarizing it) before ever touching the current message

Design a fallback chain for a provider outage

Design a fallback chain for a production feature when the primary AI provider is unavailable.

Hint

e.g. retry with backoff, then fail over to a secondary provider if configured, then serve a cached or simpler deterministic response, then explicitly inform the user the feature is temporarily degraded -- never silently fail with no response

Choose sync or async: a report-generation agent

Hint

asynchronous -- a 2-minute synchronous wait is a poor user experience; accept the request, notify the user when the report is ready

Choose sync or async: a live chat response

Hint

synchronous -- the user is actively waiting for this specific response before continuing the conversation

Design a human-in-the-loop checkpoint
