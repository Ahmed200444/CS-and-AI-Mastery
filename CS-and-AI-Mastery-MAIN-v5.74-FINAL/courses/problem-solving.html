01The method

What you will learn

  • Apply a repeatable method: restate, example, brute force, then optimize
  • Explain how decomposition changes the behavior, result, or engineering decision in a concrete example
  • Connect decomposition with pattern recognition and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Strong problem-solvers don't code first. They: (1) restate the problem, (2) work a tiny example by hand, (3) find the pattern/tool, (4) write brute force, (5) optimize, (6) explain the trade-offs.

Key concepts

decompositionpattern recognitionbrute-force-firsttrade-offs

Example

Restate → example → pattern → brute force → optimize → explain
Common mistake: Jumping straight to code before restating the problem or working a small example by hand, risking solving the wrong problem.
02Understanding the problem first

What you will learn

  • Explain how restat changes the behavior, result, or engineering decision in a concrete example
  • Connect restat with clarifying questions and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Restating a problem in your own words surfaces misunderstandings early, before any code is written to fix the wrong problem. Ambiguous problems often have several valid interpretations -- asking clarifying questions before diving in avoids solving the wrong one.

Key concepts

restatclarifying questionsdefine doneambiguousfirst stepunderstand the problemrisk of writing codedefine

Example

# before writing any code:
# 1. restate the problem in your own words
# 2. ask: what's the input range? what should happen on empty input?
# 3. define done: 'this function returns X for input Y, handling Z edge case'
Common mistake: Jumping straight to code before confirming you understand what's actually being asked -- this can waste significant effort solving the wrong problem.

  • Connect small example with brute force and predict what changes when one assumption changes

Explanation

Working through a small example by hand helps you discover the actual pattern needed, and gives you a test case to check against.

Key concepts

small examplebrute forcebrute-force solutionbrute force first

Example

# example: 'find the longest streak of a repeated number'
# work a tiny example by hand first: [3,3,3,5,5] -> streak of 3, length 3

04Breaking problems down

What you will learn

  • Split a problem into smaller subproblems, and reduce it to a known pattern
  • Explain how subproblems changes the behavior, result, or engineering decision in a concrete example
  • Connect subproblems with divide and conquer and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Breaking a problem into smaller subproblems makes each piece easier to reason about, implement, and test independently. Divide and conquer is a specific version of this: split into smaller, similar subproblems, solve each, then combine the results.

Key concepts

subproblemsdivide and conquerreduceknownalready know how to solve

Example

# instead of solving 'sort and deduplicate and count' all at once:
# subproblem 1: sort the list
# subproblem 2: remove duplicates from the sorted list
# subproblem 3: count what's left
# each piece is small enough to get right and test on its own
Common mistake: Trying to solve a large, multi-part problem in one single pass instead of splitting it into independently checkable pieces.
05Constraints & complexity

  • Connect constraints with time complexity and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Identifying constraints (input size, time limit, edge cases) before choosing an approach matters because they determine which approaches are even feasible -- an O(n^2) approach might be fine for small inputs but impractical for millions of records.

Key concepts

constraintstime complexitycomparing approachessimplerless efficientright choice

Example

# a solution that's O(n^2) might run instantly on 100 items
# but take minutes or crash on 10 million items --
# always ask: what's the REAL expected input size?
Common mistake: Ignoring stated or implied constraints (input size, time limits) when choosing an approach, only to discover the solution doesn't scale.
06Edge cases & verification

What you will learn

  • Test against edge cases and verify your solution by hand
  • Explain how edge cases changes the behavior, result, or engineering decision in a concrete example
  • Connect edge cases with verify and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An edge case is an input at the boundary of what's expected -- empty, zero, negative, maximum size, duplicates -- easy to overlook but a common source of real bugs. Testing your solution against these edge cases, not just the 'normal' example, catches algorithms that work for typical input but silently fail at boundaries.

Key concepts

edge casesverifyhand-computedboundaryedge caseempty list

Example

# always explicitly test:
# - empty input: []
# - a single element: [5]
# - duplicates: [3,3,3]
# - the largest size you're told to expect
Common mistake: Testing only the 'normal' example from the problem statement and skipping empty/boundary cases entirely.

Explanation

Explaining your reasoning out loud (in an interview or otherwise) makes your thought process visible, which is often what's actually being evaluated, and can surface your own reasoning gaps. Drawing a diagram or table can reveal a problem's structure faster than abstract reasoning alone.

Key concepts

thinking aloudexplaining your reasoningdiagramtrackingstuckstrategy

Example

# habits that compound:
# - narrate your thinking, even the uncertain parts
# - sketch the data structure or flow on paper before coding
# - jot down 'tried X, didn't work because Y' so you don't repeat it
Common mistake: Going completely silent while thinking, especially under observation (like an interview) -- this leaves the listener with no way to help or evaluate your approach.
08After solving: reflection & careful translation

What you will learn

  • Reflect after solving, and translate your idea into code carefully
  • Explain how translating changes the behavior, result, or engineering decision in a concrete example
  • Connect translating with reflection and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A common mistake is rushing the translation of a working idea into code, introducing small implementation bugs (off-by-one, wrong variable) that don't reflect any flaw in the actual idea. After solving, briefly reflecting on what made it hard, and whether a simpler or more general approach existed, compounds your skill over time.

Key concepts

translatingreflectionexplain a solutiongood habitcommon mistake

Example

# after solving:
# - did I translate the idea into code carefully, or rush it?
# - what made this hard? would I recognize this pattern faster next time?
# - could I explain this solution clearly to someone else right now?
Common mistake: Treating a problem as 'done' the instant it passes, without any reflection on whether the approach was accidental or genuinely understood.
09Heuristics & simplifying first

What you will learn

  • Use heuristics and simplified versions to make progress on hard problems
  • Explain how heuristic changes the behavior, result, or engineering decision in a concrete example
  • Connect heuristic with simplest and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A heuristic is a practical rule-of-thumb approach that often works well, even without a guarantee of the best possible result. Starting with the SIMPLEST possible version of a problem, even if the real problem is more complex, often reveals the core structure needed, which you then extend for the full complexity.

Key concepts

heuristicsimplestsimplest possible version

Example

# simplify first: if the real problem is 'find the best route through 50 cities,'
# first solve it for 3 cities by hand -- the core idea often becomes clear at small scale
Common mistake: Attempting the full, complex version of a problem directly instead of starting from a deliberately simplified version to find the core idea first.

Diagnose a wrong approach chosen from ignored constraints

Hint

Diagnose a solution that missed an edge case

Hint

  4. a solution written in assembly language

  1. brute force is always the best final answer
  2. it establishes a correct baseline you can test against and improve incrementally, rather than risking a broken 'clever' solution
  3. it's required by all programming languages
  4. optimized solutions are always wrong

  1. nothing, it just adds complexity
  2. each smaller piece becomes easier to reason about, implement, and test independently
  3. it's only useful for recursive problems
  4. it always makes the code slower

  1. constraints never matter

  3. constraints are only relevant in coding interviews
  4. identifying constraints is the interviewer's job, not yours
What is an edge case?
  1. a case that never actually happens
  2. an input at the boundary of what's expected (empty, zero, negative, maximum size, duplicates) that's easy to overlook
  3. a bug that can't be fixed
  4. a case only relevant to security code
Why explicitly consider edge cases like an empty list or single-element list?
  1. they're rare enough to ignore
  2. many real bugs come specifically from these boundary conditions behaving differently than the 'normal' case
  3. the language handles them automatically in every case
  4. only advanced programmers need to worry about them
What is the benefit of explaining your reasoning out loud while solving a problem (in an interview or otherwise)?
  1. no benefit, it's just noise
  2. it makes your thought process visible, which is often what's actually being evaluated, and can surface your own reasoning gaps
  3. it only helps the listener, not you
  4. it's required by law in technical interviews

  1. questions make you look unprepared
  2. ambiguous problems often have several valid interpretations, and solving the wrong one wastes all the effort spent
  3. clarifying questions are only for beginners
  4. the problem statement is always complete and unambiguous
What does time complexity (e.g. O(n), O(n^2)) describe?
  1. the exact number of seconds a program takes
  2. how the amount of work grows relative to the size of the input, at a high level
  3. the number of lines of code
  4. how much memory a variable uses
Why does time complexity matter even if a solution 'works' on small test cases?
  1. it doesn't matter if tests pass
  2. an approach that's fine for small inputs can become impractically slow as input size grows, which small tests won't reveal
  3. small test cases always represent the worst case
  4. complexity only matters for sorting algorithms
What is a common strategy when you're stuck and don't know where to start?
  1. give up immediately
  2. try a small concrete example, or explicitly restate what you know and don't know yet
  3. guess randomly until something works
  4. always ask for the answer immediately
Why test your solution against the edge cases you identified earlier, not just the 'normal' example?
  1. edge cases are guaranteed to work if the normal case does
  2. many algorithms that work for typical input silently fail exactly at boundaries
  3. testing edge cases is optional busywork
  4. edge cases only matter for security-critical code
What is the value of comparing multiple possible approaches before committing to one?
  1. there's no value, the first idea is usually best
  2. different approaches trade off differently (speed, memory, complexity, readability), and comparing surfaces the right fit for the actual constraints
  3. comparing approaches wastes valuable time always
  4. only experts should compare approaches
Why might a simpler, slightly less efficient solution sometimes be the RIGHT choice over a more complex optimal one?
  1. simpler solutions are never acceptable
  2. readability, maintainability, and lower bug risk can outweigh marginal performance gains, especially if the problem's actual scale doesn't need the optimization
  3. efficiency never matters in real projects
  4. simpler code always runs faster too
What does 'divide and conquer' mean as a problem-solving strategy?
  1. splitting work between two programmers
  2. breaking a problem into smaller, similar subproblems, solving each, then combining the results
  3. avoiding difficult problems entirely
  4. a specific sorting algorithm only
Why keep track of what you've already tried when working through a hard problem?
  1. there's no benefit to tracking attempts
  2. it avoids wasting time re-trying the same failed approach and helps you reason about what's actually different in remaining options
  3. it's only useful for graded assignments
  4. tracking attempts guarantees you'll find the answer faster
What is the risk of writing code before you fully understand the problem?
  1. there's no risk, code can always be adjusted
  2. you may build in the wrong direction, discovering the misunderstanding only after significant wasted effort
  3. code written early is always more efficient
  4. understanding the problem fully is unnecessary if you're a fast typer
Why is verifying your solution's output against a hand-computed expected result valuable, even before running any real tests?
  1. it's not valuable, real tests are always sufficient
  2. it catches your own misunderstanding of the problem or a logic error early, before investing further
  3. hand computation is always wrong
  4. this step is only needed for math-heavy problems
What does it mean to 'reduce a new problem to one you already know how to solve'?
  1. ignoring the new problem entirely
  2. recognizing that the new problem shares structure with a familiar pattern or algorithm, and adapting that known solution
  3. always writing brand new code from scratch
  4. a technique that only works for exam questions
Why is drawing a diagram or table sometimes more useful than jumping straight to code?
  1. diagrams are never useful for programming
  2. visualizing the problem's structure (e.g. a graph, a sequence, states) can reveal the right approach faster than abstract reasoning alone
  3. diagrams are only for non-technical people
  4. code is always faster to write than to think through first
What's a good habit after solving a problem, even successfully?
  1. move on immediately, there's nothing more to learn
  2. briefly reflect on what made it hard and whether a simpler or more general approach existed
  3. delete the solution to save space
  4. never revisit solved problems

  1. it doesn't help, simplifying wastes time
  2. solving a simplified version first often reveals the core structure needed, which you then extend for the full complexity
  3. simplified versions are usually a completely different problem
  4. this only applies to math, not programming
What is a heuristic, in the context of problem-solving?
  1. a guaranteed, provably optimal method
  2. a practical rule-of-thumb approach that often works well, even without a guarantee of the best possible result
  3. a type of programming language
  4. a formal mathematical proof
Why explicitly define what 'done' looks like before starting to solve a problem?
  1. it's unnecessary, you'll know when you're done
  2. without a clear definition of success, it's easy to either stop too early or keep 'improving' indefinitely
  3. defining done is the grader's job only
  4. this only matters for open-ended projects, not exercises

  1. there are no common mistakes at this stage

  4. testing too early
