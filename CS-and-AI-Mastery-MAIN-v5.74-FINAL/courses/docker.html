Explanation

'It works on my machine' happens because your machine has different OS versions, library versions, and config than the server. A container packages your app WITH its exact dependencies into one portable unit that runs identically anywhere Docker is installed.

Key concepts

containervirtual machineportabilityisolation

Example

# Without Docker: 'runs fine locally, breaks in prod'
# because prod has Python 3.9 and your machine has 3.12

# With Docker: the container HAS Python 3.9 baked in,
# identical everywhere
Common mistake: Thinking a container IS a lightweight VM — it isn't; it shares the host kernel, which is exactly why it's fast but also why it isn't as isolated as a real VM.
02Images vs containers

What you will learn

  • Define image and container precisely
  • Explain the relationship between them
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: container registry.

Explanation

An image is a read-only template — your app plus its dependencies, frozen as a set of layered files. A container is a running instance of that image, with its own writable layer on top.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: container registry.

Key concepts

imagecontainerlayerscontainer registry

Example

docker images        # list images (the templates)
docker ps             # list running containers (instances)
docker run python:3.11  # spins up a NEW container from the python:3.11 image
Common mistake: Confusing 'stopping a container' with 'deleting the image' — stopping just pauses the running instance; the image (template) is untouched.
03Basic docker CLI

What you will learn

  • Run, list, stop, and inspect containers from the command line
  • Explain how docker run changes the behavior, result, or engineering decision in a concrete example
  • Connect docker run with docker ps and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A small set of commands covers most day-to-day container use: `docker run` starts a new container from an image, `docker ps` lists running containers, `docker stop` gracefully stops one, and `docker logs` shows its output — essential for debugging.

Key concepts

docker rundocker psdocker logsport mapping

Example

docker run -d --name myapp -p 8000:8000 myimage
docker ps
docker logs myapp
docker stop myapp
Common mistake: Forgetting `-p` (port mapping) and then wondering why the app 'isn't responding' — the container is running, but nothing outside it can reach the port.
04Writing a Dockerfile

What you will learn

  • Write a Dockerfile that builds a working image
  • Explain each common instruction
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: HEALTHCHECK.

Explanation

A Dockerfile is a recipe for building an image: FROM picks a base image, COPY brings in your code, RUN executes setup commands (like installing dependencies) at build time, and CMD specifies what runs when the container starts.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: HEALTHCHECK.

Key concepts

FROMCOPYRUNCMDWORKDIRHEALTHCHECK

Example

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
Common mistake: Copying all your code BEFORE installing dependencies — this busts the build cache on every code change, since Docker rebuilds every layer after the first one that changed.
05Volumes & persisting data

What you will learn

  • Explain why container data is ephemeral by default
  • Use a volume to persist data
  • Explain how volume changes the behavior, result, or engineering decision in a concrete example
  • Connect volume with ephemeral storage and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A container's writable layer disappears when the container is removed — anything your app wrote (a database file, uploaded images) is gone too, unless you use a volume: a directory managed by Docker (or mounted from the host) that survives container restarts and removal.

Key concepts

volumeephemeral storagebind mount

Example

docker run -v mydata:/app/data myimage
# 'mydata' volume persists even if the container is deleted and recreated
Common mistake: Storing a database's data files inside the container with no volume — a routine `docker rm` silently wipes the database.
06Docker Compose for multi-container apps

What you will learn

  • Read and write a docker-compose.yml for a multi-service app
  • Explain how docker-compose.yml changes the behavior, result, or engineering decision in a concrete example
  • Connect docker-compose.yml with services and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Real apps are rarely one container — a web app + a database + a cache is typical. Docker Compose lets you define all of them, plus how they connect, in one YAML file, and bring the whole stack up or down with a single command.

Key concepts

docker-compose.ymlservicesdepends_on

Example

# docker-compose.yml
services:
  web:
    build: .
    ports: ["8000:8000"]
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
Common mistake: Assuming `depends_on` waits for the database to be READY (accepting connections) — it only waits for the container to START, which is not the same thing; apps often need their own retry.
07Multi-Stage Builds & Image Optimization

What you will learn

  • Use multi-stage builds to keep production images small and free of build-time dependencies
  • Explain how multi-stage build changes the behavior, result, or engineering decision in a concrete example
  • Connect multi-stage build with build stage and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A naive Dockerfile often ships the whole build toolchain (compilers, dev dependencies, source maps) inside the final image, even though none of that is needed to actually RUN the app -- this bloats image size and increases attack surface.

Key concepts

multi-stage buildbuild stageCOPY --fromimage optimizationslim base imageattack surface

Example

# Stage 1: build
FROM node:20 AS build
WORKDIR /app
COPY package.json .
RUN npm install
COPY . .
RUN npm run build

# Stage 2: run -- only the compiled output ships, not node_modules or source
FROM node:20-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
CMD ["node", "dist/server.js"]
Common mistake: Shipping the entire build stage (compilers, dev dependencies, source files) in the final image because it's simpler than setting up a second stage -- this can make images several times.
08Container Networking & Environment Configuration

What you will learn

  • Configure containers with environment variables and understand how containers reach each other over Docker's network
  • Explain how environment variable changes the behavior, result, or engineering decision in a concrete example
  • Connect environment variable with env-file and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Environment variables (passed via `docker run -e KEY=value` or an `--env-file`, or the `environment:` section in Compose) let the same image behave differently across environments -- a database URL, an API key, a feature flag -- without baking those values into the image itself, which also keeps secrets out of version control.

Key concepts

environment variableenv-filecontainer networkingbridge networkservice name resolutionlocalhost inside a container

Example

docker run -e DATABASE_URL=postgres://db:5432/app -e DEBUG=false my-app

# in docker-compose.yml, a Flask service reaching a Redis service:
services:
  web:
    build: .
    environment:
      - REDIS_HOST=redis   # service name, NOT localhost
  redis:
    image: redis:7
Common mistake: Using `localhost` to reach another container -- from inside a container, localhost refers to that container itself, not the host machine or a sibling service; use the other service's name on.

Hint
