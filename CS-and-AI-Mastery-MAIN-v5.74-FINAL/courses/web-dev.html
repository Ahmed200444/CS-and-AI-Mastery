01How browsers and servers communicate

What you will learn

  • Trace the full request/response cycle between browser and server
  • Explain how DNS changes the behavior, result, or engineering decision in a concrete example
  • Connect DNS with HTTP request/response and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Typing a URL and hitting enter triggers: DNS resolves the domain to an IP, the browser opens a connection and sends an HTTP request, the server processes it and sends back an HTTP response (usually HTML/JSON/etc), and the browser renders or uses that response.

Key concepts

DNSHTTP request/responseclient-server model

Example

Browser --DNS lookup--> IP address
Browser --HTTP GET /--> Server
Server --HTTP 200 + HTML--> Browser
Browser renders the page
Common mistake: Thinking of 'the frontend' and 'the backend' as unrelated systems rather than two ends of the same conversation.
02Frontend vs backend responsibilities

What you will learn

  • Draw a clear line between what belongs on each side
  • Explain how separation of concerns changes the behavior, result, or engineering decision in a concrete example
  • Connect separation of concerns with client-side vs server-side and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Frontend owns what the user sees and directly interacts with: layout, styling, client-side interactivity, and calling APIs. Backend owns business logic, data storage, security enforcement, and anything that must be trusted (never trust validation that only happens in the browser — the backend must re-check everything).

Key concepts

separation of concernsclient-side vs server-sidetrust boundaryclient-side validation

Example

# Frontend: 'disable the submit button if the email field is empty' (UX nicety)
# Backend: 'reject the request if the email field is empty' (the REAL enforcement)
# Both matter -- but only one can be trusted.
Common mistake: Relying only on frontend validation for anything that matters — a user can bypass your JavaScript entirely and hit your API directly.
03The full-stack request lifecycle

What you will learn

  • Trace a realistic request end to end through a full-stack app
  • Explain how request lifecycle changes the behavior, result, or engineering decision in a concrete example
  • Connect request lifecycle with middleware and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A real request touches many layers in sequence: browser sends a request -> (optionally) a CDN/load balancer -> your backend server -> authentication check -> business logic -> database query -> response assembled -> sent back -> frontend updates the DOM with the result.

Key concepts

request lifecyclemiddlewarefull-stack debugging

Example

Browser -> Load Balancer -> API server -> Auth middleware -> Route handler
  -> Database query -> Response JSON -> Frontend renders it
Common mistake: Debugging 'the app is broken' by guessing instead of tracing which layer actually failed (network tab, server logs, database) first.
04APIs and data flow between frontend and backend

What you will learn

  • Design a simple API contract that frontend and backend both agree on
  • Explain how API contract changes the behavior, result, or engineering decision in a concrete example
  • Connect API contract with JSON shape and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The API is the CONTRACT between frontend and backend: an agreed shape of requests and responses (usually JSON) that lets both sides be built and even changed somewhat independently, as long as the contract holds.

Key concepts

API contractJSON shapefrontend/backend parallelism

Example

// contract both sides agree on:
// GET /api/users/:id -> { id, name, email }
// frontend can build its UI against this shape
// before the backend team even finishes the real implementation
Common mistake: Changing an API's response shape without telling the frontend team — a classic, entirely preventable full-stack breakage.
05Deployment basics for a full-stack app

What you will learn

  • Explain, at a high level, how a full-stack app reaches real users
  • Explain how static hosting changes the behavior, result, or engineering decision in a concrete example
  • Connect static hosting with environment config and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A deployed full-stack app usually has: the frontend built into static files and served from a CDN or static host, the backend running as a containerized service behind a load balancer, and a managed database — all wired together with environment variables (API URLs, secrets) instead of hardcoded values.

Key concepts

static hostingenvironment configfrontend/backend deployment

Example

# frontend: build -> static files -> CDN
# backend: Docker container -> cloud compute service
# both configured via env vars, e.g. API_BASE_URL, DATABASE_URL
Common mistake: Hardcoding a 'localhost' API URL into the frontend build — it works perfectly until deployed, then breaks for every real user.
06Full-stack architecture, end to end

What you will learn

  • Describe a complete, coherent full-stack architecture for a real app
  • Explain how end-to-end architecture changes the behavior, result, or engineering decision in a concrete example
  • Connect end-to-end architecture with independent scaling and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Putting it all together: a frontend (Frontend Development track) talks over HTTP to a backend (Backend Development track), which validates input, enforces auth, and reads/writes a database (Databases track); the whole thing is containerized (Docker) and deployed to the cloud (Cloud Computing) behind a load balancer.

Key concepts

end-to-end architectureindependent scalingfull-stack system design

Example

[Frontend: React/static] --HTTPS--> [Load Balancer] --> [Backend API containers]
                                                              |
                                                        [Database + cache]
Common mistake: Treating frontend and backend as needing to scale together — in real systems they almost always scale independently, since their bottlenecks are completely different.
