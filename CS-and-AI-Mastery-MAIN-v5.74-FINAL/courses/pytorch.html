01Tensors: creation, shapes & operations

What you will learn

  • Create PyTorch tensors and reason about their shapes
  • Explain how tensor changes the behavior, result, or engineering decision in a concrete example
  • Connect tensor with shape and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A PyTorch tensor is like a NumPy array (as covered in the Data Science track) with two extras: it can live on a GPU, and it tracks operations for automatic differentiation. Getting shapes right is the single most common source of PyTorch bugs — most errors are a mismatched dimension somewhere in a chain of operations.

Key concepts

tensorshapedtypematrix multiplication

Example

import torch
x = torch.tensor([[1., 2.], [3., 4.]])
print(x.shape)          # torch.Size([2, 2])
y = x @ x.T              # matrix multiply -- shape must align: (2,2) @ (2,2) -> (2,2)
print(x.dtype)           # torch.float32 -- most model math expects float, not int
Common mistake: Mixing float and integer tensors, or mismatched shapes, and being surprised by a cryptic runtime error — always print `.shape` and `.dtype` when debugging, before anything else.
02Autograd: automatic differentiation

What you will learn

  • Explain how PyTorch computes gradients automatically via autograd
  • Explain how autograd changes the behavior, result, or engineering decision in a concrete example
  • Connect autograd with requires_grad and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Every tensor operation with `requires_grad=True` is recorded in a computation graph; calling `.backward()` on a final scalar (usually the loss) walks this graph backward, computing the gradient of that scalar with respect to every tracked tensor automatically — this IS the backpropagation covered conceptually in the Deep Learning track, made concrete.

Key concepts

autogradrequires_gradcomputation graph.backward()

Example

w = torch.tensor(2.0, requires_grad=True)
y = w ** 2 + 3 * w
y.backward()             # computes dy/dw automatically
print(w.grad)            # 7.0  (since dy/dw = 2w + 3 = 2*2+3 = 7)
Common mistake: Forgetting `optimizer.zero_grad()` between training steps — gradients ACCUMULATE by default in PyTorch, silently corrupting the update direction on the next step.
03Building a model with nn.Module

What you will learn

  • Define a custom model by subclassing nn.Module
  • Explain how nn.Module changes the behavior, result, or engineering decision in a concrete example
  • Connect nn.Module with __init__ vs forward and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A PyTorch model is a Python class inheriting from `nn.Module`: `__init__` defines the layers as attributes, and `forward` defines how data flows through them. This is deliberately just Python — you can use any control flow, print statements, or debugging tools you'd use in normal Python code, unlike more declarative frameworks.

Key concepts

nn.Module__init__ vs forwardlayers as attributes

Example

import torch.nn as nn
class SimpleNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(784, 128)
        self.fc2 = nn.Linear(128, 10)
    def forward(self, x):
        x = torch.relu(self.fc1(x))
        return self.fc2(x)
model = SimpleNet()
Common mistake: Forgetting to call `super().__init__()` in a custom module's `__init__` — PyTorch's internal parameter-tracking machinery silently doesn't work correctly without it.
04Datasets & DataLoaders

What you will learn

  • Wrap real data in a Dataset and load it efficiently with a DataLoader
  • Explain how Dataset changes the behavior, result, or engineering decision in a concrete example
  • Connect Dataset with DataLoader and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A `Dataset` defines how to get one item (`__getitem__`) and how many items exist (`__len__`) — your data can come from anywhere (files, a database, a folder of images). A `DataLoader` wraps a Dataset to handle batching, shuffling, and parallel loading automatically, so your training loop just asks for the next batch without knowing any of these details.

Key concepts

DatasetDataLoaderbatchingshuffling

Example

class MyDataset(torch.utils.data.Dataset):
    def __init__(self, data, labels): self.data, self.labels = data, labels
    def __len__(self): return len(self.data)
    def __getitem__(self, i): return self.data[i], self.labels[i]

loader = torch.utils.data.DataLoader(MyDataset(X, y), batch_size=32, shuffle=True)
for batch_x, batch_y in loader: ...
Common mistake: Loading an entire large dataset into memory in `__init__` instead of loading each item lazily in `__getitem__` — this defeats the purpose of a Dataset for data too large to fit in memory at.

  • Connect training loop with model.train() vs model.eval() and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

This assembles the Deep Learning track's training-loop concept into real, runnable code: for each batch, compute the model's prediction (forward pass), compute the loss, zero old gradients, call `.backward()` to compute new ones, and step the optimizer to update weights.

Key concepts

training loopmodel.train() vs model.eval()torch.no_grad()model.train()model.eval()

Example

for epoch in range(num_epochs):
    model.train()
    for batch_x, batch_y in train_loader:
        optimizer.zero_grad()
        preds = model(batch_x)
        loss = loss_fn(preds, batch_y)
        loss.backward()
        optimizer.step()
    # then: model.eval(), compute validation loss with torch.no_grad()

When a model won't learn, work through a checklist rather than guessing: are shapes actually what you expect at each step (print them)? Is the loss actually decreasing at all, even slightly, on a tiny subset of data (if it can't overfit 10 examples, something is fundamentally broken)?

Key concepts

shape debuggingthe overfit-10-examples testgradient inspection

# the single most useful debugging step: try to overfit a TINY subset (e.g. 10 examples)
# if the model can't drive loss near zero on just 10 examples, the bug is in your code,
# not your model's capacity or the dataset's difficulty
Common mistake: Assuming a bug is due to 'the model needing more data/epochs' before ruling out an actual code bug — the tiny-subset overfit test is a fast, decisive way to separate the two.
07GPU/device management

What you will learn

  • Move models and data to a GPU correctly and avoid device-mismatch errors
  • Explain how device management changes the behavior, result, or engineering decision in a concrete example
  • Connect device management with CPU vs GPU and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

PyTorch tensors and models must be explicitly moved to a device (CPU or GPU) with `.to(device)`, and a model and the data it processes must be on the SAME device, or you'll get an explicit error. Writing device-agnostic code (checking `torch.cuda.is_available()`) lets the same code run correctly whether or not a GPU is present.

Key concepts

device managementCPU vs GPUdevice-agnostic code

Example

device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
model = model.to(device)
for batch_x, batch_y in loader:
    batch_x, batch_y = batch_x.to(device), batch_y.to(device)
    preds = model(batch_x)   # now both model and data are on the same device
Common mistake: Moving the model to a GPU but forgetting to move each batch of data too — this throws an explicit 'expected all tensors on same device' error, one of the most common early PyTorch mistakes.
08Saving, loading & deploying a trained model

What you will learn

  • Save and reload a trained model's weights, and describe the path to deployment
  • Explain how state_dict changes the behavior, result, or engineering decision in a concrete example
  • Connect state_dict with weights vs architecture and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

PyTorch typically saves just the model's learned weights (`state_dict`), not the whole Python object, since code can change between saving and loading — you recreate the model architecture in code, then load the saved weights into it.

Key concepts

state_dictweights vs architecturemodel.eval() before inference

Example

torch.save(model.state_dict(), 'model_weights.pth')

# later, even in a different script/session:
model = SimpleNet()                      # recreate the architecture first
model.load_state_dict(torch.load('model_weights.pth'))
model.eval()                              # ready for inference
Common mistake: Saving the entire model object with `torch.save(model, ...)` instead of just its `state_dict` — this can break if your class definition changes even slightly later, unlike loading weights.
09Common PyTorch pitfalls

What you will learn

  • Recognize frequent, specific PyTorch mistakes
  • Explain how zero_grad changes the behavior, result, or engineering decision in a concrete example
  • Connect zero_grad with gradient accumulation bug and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Forgetting optimizer.zero_grad() before backward() causes gradients to accumulate incorrectly across batches. Forgetting model.eval() during inference leaves dropout/batchnorm in training mode, giving inconsistent results.

Key concepts

zero_gradgradient accumulation bugshape mismatch

Example

for batch in dataloader:
    optimizer.zero_grad()   # forgetting this accumulates gradients across batches -- a real, common bug
    output = model(batch)
    loss = criterion(output, target)
    loss.backward()
    optimizer.step()
Common mistake: Forgetting optimizer.zero_grad() -- gradients silently accumulate across batches instead of being computed fresh each time, corrupting training.
