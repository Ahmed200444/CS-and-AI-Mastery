Key concepts

branchgit checkout -bHEAD

Example

Common mistake: Forgetting which branch you're currently on before making changes -- always check with `git status` or `git branch`, which marks the current branch.
04Merging & conflicts

What you will learn

  • Merge branches and resolve a merge conflict
  • Explain how merge changes the behavior, result, or engineering decision in a concrete example
  • Connect merge with merge conflict and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

git merge combines changes from one branch into another. A merge conflict happens when Git can't automatically reconcile changes to the same lines and needs manual resolution -- you edit the conflicting file, choose the correct content, then commit.

Key concepts

mergemerge conflictfast-forward

Example

git checkout main
git merge feature
# if there's a conflict, Git marks the file --
# edit it, then:
git add resolved_file.txt
git commit
Common mistake: Panicking and discarding all changes when a merge conflict appears -- conflicts are a normal, expected part of merging and are meant to be resolved, not avoided.

06Undoing changes: revert, reset & stash

What you will learn

  • Safely undo a commit, and temporarily shelve changes
  • Explain how git revert changes the behavior, result, or engineering decision in a concrete example
  • Connect git revert with git reset and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

git revert <commit> creates a NEW commit that undoes a previous one -- safe for shared history since nothing is deleted. git reset rewrites history instead, which is risky if that history has already been pushed and shared.

Key concepts

git revertgit resetgit stash

Example

git revert a1b2c3d      # safe: adds an undo commit
git stash                # shelve current uncommitted changes
git stash pop            # restore them later
Common mistake: Using git reset on commits that have already been pushed and shared -- this rewrites history other people's copies still expect, causing confusion.

Explanation

.gitignore lists files and patterns Git should never track (build artifacts, secrets, local config) -- keeping the repository clean. Small, focused commits with clear messages are easier to review, understand later, and revert individually if something goes wrong, compared to one giant commit covering unrelated changes.

Key concepts

.gitignorecommit messagessmall commits

Example

*.log

# good commit message: 'Fix null pointer in checkout flow'
# not: 'stuff' or 'fix'
Common mistake: Committing generated files (build output, dependencies) directly into the repository instead of ignoring them -- this bloats the repo and causes unnecessary merge conflicts.

Explanation

A pull request (or merge request) is a proposal to merge changes from one branch into another, typically reviewed by teammates before merging -- it's the standard way real teams review and discuss code changes before they become part of the main branch.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: branch protection rules, required CI checks.

Key concepts

pull requestbranch protection rulesrequired CI checks

Example

# typical flow:
# 1. git checkout -b my-feature
# 2. make changes, commit, git push origin my-feature
# 3. open a pull request on GitHub comparing my-feature -> main
# 4. teammates review, discuss, request changes if needed
# 5. merge once approved
Common mistake: Pushing directly to a shared main branch without review, on a team that expects pull requests -- this skips the review step meant to catch issues before they land.
10Rebasing & Rewriting History

What you will learn

  • Use rebase to keep a clean, linear history, and know when rebasing a branch is genuinely unsafe
  • Explain how rebase changes the behavior, result, or engineering decision in a concrete example
  • Connect rebase with interactive rebase and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Merging preserves exactly what happened, including a merge commit tying two branches together; rebasing replays your branch's commits on top of another branch's latest state instead, producing a clean, linear history with no merge commit.

Key concepts

rebaseinteractive rebasesquashlinear historyrewriting historyforce-pushgolden rule of rebaseshared branch

Example

# clean up your OWN unpushed commits before opening a PR:
git rebase -i HEAD~3
# lets you squash 'wip', 'fix typo', 'actually fix it' into one clean commit

# update your feature branch on top of main's latest commits:
git fetch origin
git rebase origin/main

# NEVER do this on a branch others have already pulled:
git push --force   # rewrites history that others may depend on -- breaks their repo
Common mistake: Rebasing (and force-pushing) a branch that's already been pushed and pulled by teammates -- this rewrites history they've already built work on top of, and force-pushing then makes their.
