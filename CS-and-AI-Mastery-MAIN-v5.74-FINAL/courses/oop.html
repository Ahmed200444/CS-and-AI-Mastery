02Encapsulation

What you will learn

  • Bundle data and behavior together, and control access to internal state
  • Explain how encapsulation changes the behavior, result, or engineering decision in a concrete example
  • Connect encapsulation with internal state and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Encapsulation means bundling data (attributes) and the methods that operate on it inside one class, while controlling what's exposed to the outside. A leading underscore (_balance) is Python's convention signaling 'internal, don't touch directly,' even though it's not strictly enforced.

Key concepts

encapsulationinternal state_balance convention

Example

class BankAccount:
    def __init__(self, balance):
        self._balance = balance   # convention: internal
    def deposit(self, amount):
        self._balance += amount
    def get_balance(self):
        return self._balance
Common mistake: Exposing internal attributes directly and letting external code modify them freely, bypassing any validation the class's own methods would apply.
03Abstraction

What you will learn

  • Expose only what's necessary, hiding implementation detail
  • Explain how abstraction changes the behavior, result, or engineering decision in a concrete example
  • Connect abstraction with abstract class and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Abstraction means exposing a simple interface while hiding the complex implementation behind it. When you call .sort() on a list, you don't need to know which sorting algorithm runs underneath -- that detail is abstracted away.

Key concepts

abstractionabstract classinterfaceabstractmethod

Example

from abc import ABC, abstractmethod
class Shape(ABC):
    @abstractmethod
    def area(self):
        pass   # subclasses MUST implement this, but this class doesn't say how
Common mistake: Exposing every internal implementation detail through the public interface, forcing users of a class to understand its internals just to use it.

Key concepts

05Composition vs inheritance

What you will learn

  • Choose between 'is-a' inheritance and 'has-a' composition
  • Explain how composition changes the behavior, result, or engineering decision in a concrete example
  • Connect composition with is-a and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Inheritance models an 'is-a' relationship (a Dog IS-A Animal). Composition models a 'has-a' relationship (a Car HAS-A Engine) by holding an instance of another class as an attribute, rather than inheriting from it.

Key concepts

compositionis-ahas-ainheritance vs composition

Example

class Engine:
    def start(self):
        return 'Engine started'

class Car:
    def __init__(self):
        self.engine = Engine()   # HAS-A engine -- composition
    def start(self):
        return self.engine.start()
Common mistake: Reaching for inheritance by default for every kind of code reuse, even when the relationship is really 'has-a' rather than 'is-a.'

Explanation

A design pattern is a reusable, named solution to a recurring design problem. Singleton ensures a class has only one instance globally.

Key concepts

design patternsingletonfactory patternobserver pattern

Example

# Singleton: only one instance ever exists
class Config:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
Common mistake: Forcing a design pattern into code where it doesn't actually fit, just because it's a known pattern -- patterns solve specific problems, they're not universally 'better.'
08Interfaces & abstract classes in practice

What you will learn

  • Use abstract classes to enforce a shared contract across subclasses
  • Explain how abstract class changes the behavior, result, or engineering decision in a concrete example
  • Connect abstract class with contract and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An abstract class defines a contract -- methods every subclass MUST implement -- without providing (or only partially providing) the implementation itself. This lets you write code that works with ANY subclass polymorphically, as long as it fulfills the contract, without needing to know which specific subclass it is at runtime.

Key concepts

abstract classcontractpolymorphic use

Example

class Shape(ABC):
    @abstractmethod
    def area(self): pass

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2

class Square(Shape):
    def __init__(self, s): self.s = s
    def area(self): return self.s ** 2

for shape in [Circle(2), Square(3)]:
    print(shape.area())   # works for ANY Shape subclass
Common mistake: Trying to instantiate an abstract class directly -- it's meant to be subclassed, not used on its own, and most languages enforce this.

Code that works correctly with any `Rectangle` -- setting width and height independently and checking the resulting area -- breaks when passed a `Square`. Which SOLID principle's substitutability guarantee is being violated, and what's the real design fix?

Hint

this violates the Liskov Substitution Principle -- a subclass should be usable anywhere its parent is expected without breaking correctness; the real fix isn't a special case for Square, it's recognizing that Square inheriting from Rectangle was the wrong relationship in the first place, since a Square doesn't actually behave like every Rectangle

Diagnose a broken subclass from a missing super().__init__()

A subclass defines its own `__init__` to add a new attribute, but forgets to call `super().__init__()`. Objects of this subclass are missing attributes the parent class was supposed to set up, causing errors later when parent methods try to use them. What went wrong, and what's the fix?

Hint

overriding __init__ in a subclass completely replaces the parent's __init__ unless you explicitly call super().__init__(...) -- without it, none of the parent class's setup runs, so any attributes or state the parent was responsible for initializing simply don't exist

Refactor a working-but-messy system into clean, SOLID-aligned design

Take a small system that technically works but has real design problems (a class doing too many unrelated things, inheritance used where composition would fit better, hardcoded dependencies that make testing hard) and refactor it applying SOLID principles deliberately -- not just because a checklist says to, but because you can explain what specific problem each change fixes. This capstone is about design judgment under a realistic 'this already works, don't break it' constraint, not designing a clean system from a blank page.
