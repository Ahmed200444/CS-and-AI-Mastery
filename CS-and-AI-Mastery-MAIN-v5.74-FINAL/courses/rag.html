Explanation

RAG solves the LLM's stale/unknown-data problem: split your docs into chunks, embed them into vectors, store them, then for each query retrieve the most similar chunks and feed them to the LLM so its answer is grounded.

Key concepts

query -> embed -> top-k similar -> LLM(query+chunks)
Common mistake: Skipping evaluation of the retrieval step specifically -- a wrong final answer might stem from bad retrieval, not bad generation.

Explanation

Before documents can be searched, they must be ingested (loaded from PDFs, web pages, databases) and chunked — split into smaller pieces, since embedding and retrieving an entire long document as one unit loses precision (you'd retrieve the whole thing even if only one paragraph is relevant).

Key concepts

ingestionchunkingchunk size trade-offdense technical documentslarger chunk sizes

Example

# naive chunking: split every 500 characters, ignoring sentence/paragraph boundaries
# better: split on natural boundaries (paragraphs, sections), with some overlap between
# chunks so a fact split across a boundary isn't completely lost
Common mistake: Chunking purely by a fixed character count with no regard for sentence or paragraph boundaries — this routinely splits a single coherent idea across two chunks, weakening retrieval for.

05Hybrid Search: Combining Dense and Sparse Retrieval

What you will learn

  • Explain why combining dense (embedding-based) and sparse (keyword-based) retrieval catches more relevant results than either alone
  • Explain how hybrid search changes the behavior, result, or engineering decision in a concrete example
  • Connect hybrid search with dense retrieval and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Dense retrieval (embeddings + vector similarity) is good at capturing MEANING -- it can find a relevant passage even if it doesn't share exact wording with the query. But it can miss exact matches that matter, like a specific product ID, error code, or rare technical term, since embeddings represent overall semantic meaning, not precise token identity.

Key concepts

hybrid searchdense retrievalsparse retrievalBM25keyword searchembedding blind spot

Example

# Dense retrieval alone: might miss an exact match for a specific error code
# if the surrounding wording differs a lot from the query's phrasing

# Sparse (BM25) retrieval alone: would nail the exact error code match,
# but might miss a conceptually relevant passage that doesn't use the
# same words as the query

# Hybrid: run both retrievers, combine/rerank their results --
# catches the exact-match case AND the semantic-similarity case
Common mistake: Assuming dense (embedding-based) retrieval alone is always sufficient -- it's genuinely weak at exact matches (IDs, codes, rare terms) precisely because embeddings capture overall meaning.
06Reranking & context construction

What you will learn

  • Explain why an initial retrieval pass is often reranked, and how final context is assembled
  • Explain how reranking changes the behavior, result, or engineering decision in a concrete example
  • Connect reranking with two-stage retrieval and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Initial similarity search (fast, approximate) often returns a broader set of candidate chunks than needed; a reranking step (using a slower but more accurate model) reorders these candidates by true relevance to the specific query, improving precision at the cost of some extra latency.

Key concepts

rerankingtwo-stage retrievalcontext assembly

Example

candidates = vector_search(query, top_k=50)     # fast, broad first pass
reranked = rerank_model(query, candidates)        # slower, more accurate reordering
final_context = format_top_n(reranked, n=5)        # assemble what actually goes in the prompt
Common mistake: Sending all 50 initially-retrieved chunks directly to the LLM without reranking or trimming — this wastes context budget on lower-relevance chunks and can bury the truly relevant ones.
07Grounded generation & citation design

What you will learn

  • Design prompts and system behavior for grounded, citable generation
  • Explain how grounded generation changes the behavior, result, or engineering decision in a concrete example
  • Connect grounded generation with citation attribution and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Grounded generation explicitly instructs the model to answer ONLY using the retrieved context provided (not its general pretrained knowledge), and to say it doesn't know when the retrieved context doesn't contain the answer — directly fighting hallucination.

Key concepts

grounded generationcitation attributionexplicit 'I don't know' instructionI don't know

Example

# grounding instruction: 'Answer ONLY using the provided context below.
# If the context doesn't contain the answer, say you don't know. Cite the source for each claim.'
# -- without this explicit instruction, the model may blend in ungrounded pretrained knowledge
Common mistake: Assuming retrieval alone guarantees grounded answers — without an EXPLICIT instruction to use only the provided context, the model can still blend in unrelated pretrained knowledge alongside.
08Retrieval & generation evaluation

What you will learn

  • Evaluate a RAG system's retrieval quality and final answer quality separately
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: Recall@K, MRR (mean reciprocal rank).
  • Explain how retrieval evaluation changes the behavior, result, or engineering decision in a concrete example
  • Connect retrieval evaluation with generation evaluation and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

RAG systems need TWO separate evaluations: retrieval evaluation (did we find the right chunks? measured with metrics like hit rate or recall against a labeled set of query-to-correct-document pairs) and generation evaluation (given good chunks, did the model produce a good, grounded, accurate answer?).

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: Recall@K, MRR (mean reciprocal rank).

Key concepts

retrieval evaluationgeneration evaluationseparating failure stagesretrieval or generation failureRecall@KMRR (mean reciprocal rank)

Example

# retrieval eval: for 50 labeled test queries, does the retrieved set contain the KNOWN correct document?
# generation eval (given GOOD retrieved chunks): is the final answer accurate, grounded, and well-cited?
# -- always debug these two stages SEPARATELY, not as one combined 'is the answer good' check
Common mistake: Debugging a bad RAG answer by only looking at the final output — always check whether retrieval found the right chunks FIRST, before assuming the problem is in generation.
09Freshness, access control & common failure modes

What you will learn

  • Identify practical operational concerns and common RAG failure patterns
  • Explain how index freshness changes the behavior, result, or engineering decision in a concrete example
  • Connect index freshness with access control enforcement and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Real RAG systems need a plan for freshness (how often is the underlying document index updated as source documents change) and access control (a user should only ever retrieve chunks from documents they're actually permitted to see — a critical, easy-to-miss security requirement, not an afterthought).

Key concepts

index freshnessaccess control enforcementtopically-related-but-not-answering failure

Example

# access control failure (serious): a shared vector index with no permission filtering means
# ANY user's query could retrieve chunks from documents they shouldn't have access to at all
# -- metadata filtering by user/team permissions must be enforced at retrieval time, always
Common mistake: Building a shared vector index without permission-aware filtering baked into every retrieval call — this is a real, serious security gap, not a minor edge case.
10When RAG is (and isn't) the right approach

What you will learn

  • Decide when RAG genuinely solves the problem at hand
  • Explain how when to use RAG changes the behavior, result, or engineering decision in a concrete example
  • Connect when to use RAG with document-dependent answers and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

RAG is well-suited when answers depend on specific, current, or proprietary documents a model wasn't trained on. It's a poor fit when the task needs general reasoning rather than document lookup, or when the true answer isn't actually contained in any retrievable document -- RAG can't invent grounding that doesn't exist in the corpus.

Key concepts

when to use RAGdocument-dependent answerspoor fit for RAGgood indicator that RAG

Example

# good RAG fit: 'What does OUR company's return policy say about X?'
# poor RAG fit: 'Write a creative poem about autumn'
# (nothing to retrieve -- this needs generation, not lookup)
Common mistake: Reaching for RAG by default for every task, even ones that don't actually depend on retrievable documents at all.
