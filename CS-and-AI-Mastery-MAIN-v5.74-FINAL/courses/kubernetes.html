Explanation

Docker packages and runs a single container well, but production systems need many containers across many machines, restarted automatically when they crash, scaled up under load, and rolled out without downtime.

Key concepts

container orchestrationdesired stateself-healingbeyond what Docker provides

Example

# Docker alone: you manually run/restart containers on one machine
# Kubernetes: you declare 'I want 3 replicas of this container running'
# and the cluster continuously enforces that, across many machines,
# restarting failed ones and rescheduling if a machine goes down
Common mistake: Assuming Docker alone is sufficient for production -- Docker runs containers; Kubernetes is what keeps many containers running correctly, at scale, across failures, without manual.
02Kubernetes architecture: control plane & nodes

What you will learn

  • Describe the roles of the control plane and worker nodes
  • Explain how control plane changes the behavior, result, or engineering decision in a concrete example
  • Connect control plane with API server and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A Kubernetes cluster has a control plane (the brain: the API server, which everything talks to; the scheduler, which decides where new workloads run; and etcd, which stores the cluster's actual state) and worker nodes (machines that actually run your containers, each running a kubelet agent that talks to the control plane).

Key concepts

control planeAPI serveretcdschedulerworker nodekubelet

Example

# conceptual flow:
# kubectl apply -f deployment.yaml
# -> API server receives the desired state
# -> scheduler decides which node(s) should run it
# -> kubelet on that node actually starts the container
Common mistake: Trying to manage containers by directly SSHing into nodes -- this bypasses Kubernetes entirely and the control plane will fight you, since it continuously tries to reconcile actual state.

05Deployments & ReplicaSets

What you will learn

  • Explain how a Deployment manages replicas and enables safe rollouts
  • Explain how Deployment changes the behavior, result, or engineering decision in a concrete example
  • Connect Deployment with ReplicaSet and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

You rarely create bare pods directly in production -- a Deployment manages a ReplicaSet, which ensures a specified number of identical pod replicas are running at all times, automatically replacing any that crash or get deleted.

Key concepts

DeploymentReplicaSetreplicasrolling update

Example

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app
        image: my-app:2.0
Common mistake: Manually creating and managing individual pods instead of a Deployment -- you lose automatic replacement on crash, easy scaling, and safe rolling updates, all of which a Deployment gives you.
06Services: stable networking for pods

What you will learn

  • Explain why Services exist and the main Service types
  • Explain how Service changes the behavior, result, or engineering decision in a concrete example
  • Connect Service with ClusterIP and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Pods are ephemeral -- they get replaced constantly, and each replacement gets a new IP address. A Service provides a single, stable IP address and DNS name that automatically routes traffic to whichever healthy pods currently match its label selector, so other parts of your system never need to track individual pod IPs directly.

Key concepts

ServiceClusterIPNodePortLoadBalancerlabel selector

Example

apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
Common mistake: Hardcoding a pod's IP address anywhere in application config -- pod IPs change constantly as pods are replaced; always target a Service's stable address instead.

08Namespaces: organizing a cluster

What you will learn

  • Use namespaces to isolate resources within a shared cluster
  • Explain how namespace changes the behavior, result, or engineering decision in a concrete example
  • Connect namespace with namespace-scoped resources and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A namespace is a way to divide a single cluster into multiple virtual clusters -- useful for separating environments (dev/staging/prod) or teams sharing one physical cluster. Most resources are namespace-scoped (a Service in namespace A can't be found by name alone from namespace B), while some cluster-wide resources (like nodes) are not namespaced at all.

Key concepts

namespacenamespace-scoped resourcescluster-wide resources

Example

kubectl get pods -n staging
kubectl create namespace staging
# a Service 'my-app' in namespace 'staging' is reached at:
# my-app.staging.svc.cluster.local from elsewhere in the cluster
Common mistake: Forgetting to specify -n <namespace> and assuming kubectl commands operate cluster-wide -- most commands default to the 'default' namespace, silently missing resources that live elsewhere.
09Ingress: routing external traffic

What you will learn

  • Explain how Ingress routes external HTTP(S) traffic to services
  • Explain how Ingress changes the behavior, result, or engineering decision in a concrete example
  • Connect Ingress with Ingress Controller and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A LoadBalancer Service works, but provisioning one per application gets expensive and doesn't handle path/host-based routing well.

Key concepts

IngressIngress Controllerhost-based routingpath-based routing

Example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: {name: my-ingress}
spec:
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service: {name: my-app-service, port: {number: 80}}
Common mistake: Provisioning a separate LoadBalancer Service for every single application -- this is expensive and doesn't scale; Ingress lets many applications share one entry point with routing rules.
10Scaling & the Horizontal Pod Autoscaler

What you will learn

  • Explain manual and automatic scaling of pod replicas
  • Explain how horizontal scaling changes the behavior, result, or engineering decision in a concrete example
  • Connect horizontal scaling with Horizontal Pod Autoscaler and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Scaling a Deployment manually (kubectl scale) is simple but requires you to notice load changes yourself.

Key concepts

horizontal scalingHorizontal Pod Autoscalertarget utilizationmin/maxReplicas

Example

kubectl scale deployment my-app --replicas=5

# or, automatically:
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: {kind: Deployment, name: my-app}
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}
Common mistake: Setting no maxReplicas ceiling on an HPA -- an unexpected traffic spike (or a bug causing runaway load) could then scale far beyond what your cluster's actual capacity or budget can handle.

Key concepts

Helmcharttemplated valueshelm install/upgrade/rollback

Example

What problem does Kubernetes solve beyond what Docker provides?

  1. a feature that fixes bugs in your code

  3. a manual process an operator must trigger
  4. a synonym for autoscaling
What is the control plane?
  1. the machines running your application containers
  2. the set of components (API server, scheduler, etcd) that manage the cluster's overall state
  3. a synonym for a single node
  4. a type of Service
What does the Kubernetes API server do?
  1. stores application logs only
  2. acts as the central point every client (kubectl, controllers) talks to in order to read/change cluster state
  3. runs application containers directly
  4. only handles authentication

  3. stores cluster state
  4. handles external HTTP routing
What is the correct way to interact with a Kubernetes cluster?
  1. SSH directly into nodes to manage containers

What is a pod?
  1. a synonym for a container
  2. the smallest deployable unit, which can hold one or more tightly-coupled containers
  3. a type of node
  4. a synonym for a Deployment
Why might a pod hold more than one container?
  1. it's never allowed to
  2. for tightly-coupled containers that must share network/storage, like a sidecar shipping logs
  3. to save on Kubernetes licensing costs
  4. pods can only ever hold exactly one container

  1. deletes all pods

  1. nothing different

  4. the cluster's total node count
What does a Deployment manage?
  1. a single, un-replaceable pod

  3. only Services, not pods
  4. cluster-wide networking
What happens to a pod managed by a Deployment if it crashes?
  1. nothing, it stays crashed until manually restarted

  1. replacing all pods with new ones simultaneously, causing downtime
  2. gradually replacing old pods with new ones, avoiding an all-at-once cutover
  3. a synonym for a rollback
  4. only available in single-replica Deployments
Why do pods need a Service rather than being addressed directly by IP?
  1. pods never get IP addresses
  2. pod IPs change constantly as pods are replaced; a Service provides a stable address that always routes to healthy pods
  3. Services are required by Kubernetes licensing
  4. direct pod IPs are faster

  1. LoadBalancer

  1. nothing external

  1. sensitive passwords only
  2. non-sensitive configuration data, kept separate from the container image
  3. container images

Is data in a Kubernetes Secret encrypted by default?
  1. yes, always fully encrypted
  2. no, only base64-encoded by default, which anyone with read access can decode
  3. Secrets can't store any data

What is a namespace used for?
  1. speeding up the cluster
  2. dividing a single cluster into virtual clusters, useful for separating environments or teams
  3. a synonym for a node
  4. storing container images
What happens if you forget to specify a namespace in a kubectl command?
  1. it operates across the whole cluster automatically

Why does Ingress exist, given LoadBalancer Services already work?
  1. Ingress replaces the need for Services entirely
  2. provisioning a separate LoadBalancer per app is expensive; Ingress lets many apps share one entry point with routing rules
  3. Ingress is required for any cluster to function
  4. Ingress only works for internal traffic
What does an Ingress Controller do?
  1. nothing, Ingress works without one
  2. actually implements the routing rules defined by Ingress resources
  3. replaces the API server
  4. stores cluster secrets
What does the Horizontal Pod Autoscaler (HPA) do?
  1. scales the cluster's node count only
  2. automatically adjusts a Deployment's replica count based on a watched metric like CPU utilization
  3. manually requires an operator to type kubectl scale each time
  4. only works with a fixed number of replicas
Why set a maxReplicas ceiling on an HPA?
  1. it's not necessary
  2. without it, a traffic spike or bug could scale far beyond what the cluster's capacity or budget can handle
  3. maxReplicas is required syntax with no real effect
  4. HPA ignores maxReplicas anyway
What problem does Helm solve?
  1. it replaces kubectl entirely
  2. packaging many coordinated, templated YAML files as one versioned, installable/upgradable unit
  3. it removes the need for a control plane
  4. it only works for single-container apps
What does `helm rollback` do?
  1. deletes the application entirely
  2. reverts an installed chart to a previous revision
  3. installs a brand new chart
  4. only works before the first install
What does `kubectl rollout undo` do?
  1. permanently deletes the Deployment
  2. instantly reverts a Deployment to its previous working revision
  3. only works for Services, not Deployments
  4. requires manually rewriting the YAML file first
What does CrashLoopBackOff typically indicate?
  1. the pod is running perfectly
  2. the container keeps starting and immediately crashing
  3. the cluster has run out of nodes
  4. the image was never found
What does ImagePullBackOff typically indicate?
  1. the container crashed after starting
  2. the specified image doesn't exist or credentials to pull it are missing
  3. the pod is using too much CPU
  4. a networking misconfiguration in the Service
