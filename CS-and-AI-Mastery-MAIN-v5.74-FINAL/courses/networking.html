01How computer networks work

What you will learn

  • Explain what a network is and describe LAN, WAN, and topologies at a practical level
  • Explain how LAN changes the behavior, result, or engineering decision in a concrete example
  • Connect LAN with WAN and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A computer network is simply two or more devices connected so they can exchange data. A LAN (Local Area Network) connects devices in one physical location, like an office or home; a WAN (Wide Area Network) spans a much larger area, connecting multiple LANs together -- the internet is the largest WAN of all.

Key concepts

LANWANintranetinternetnetwork topologystar topology

Example

# practical scale, smallest to largest:
# your home Wi-Fi = a LAN
# your company's offices connected across cities = a WAN
# a company's internal-only network = an intranet
# the whole public internet = the largest WAN, built of countless smaller networks
Common mistake: Assuming 'the internet' and 'a network' are different kinds of things -- the internet IS a network, specifically a massive WAN connecting countless smaller networks together.

Key concepts

modemrouterswitchaccess pointfirewallhub vs switch

03The OSI model & the TCP/IP model

What you will learn

  • Describe both layered models and explain what encapsulation means
  • Explain how OSI model changes the behavior, result, or engineering decision in a concrete example
  • Connect OSI model with TCP/IP model and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The OSI model is a 7-layer conceptual framework for thinking about networking: Physical, Data Link, Network, Transport, Session, Presentation, Application -- from raw electrical signals up to the applications you actually use.

Key concepts

OSI modelTCP/IP modelencapsulationlayered architecture

Example

# encapsulation, simplified (sending an HTTP request):
# Application layer: your HTTP request data
# + Transport layer header (TCP: source/destination port)
# + Internet layer header (IP: source/destination IP address)
# + Link layer header (MAC: source/destination hardware address)
# -- each layer adds its own header before handing off to the layer below
Common mistake: Trying to memorize OSI's 7 layers as if they're all equally used in practice -- real-world networking discussions center on the simpler 4-layer TCP/IP model far more often.
04MAC addresses & IP addresses (IPv4, IPv6, public vs private)

What you will learn

  • Distinguish MAC addresses from IP addresses and identify private vs public IP ranges
  • Explain how MAC address changes the behavior, result, or engineering decision in a concrete example
  • Connect MAC address with IP address and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A MAC address is a hardware address burned into a network interface, used for delivery WITHIN a local network (the Link layer).

Key concepts

MAC addressIP addressIPv4IPv6private IPpublic IP

Example

# MAC address: 3C:22:FB:4A:9B:1E -- identifies THIS specific network card, never changes
# Private IP: 192.168.1.42 -- only meaningful inside your home network
# Public IP: 203.0.113.5 -- how the outside internet actually reaches your network
Common mistake: Assuming a device's IP address is permanent and unique like its MAC address -- private IPs are commonly reused across millions of different home networks, since they're never directly internet-routable.
05Subnetting concepts (without the math)

What you will learn

  • Explain WHY networks are subnetted, conceptually, without doing subnet-mask arithmetic
  • Explain how subnetting changes the behavior, result, or engineering decision in a concrete example
  • Connect subnetting with subnet mask and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Subnetting divides one larger network into smaller, separate sub-networks -- this is a PURPOSE-driven decision, not a math exercise: it isolates traffic (a problem in one subnet doesn't flood the whole network), improves security (different subnets can have different firewall rules), and organizes devices logically (all servers in one subnet.

Key concepts

subnettingsubnet masknetwork segmentation

Example

# conceptual example, no math needed:
# Subnet A (10.0.1.0/24): internal database servers -- no direct internet access
# Subnet B (10.0.2.0/24): public-facing web servers -- internet-accessible, isolated from the databases
# if Subnet B gets compromised, Subnet A isn't automatically exposed
Common mistake: Thinking subnetting is purely an academic exercise in address math -- in real infrastructure, it's a deliberate security and organization decision.
06Ports, sockets, TCP & UDP

What you will learn

  • Explain what a port and socket are, and contrast TCP with UDP
  • Explain how port changes the behavior, result, or engineering decision in a concrete example
  • Connect port with socket and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A port is a number (0-65535) identifying a specific service or application on a device -- port 80 for HTTP, 443 for HTTPS, 22 for SSH. A socket is the combination of an IP address AND a port, uniquely identifying one specific connection endpoint.

Key concepts

portsocketTCPUDPconnection-orientedconnectionless

Example

# socket = IP address + port, e.g. 192.168.1.10:443
# TCP: web browsing, file transfer, email -- correctness matters more than raw speed
# UDP: live video calls, online gaming, DNS lookups -- speed matters more than perfect delivery
Common mistake: Assuming TCP is always the 'better' choice because it's reliable -- for real-time media, UDP's lower latency is usually the RIGHT trade-off, since a slightly-lost frame beats a frozen, buffering stream.
07The TCP handshake, packets, frames & segments

What you will learn

  • Trace the 3-way TCP handshake and distinguish packets, frames, and segments
  • Explain how 3-way handshake changes the behavior, result, or engineering decision in a concrete example
  • Connect 3-way handshake with SYN and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Before any data flows over TCP, both sides perform a 3-way handshake: the client sends SYN (synchronize, 'let's connect'), the server responds SYN-ACK (acknowledging, and requesting its own synchronization), and the client replies ACK (confirming) -- only then is the connection ESTABLISHED and ready for real data.

Key concepts

3-way handshakeSYNSYN-ACKACKsegmentpacketframe

Example

# 3-way handshake:
# Client -> Server: SYN
# Server -> Client: SYN-ACK
# Client -> Server: ACK
# -- connection now ESTABLISHED, data can flow

# same data, different names by layer:
# Transport layer: segment (has a TCP header)
# Internet layer: packet (segment + IP header)
# Link layer: frame (packet + MAC header)
Common mistake: Using 'packet' as a catch-all term for any unit of network data -- in precise usage, packet specifically refers to the Internet-layer unit, not the Transport-layer segment or Link-layer frame.

Explanation

DNS (Domain Name System) translates human-readable domain names (like example.com) into IP addresses computers actually use to route traffic -- often through a CHAIN of lookups (a CNAME pointing to another name, which finally resolves to an A record).

Key concepts

DNSDHCPARPICMPpingCNAMEA record

Example

# DNS resolution can chain through multiple records:
# shop.example.com (CNAME) -> cdn.example.com (A) -> 93.184.216.34
# -- the final A record is what actually has an IP address

# ping uses ICMP echo request/reply to test reachability and measure latency
Common mistake: Assuming DNS always resolves in one direct hop -- CNAME chains (a name pointing to another name) are common and add extra resolution steps before reaching the final IP.
09HTTP, HTTPS & TLS

What you will learn

  • Explain how HTTP changes the behavior, result, or engineering decision in a concrete example
  • Connect HTTP with HTTPS and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

HTTP is the application-layer protocol underlying almost all web traffic: a client sends a request (method, URL, headers, optional body), the server processes it and sends back a response (status code, headers, body).

Key concepts

HTTPHTTPSTLScertificaterequest lifecycle

Example

# HTTP request lifecycle:
# 1. DNS resolves the hostname to an IP
# 2. TCP handshake establishes a connection (TLS handshake too, for HTTPS)
# 3. Client sends the HTTP request
# 4. Server processes it, sends back a response
# 5. Connection closes or stays open for reuse (keep-alive)
Common mistake: Thinking HTTPS is just 'HTTP but encrypted' with no other guarantee -- TLS also verifies the SERVER'S IDENTITY via its certificate, protecting against impersonation, not just eavesdropping.
10Routing, switching & NAT

What you will learn

  • Explain how routing decisions are made and why NAT exists
  • Explain how routing changes the behavior, result, or engineering decision in a concrete example
  • Connect routing with routing table and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Routing is the process of choosing the best path for a packet to travel across multiple networks toward its destination -- routers maintain routing tables and make this decision hop by hop, not knowing the whole path in advance.

Key concepts

routingrouting tableswitchingNAT

Example

# NAT in action:
# Device A (192.168.1.10) and Device B (192.168.1.11) both share public IP 203.0.113.5
# the router tracks: 'the request going out on port 51000 belongs to Device A'
# so when the response comes back, it's correctly routed to Device A, not Device B
Common mistake: Assuming every device on a home network has its own unique address as far as the internet is concerned -- NAT means the OUTSIDE world only sees the router's single public IP.
11Firewalls, proxies, load balancers & CDNs

What you will learn

  • Distinguish a forward proxy from a reverse proxy, and explain what load balancers and CDNs do
  • Explain how firewall changes the behavior, result, or engineering decision in a concrete example
  • Connect firewall with forward proxy and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A firewall filters traffic based on rules (allow/deny by port, IP, protocol). A forward proxy sits in front of CLIENTS, making requests on their behalf (hiding the client from the destination server).

Key concepts

firewallforward proxyreverse proxyload balancerCDN

Example

# forward proxy: hides the CLIENT from the destination (e.g. a corporate proxy for outbound browsing)
# reverse proxy: hides the SERVER from the client (e.g. nginx in front of your actual backend)
# load balancer: routes each request to whichever of several backend servers should handle it
# CDN: serves a cached copy of your static assets from a server physically near the user
Common mistake: Confusing forward and reverse proxies -- the direction of WHO is being hidden from WHOM is the entire distinction between them.
12WebSockets, Server-Sent Events & network troubleshooting

What you will learn

  • Explain when to use WebSockets vs SSE, and name the core troubleshooting commands
  • Explain how WebSockets changes the behavior, result, or engineering decision in a concrete example
  • Connect WebSockets with Server-Sent Events and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Regular HTTP is request-response only -- the server can't push data to the client on its own. WebSockets open a persistent, two-way connection, letting either side send data at any time (used for chat apps, live collaboration, gaming).

Key concepts

WebSocketsServer-Sent Eventspingtraceroutedigcurlnetstat

Example

# choosing WebSockets vs SSE:
# chat app (client sends AND receives) -> WebSockets
# live stock ticker (server only pushes, client never sends) -> SSE, simpler

# troubleshooting toolkit:
# ping example.com          -- is the host reachable at all?
# traceroute example.com    -- where does the path actually break?
# dig example.com           -- what does DNS actually resolve to?
# curl -v https://example.com  -- see the full request/response, including headers
Common mistake: Reaching for WebSockets by default for any real-time feature -- if the client never needs to send data back over the same connection, SSE is simpler and sufficient.
13Routing protocols: OSPF & BGP fundamentals

What you will learn

  • Explain the purpose of OSPF inside a network and BGP between autonomous systems
  • Explain how OSPF changes the behavior, result, or engineering decision in a concrete example
  • Connect OSPF with BGP and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Routers need protocols to learn which next hop should carry traffic toward a destination. OSPF is a link-state interior routing protocol commonly used within an organization: routers share topology information and compute shortest paths.

Key concepts

OSPFBGProuting tableautonomous systempath selection

Example

A data-center or enterprise network may use an interior protocol such as OSPF to learn internal routes, while edge routers use BGP to exchange external prefixes with other networks. Application code normally does not run BGP, but infrastructure and network-automation roles need to reason about it.
Common mistake: Calling BGP simply a shortest-path protocol.

likely a firewall blocking port 443, or the server/service isn't actually listening on that port -- check firewall rules and confirm the service is running and bound to that port

Choose TCP or UDP

You're building a real-time multiplayer game where occasional dropped position updates are acceptable, but delay is not. Would you choose TCP or UDP, and why?

Hint

UDP -- lower latency matters more than guaranteed delivery for this use case

Diagnose a slow API response

An API request succeeds (200 OK) but takes 4 seconds. DNS resolved instantly and the TCP handshake completed quickly. Where would you look next, and why might a reverse proxy or load balancer be relevant here?

Hint

the delay is likely happening at the application layer (slow backend processing) or a slow upstream dependency -- check reverse proxy/load balancer logs to see if the delay is in reaching the backend or in the backend's own processing time
