Explanation

Replication means keeping copies of the same data on multiple machines -- for two reasons: durability (if one machine's disk dies, the data survives elsewhere) and availability (if one machine is down, another can still serve requests).

Key concepts

04The CAP theorem

What you will learn

  • Explain what CAP actually claims, and correct the most common misreading of it
  • Explain how CAP theorem changes the behavior, result, or engineering decision in a concrete example
  • Connect CAP theorem with consistency and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The CAP theorem states that during a network partition (when some machines can't reach others), a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a response, even if it might be stale) -- it cannot guarantee both at the same time during that partition.

Key concepts

CAP theoremconsistencyavailabilitynetwork partition

Example

# during a network partition specifically:
# choose Consistency (CP): reject requests you can't verify are up-to-date -- correctness over uptime
# choose Availability (AP): answer anyway, possibly with stale data -- uptime over perfect correctness
# NOT during a partition: a good system can be both consistent AND available
Common mistake: Treating CAP as 'pick 2 of 3, always' -- it's specifically about partition behavior; conflating it with a permanent, constant trade-off is the single most common misreading of this theorem.

07Idempotency

What you will learn

  • Explain why idempotency matters specifically because networks are unreliable
  • Explain how idempotency changes the behavior, result, or engineering decision in a concrete example
  • Connect idempotency with idempotency key and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An operation is idempotent if performing it multiple times has the exact same effect as performing it once. This matters enormously in distributed systems because networks are unreliable: a client might send a request, the server processes it successfully, but the RESPONSE gets lost -- the client, seeing no response, retries the exact same request.

Key concepts

idempotencyidempotency keyretry safetyduplicate request

Example

# without an idempotency key: retry after a lost response -> customer charged TWICE
# with an idempotency key: server remembers request ID 'req-abc' was already processed ->
# a retry with the SAME ID returns the ORIGINAL result instead of charging again
Common mistake: Assuming retries are automatically safe because 'the client will just get an error and stop' -- a LOST RESPONSE (not a lost request) is exactly the scenario where the server already.
08Retries, timeouts & circuit breakers

What you will learn

  • Explain why naive retries can make an outage worse, and how backoff and circuit breakers prevent that
  • Explain how exponential backoff changes the behavior, result, or engineering decision in a concrete example
  • Connect exponential backoff with circuit breaker and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Retrying a failed request seems obviously helpful, but retrying IMMEDIATELY and REPEATEDLY can make a struggling service's situation worse -- exactly when it's already overloaded, a flood of instant retries from every caller adds MORE load, not less.

Key concepts

exponential backoffcircuit breakerCLOSED/OPEN/HALF-OPENcascading failure

Example

# circuit breaker states:
# CLOSED (normal) -- failures accumulate -- threshold reached -> OPEN (reject immediately, no load added)
# OPEN -- after a cooldown timeout -> HALF-OPEN (allow ONE test request through)
# HALF-OPEN: succeeds -> CLOSED (back to normal). fails -> OPEN again (cooldown restarts)
Common mistake: Retrying immediately in a tight loop with no backoff -- this is one of the most common REAL causes of a small outage turning into a much larger cascading failure across an entire system.
09Leader election

  • Explain how leader election changes the behavior, result, or engineering decision in a concrete example
  • Connect leader election with split brain and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Some operations need exactly ONE node acting as the coordinator at any moment (e.g. deciding write order for a replicated log) -- having two nodes both believe they're the leader (a 'split brain') can cause serious inconsistency.

Key concepts

leader electionsplit brainbully algorithmconsensus

Example

# simplified bully algorithm:
# node 2 notices the leader is down, and asks: is anyone with HIGHER priority still alive?
# if node 5 (highest) responds -> node 5 becomes leader
# if nodes 4 and 5 are BOTH down -> node 3 (next highest alive) becomes leader
# if node 2 gets no responses at all -> node 2 becomes leader itself
Common mistake: Assuming leader election, once done, is permanent -- real systems must continuously detect leader failure and RE-elect, since the whole point is surviving the CURRENT leader eventually.

11Messaging & event-driven systems

What you will learn

  • Explain why decoupling services with a message queue changes failure behavior, not just architecture style
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: at-least-once delivery, at-most-once delivery, exactly-once semantics caveat, backpressure.
  • Explain how message queue changes the behavior, result, or engineering decision in a concrete example
  • Connect message queue with producer/consumer and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

In a direct request/response call, if the receiving service is down, the request simply fails immediately. A message queue decouples this: the sender publishes a message and moves on; the queue holds it until a consumer is ready to process it -- meaning a temporarily-down consumer doesn't cause the sender to fail at all.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: at-least-once delivery, at-most-once delivery, exactly-once semantics caveat, backpressure.

Key concepts

message queueproducer/consumerevent-driven architecturedecouplingat-least-once deliveryat-most-once deliveryexactly-once semantics caveatbackpressure

Example

# direct call vs queue-based, when the downstream service is temporarily down:
# direct call: request fails immediately, caller must handle the error right now
# queue-based: message waits in the queue; once the consumer recovers, it processes
# the backlog -- the original caller never even knew there was a problem
Common mistake: Assuming a message queue guarantees messages are processed in the exact order they were sent -- many real queue systems (for scalability reasons) only guarantee this per-partition/per-key.
12Concurrency models & async programming

What you will learn

  • Distinguish concurrency at the distributed-systems level from single-machine threading, and explain why async I/O matters at scale
  • Explain how blocking I/O changes the behavior, result, or engineering decision in a concrete example
  • Connect blocking I/O with async/non-blocking I/O and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Within ONE machine handling MANY simultaneous distributed requests, blocking I/O (waiting synchronously for a network call or disk read to finish) wastes a thread that could otherwise be doing other work -- at scale, this severely limits how many concurrent connections a single machine can handle.

Key concepts

blocking I/Oasync/non-blocking I/Oconcurrency at scaleevent loop

Example

# blocking vs async, serving 10,000 concurrent slow network calls:
# blocking: needs (roughly) 10,000 threads, each stuck waiting -- huge memory/context-switch overhead
# async: a small pool of threads, each juggling many in-flight calls,
# resuming exactly when a result becomes ready -- vastly less overhead for the same load
Common mistake: Assuming 'more threads' is the answer to handling more concurrent connections -- past a point, thread overhead itself becomes the bottleneck, which is exactly the problem async I/O is.

Explanation

Consensus lets a group of machines agree on ordered state changes even when some machines or messages fail. Raft presents the problem through leader election, replicated logs, and majority commitment; Paxos is a foundational family of consensus algorithms with a different formulation.

Key concepts

consensusRaftPaxosquorumleader electionlog replication

17Distributed storage: replication & erasure coding

What you will learn

  • Compare full replication with erasure coding for durability, storage cost, and recovery
  • Explain how replication changes the behavior, result, or engineering decision in a concrete example
  • Connect replication with erasure coding and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Replication stores full copies on multiple nodes, making reads and recovery straightforward but multiplying storage cost. Erasure coding splits data into fragments plus parity so the original can be reconstructed after some fragment loss with lower storage overhead, at the cost of more CPU/network work and more complex recovery.

Key concepts

replicationerasure codingdurabilityrecoverystorage overhead

Example

Three-way replication stores roughly three full copies. An erasure-coded scheme can tolerate failures with less than 3x raw storage, but rebuilding a lost fragment may require reading several surviving fragments and computing reconstruction data.
Common mistake: Comparing only storage cost.

Choose a replication mode

A system logs analytics events where losing the last few seconds of data during a crash is acceptable, but write speed matters a lot. Would you choose synchronous or asynchronous replication, and why?

Hint

asynchronous -- the acceptable data-loss window trades for meaningfully faster writes, which matches this workload's priorities

Trace a consistent-hashing reassignment

Given a hash ring with nodes at positions 50, 150, 250, and keys hashing to 30, 90, 200, 280 -- which node does each key map to (clockwise, wrapping around)? If a new node is added at position 100, which keys actually move?

Hint

only keys between 50 and 100 (the new node's position) reassign from node-150 to node-100 -- everything else stays exactly where it was

Identify the CAP misreading

A colleague says "our system can't be both consistent and available, ever, because of CAP." What's wrong with this statement?

Hint

CAP's trade-off only applies DURING a network partition -- when the network is healthy, a well-designed system can offer both consistency and availability

Pick the right consistency model

For a live view-counter on a video (shown publicly, briefly stale is fine) versus an account balance (must never show a stale, too-high number a user could act on) -- which consistency model fits each?

Hint

view counter: eventual consistency is fine. Account balance: needs strong consistency, since a stale read could let a user overdraw

Diagnose a silent failure

A service wraps every downstream call in a try/except that logs nothing and returns a default value on any error. Weeks later, a critical downstream outage went completely unnoticed. What's the actual root cause here, and what should change?

Hint

the silent catch-and-ignore itself is the root cause -- it should log the error clearly (and likely alert) even while still returning a safe default, rather than hiding the failure entirely

Design an idempotency key

A client submits an order twice due to a lost response (same order, retried). What would you use as the idempotency key, and where should the server check it before processing?

Hint

a client-generated unique ID sent with the request (e.g. a UUID); the server checks it BEFORE processing, and if already seen, returns the original result instead of creating a duplicate order

Trace exponential backoff

With base_delay=1 and doubling each retry, what are the wait times before attempts 2, 3, and 4?

Hint

1, 2, 4 -- doubling from the base delay each time

Trace a circuit breaker's states

A circuit breaker has failure_threshold=2. It sees: fail, fail, (circuit opens), a request comes in immediately after (before the cooldown), then after the cooldown a test request succeeds. What state is the circuit in after each event?

Hint

CLOSED, CLOSED->OPEN (2nd failure hits threshold), still OPEN (rejected, cooldown not done), HALF-OPEN then CLOSED (test request succeeds)

Diagnose a split-brain risk

A leader-elected system re-elects a new leader after 5 seconds of no heartbeat, but the old leader (just slow, not actually dead) resumes normal operation 6 seconds later, unaware a new leader was elected. What's the risk, and what should the system check before acting as leader again?

Hint

both nodes might now believe they're the leader (split brain); the old leader should check whether a newer leader term/epoch exists before resuming leader actions, and step down if so

Diagnose a distributed lock bug

Node A acquires a distributed lock with a 10-second expiry, then pauses (garbage collection) for 15 seconds. What happens to the lock, and what's the resulting risk?

Hint

the lock expires while node A is paused; another node can correctly acquire it; when node A resumes, it still believes it holds the lock -- now two nodes both think they have exclusive access

Choose direct call or message queue

A checkout flow needs to send a confirmation email after payment succeeds. Should this be a direct synchronous call, or published to a queue? Why?

Hint

a queue -- the email service being temporarily down shouldn't fail or delay the actual checkout; the message can wait in the queue and be sent once the email service recovers

most real queues (for scalability) only guarantee ordering per-partition/per-key, not globally across all partitions -- check the specific queue's documentation and partition/key strategy

Explain async I/O's benefit at scale

Hint

one-thread-per-connection means 5,000 threads mostly sitting idle waiting, with real memory/context-switching overhead; async I/O lets a small number of threads juggle many in-flight operations, resuming each only when its result is ready

Hint

examples: either downstream API times out or errors (need retries/circuit breakers), a request gets duplicated by a client retry (need idempotency), one downstream API is slow but not failed (need a sane timeout so it doesn't block everything)

Diagnose an availability vs consistency choice

During a network partition, a shopping cart service chooses to keep accepting adds-to-cart on every node, resolving conflicts later, rather than rejecting requests it can't verify are consistent. Which side of the CAP trade-off did it choose, and is that a reasonable choice for a shopping cart specifically?

Hint

it chose availability (AP) over strict consistency; reasonable for a shopping cart, since a temporarily-inconsistent cart that gets reconciled later is a much smaller problem than rejecting a user's ability to add items during a partition

Combine idempotency with retries

backoff controls WHEN retries happen, not WHETHER they're safe -- without an idempotency key, if an earlier attempt actually succeeded server-side but the response was lost, a well-spaced retry can still duplicate the charge
