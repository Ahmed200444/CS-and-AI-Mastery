01The CPU & the instruction cycle

What you will learn

  • Explain the fetch-decode-execute cycle
  • Explain how fetch-decode-execute changes the behavior, result, or engineering decision in a concrete example
  • Connect fetch-decode-execute with program counter and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A CPU repeatedly runs one cycle: fetch the next instruction from memory (using the program counter to know where), decode what it means, and execute it -- then repeat. Registers are tiny, extremely fast storage locations directly on the CPU, used to hold values mid-computation since accessing RAM is far slower than accessing a register.

Key concepts

fetch-decode-executeprogram counterregisters

Example

# simplified instruction cycle, conceptually:
while True:
    instruction = fetch(program_counter)
    program_counter += 1
    operation, operands = decode(instruction)
    execute(operation, operands)  # e.g. add two register values
Common mistake: Thinking of 'the CPU' as running your whole program in one step -- it's genuinely one tiny instruction at a time, repeated billions of times per second.
02Memory hierarchy & cache

What you will learn

  • Explain why memory is organized in a hierarchy of speed vs size vs cost
  • Explain how memory hierarchy changes the behavior, result, or engineering decision in a concrete example
  • Connect memory hierarchy with cache and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Memory exists in a hierarchy: registers (fastest, tiniest), then cache (L1/L2/L3, small and fast), then RAM (larger, slower), then disk (largest, slowest).

Key concepts

memory hierarchycachecache hitcache misslocality of reference

Example

# why this matters practically:
# looping over an array in memory order -> mostly cache hits, fast
# jumping randomly around a huge array -> mostly cache misses, much slower
# even though both do the 'same amount of work' by instruction count
Common mistake: Assuming all memory access is equally fast -- a cache miss can be 100x slower than a cache hit, which is why data layout and access patterns matter so much for real performance.
03Processes vs threads

What you will learn

  • Distinguish a process from a thread and explain why the distinction matters
  • Explain how process changes the behavior, result, or engineering decision in a concrete example
  • Connect process with thread and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A process is a running program with its OWN isolated memory space -- one process can't directly read another's memory.

Key concepts

processthreadisolated memoryshared memory

Example

# process: your web browser (one process) and your text editor (a separate process) --
# neither can accidentally read the other's memory
# thread: your browser might use one thread for rendering the page and another
# for network requests -- both share the SAME browser process's memory
Common mistake: Assuming threads are just 'lightweight processes' with no real difference -- the shared-memory aspect is exactly what causes race conditions, which isolated processes don't have to worry about.
04CPU scheduling algorithms

What you will learn

  • Compare FCFS and Round-Robin scheduling and their trade-offs
  • Explain how FCFS changes the behavior, result, or engineering decision in a concrete example
  • Connect FCFS with Round-Robin and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

With one CPU and many processes wanting to run, the scheduler decides who runs when. First-Come-First-Served (FCFS) runs processes in arrival order to completion -- simple, but one long process can make everyone else wait a long time.

Key concepts

FCFSRound-Robinquantumcontext switch

Example

# FCFS: P1(10) then P2(5) then P3(8) -- P3 waits 15 time units before even starting
# Round-Robin (quantum=4): P1 runs 4, P2 runs 4, P3 runs 4, P1 runs its remaining 6, etc --
# every process gets SOME CPU time quickly, instead of waiting for the one ahead of it to fully finish
Common mistake: Assuming a 'fair' scheduler means every process finishes at the same time -- fairness here means every process gets REGULAR turns, not equal total runtime.
05Synchronization & deadlocks

What you will learn

  • Explain race conditions, locks, and the conditions that cause deadlock
  • Explain how race condition changes the behavior, result, or engineering decision in a concrete example
  • Connect race condition with lock and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

When multiple threads share memory, a race condition happens when the outcome depends on unpredictable timing of which thread runs first -- a lock (mutex) prevents this by letting only one thread access a shared resource at a time.

Key concepts

race conditionlockmutexdeadlockcircular wait

Example

# classic deadlock: Thread A holds Lock 1, wants Lock 2.
# Thread B holds Lock 2, wants Lock 1.
# Neither can ever proceed -- this is deadlock.
# Fix: always acquire locks in the SAME consistent order across all threads.
Common mistake: Adding locks to fix a race condition without considering lock ORDER across different threads -- inconsistent lock ordering is the most common real cause of deadlock.
06Virtual memory & paging

What you will learn

  • Explain how virtual memory lets each process believe it has its own full address space
  • Explain how virtual memory changes the behavior, result, or engineering decision in a concrete example
  • Connect virtual memory with page and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Virtual memory gives each process its own private address space, translated by the OS and hardware into real physical memory addresses -- this is why one process can't accidentally read another's memory, and why a program can use addresses that don't correspond to where its data is actually, physically stored.

Key concepts

virtual memorypagepage tablepage fault

Example

# virtual address -> split into a page number and an offset within that page
# page number looked up in the page table -> physical page location
# offset added -> the exact physical byte address
# e.g. virtual address 4500 with 4096-byte pages -> page 1, offset 404
Common mistake: Confusing virtual memory with 'using disk space as extra RAM' entirely -- that's swap space specifically, one PART of what virtual memory enables, not the whole concept.
07Address spaces, segmentation & memory protection

What you will learn

  • Explain virtual address spaces, segmentation concepts, and why process memory is isolated
  • Explain how address space changes the behavior, result, or engineering decision in a concrete example
  • Connect address space with segmentation and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A process uses virtual addresses that the operating system and hardware translate to physical memory. Historically, segmentation divided memory into logical regions with base/limit rules; modern general-purpose systems rely heavily on paging, while the idea of distinct code, data, heap, and stack regions remains useful.

Key concepts

address spacesegmentationprotectionpage tablevirtual memory

Example

Reasoning exercise: two processes can both use the same virtual address value while the page tables map those addresses to different physical frames. That is why equal virtual addresses do not imply shared memory.
Common mistake: Treating segmentation and paging as identical.
08File systems, system calls & I/O

What you will learn

  • Trace how an application file operation crosses into the OS and reaches persistent storage
  • Explain how system call changes the behavior, result, or engineering decision in a concrete example
  • Connect system call with file descriptor and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Applications request privileged operating-system work through system calls. Opening a file returns a handle/file descriptor; reads and writes move data through kernel-managed buffers and the file-system layer.

Key concepts

system callfile descriptorinode/metadatabufferingfsync

Example

Conceptual flow: Python open() -> OS open system call -> file descriptor -> read/write calls -> page cache -> file-system/storage layer. Closing releases the descriptor; explicit durability may require a flush/fsync depending on guarantees needed.
Common mistake: Assuming write() or closing a high-level file object always means the bytes are physically durable on disk at that exact moment.

Hint

circular wait -- neither can proceed; if both always acquired X before Y, one would simply wait for the other to finish with X, no cycle

Hint

page_number = address // page_size, offset = address % page_size

Diagnose a cache-unfriendly access pattern

Two functions process the same 2D array: one iterates row-by-row (matching memory layout), the other column-by-column (jumping around memory). The second is much slower despite doing the same number of operations. Why?

Hint

row-by-row access matches how the array is actually laid out in memory, so it mostly hits cache; column-by-column jumps around memory, causing many more cache misses
