Explanation

03A systematic method: reproduce, hypothesize, test

What you will learn

  • Apply a repeatable method instead of guessing
  • Explain how reproduc changes the behavior, result, or engineering decision in a concrete example
  • Connect reproduc with hypothesis and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

First, reproduce the bug reliably -- without a reliable reproduction, you can't confirm whether any change actually fixed it. Then form a specific hypothesis about the cause, and test it directly (often by printing a value you 'assumed' was correct).

Key concepts

reproduchypothesisbisectionassumptionprint statementstaring at code

Example

# 1. Reproduce: run the exact steps that trigger the bug, confirm it happens every time
# 2. Hypothesize: 'I think X is None when it shouldn't be'
# 3. Test: print(X) right before the failing line to check
# 4. Bisection: if unsure WHERE it broke, check a point halfway through the logic, narrow from there
Common mistake: Trying a fix before reliably reproducing the bug -- you can't tell if the fix actually worked or the bug just didn't happen to trigger that time.
04Using a debugger: breakpoints & stepping

What you will learn

  • Use breakpoints and step through code interactively
  • Explain how breakpoint changes the behavior, result, or engineering decision in a concrete example
  • Connect breakpoint with step and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A breakpoint is a marked line where execution pauses so you can inspect the program's actual state -- variables, call stack, everything -- rather than just guessing. Stepping over a line runs it (including any function it calls) as one step; stepping into a line pauses at the FIRST line inside a called function instead, letting you follow execution deeper.

Key concepts

breakpointstep

Example

# in most debuggers:
# set a breakpoint on the suspicious line
# run until it pauses there
# inspect variables directly
# 'step over' vs 'step into' to control how deep you follow the call
Common mistake: Relying only on print statements for a genuinely complex bug when a real debugger would let you pause and inspect state far more efficiently.
05Common bug patterns: off-by-one, undefined names & edge cases

What you will learn

  • Recognize the most frequent categories of real bugs
  • Explain how off-by-one changes the behavior, result, or engineering decision in a concrete example
  • Connect off-by-one with undefined and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An off-by-one error is a loop or index boundary that's one step too far or too short (range(n) vs range(n+1)). An 'undefined' or 'not defined' error means the code references a name that was never assigned in the reachable scope.

Key concepts

off-by-oneundefinededge case

Example

for i in range(len(items) + 1):   # off-by-one: this goes one index too far
    print(items[i])                    # IndexError on the last iteration

# undefined name: using a variable before it's ever assigned in that scope
Common mistake: Assuming a loop or index boundary is correct without explicitly checking it against a small example by hand.
06Silent & intermittent bugs

  • Connect silent with intermittent and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A silent bug produces a wrong result without raising any visible error -- much harder to notice than a crash. An intermittent (flaky) bug doesn't reproduce consistently, often hinting at timing, randomness, or shared/mutable state being the real cause rather than a simple logic error.

Key concepts

silentintermittentflaky

Example

# silent bug example: a function that returns 0 instead of raising an error
# when given invalid input -- looks like it 'worked', but the result is wrong

# flaky bug example: a test that passes 9 times out of 10 --
# investigate shared state or timing assumptions, not just 'bad luck'
Common mistake: Dismissing a rarely-reproducing bug as 'probably nothing' instead of investigating shared state or timing as the likely real cause.
07Debugging habits: rubber duck, minimal repro & logging

What you will learn

  • Apply proven habits that make debugging faster
  • Explain how rubber duck changes the behavior, result, or engineering decision in a concrete example
  • Connect rubber duck with minimal reproducible example and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Rubber-duck debugging means explaining your code and reasoning out loud (even to an inanimate object) -- this often surfaces the bug yourself, mid-explanation. A minimal reproducible example is the smallest possible code that still reliably triggers the bug, with everything irrelevant removed -- shrinking it often reveals the actual cause.

Key concepts

rubber duckminimal reproducible exampleloggingprint-statement debugging

Example

# minimal reproducible example: strip a 500-line failing script down to
# the ~10 lines that still reproduce the bug -- the process of removing
# 'irrelevant' code often reveals what's actually causing it
Common mistake: Sharing (or debugging from) the entire original codebase instead of first shrinking to a minimal reproducible example -- this buries the actual cause in noise.
08Debugging in production vs locally

What you will learn

  • Reason about why a bug might only appear in one environment
  • Explain how production changes the behavior, result, or engineering decision in a concrete example
  • Connect production with used to work and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A bug that appears only 'in production' but not locally is usually caused by differences in environment: real data, configuration, dependency versions, or scale that don't match the local setup. Checking what recently changed (via git diff/log) is a strong first move when something 'used to work' but suddenly doesn't.

Key concepts

productionused to workroot causeguessingstucktake a break

Example

# common production-only causes:
# - real user data has an edge case your test data never included
# - a dependency version differs between local and production
# - production runs at a scale (data size, concurrency) local testing never reaches
Common mistake: Assuming a production-only bug is a fluke or a hardware issue before checking for genuine environment/data/scale differences.
09Verifying fixes actually work

What you will learn

  • Confirm a fix addresses the real root cause, not just a symptom
  • Explain how verify changes the behavior, result, or engineering decision in a concrete example
  • Connect verify with expected output and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Always verify a fix resolves the ORIGINAL reported symptom, not just that some error disappeared -- a change can silence one symptom while leaving the real underlying bug (or a new one) unaddressed. Explicitly comparing 'expected output' vs 'actual output' turns a vague 'something's wrong' into a precise, checkable difference.

Key concepts

verifyexpected outputactual output

Example

# before declaring a fix complete:
# 1. does it produce the ORIGINAL expected output, not just 'no error'?
# 2. does it still work for the edge cases identified earlier?
# 3. did anything else break as a side effect?
Common mistake: Declaring a bug fixed as soon as the error message disappears, without confirming the actual expected behavior is now correct.

Knowledge checks

To read a Python traceback, focus first on:
  1. the top line
  2. the last line (error+message)
  3. the middle
  4. the filename only
Bisection debugging means:
  1. guessing
  2. halving the search space
  3. adding prints everywhere
  4. rewriting
What is the first thing to check when a program crashes with an error?
  1. restart the computer
  2. read the actual error message and traceback carefully
  3. delete random lines until it works
  4. assume it's a language bug
What does a stack trace show?
  1. only the last line of code that ran
  2. the sequence of function calls that led to the point where the error occurred
  3. the entire file's contents
  4. a list of all variables in the program
What is a good first hypothesis-testing step when a bug's cause is unclear?
  1. rewrite the whole program from scratch
  2. reproduce the bug reliably first, before trying to fix anything
  3. guess a fix and hope it works
  4. ignore it if it doesn't happen often
What does 'bisection debugging' mean?
  1. writing binary code to debug
  2. narrowing down the location of a bug by repeatedly checking the midpoint between known-good and known-bad states
  3. debugging two files at once
  4. splitting a function into two smaller ones
Why is adding print statements (or using a debugger) often more effective than just staring at code?
  1. it isn't, staring is always faster
  2. it replaces assumptions about what the code does with actual observed values
  3. it makes the code run faster
  4. it's required by most languages
What is a common cause of an off-by-one error?
  1. using the wrong variable name entirely
  2. a loop or index boundary being one step too far or too short (e.g. range(n) vs range(n+1))
  3. a missing import statement
  4. a syntax error
What does it mean when an error says a variable is 'undefined' or 'not defined'?
  1. the variable has the value None
  2. the code is trying to use a name that was never assigned in the reachable scope
  3. the variable is too large
  4. the variable is a duplicate
Why is reproducing a bug BEFORE attempting a fix important?
  1. it isn't important, fixing first is faster
  2. without a reliable reproduction, you can't confirm whether a change actually fixed anything
  3. it's required by testing frameworks
  4. it only matters for large programs
What is a 'silent' bug?
  1. a bug that only happens at night
  2. a bug that produces a wrong result without raising any visible error
  3. a bug in a muted terminal
  4. a bug that only affects sound
Why can print-statement debugging become unwieldy for complex bugs?
  1. print statements are illegal in most languages
  2. it can require manually adding/removing many prints and doesn't let you pause and inspect state interactively like a real debugger
  3. print statements always crash the program
  4. it uses too much memory
What is a breakpoint in a debugger?
  1. a syntax error location
  2. a marked line where execution pauses so you can inspect the program's state
  3. the last line of a program
  4. a place where a bug is guaranteed to exist
What does 'stepping over' a line in a debugger typically do?
  1. skips the line entirely without running it
  2. executes that line (including any function it calls) and moves to the next line, without diving into the called function's internals
  3. deletes the line
  4. restarts the debugger
What does 'stepping into' a line do differently from 'stepping over'?
  1. nothing, they're identical
  2. if the line calls a function, execution pauses at the FIRST line inside that function instead of running it as one step
  3. it skips to the end of the program
  4. it undoes the previous step
Why is it useful to check your assumptions explicitly when debugging (e.g. printing a variable you 'know' has a certain value)?
  1. it's not useful, assumptions are always correct
  2. many bugs come from an assumption that's actually wrong, and verifying it directly is often faster than guessing further
  3. it slows down debugging unnecessarily
  4. it's only needed for beginners
What is a common first move when a program 'used to work but now doesn't'?
  1. rewrite it entirely
  2. check what recently changed (via git diff/log) since it last worked
  3. assume the language itself broke
  4. ignore it and start a new project
Why might a bug appear only with specific input values but not others?
  1. all bugs are truly random
  2. the code likely has an edge case (e.g. empty input, zero, negative numbers, duplicates) it doesn't handle correctly
  3. the computer is malfunctioning
  4. the input files are corrupted
What does it mean to 'rubber duck debug'?
  1. debugging using a physical duck-shaped tool
  2. explaining your code and reasoning out loud (even to an inanimate object), which often surfaces the bug yourself
  3. a joke term with no real technique behind it
  4. a debugging feature specific to one language
Why is comparing 'expected output' vs 'actual output' explicitly useful?
  1. it isn't, actual output is always obviously wrong
  2. it turns a vague 'something's wrong' into a precise, checkable difference to investigate
  3. it's only useful for math problems
  4. it replaces the need to read any code
What's a risk of fixing a bug by guessing without understanding the root cause?
  1. there is no risk, a passing test means it's fixed
  2. the same bug (or a related one) can resurface elsewhere, since the actual cause was never addressed
  3. guessing is always faster and equally reliable
  4. it will always break other tests immediately
Why check the EXACT error type/class, not just that 'an error happened'?
  1. error types don't matter at all
  2. different error types point to different root causes (e.g. TypeError vs IndexError vs KeyError), narrowing your search
  3. it's only relevant in compiled languages
  4. checking error type is unnecessary busywork
What does it mean if a bug is 'intermittent' or 'flaky'?
  1. it only happens once and never again
  2. it doesn't reproduce consistently, often hinting at timing, randomness, or shared/mutable state issues
  3. it's not a real bug
  4. it only affects the user interface
Why read error messages from the BOTTOM up in a Python traceback?
  1. Python always prints errors upside down for style
  2. the bottom of the traceback usually shows the actual error and where it was raised; the lines above show the call chain that led there
  3. it doesn't matter, read it any direction
  4. the bottom is always irrelevant
What's a reasonable next step if you're stuck on a bug for a long time with no progress?
  1. give up on the project entirely
  2. take a break, explain the problem to someone else, or write down exactly what you've already tried and ruled out
  3. keep making random changes as fast as possible
  4. assume it's unsolvable
Why might logging (writing to a log file) be preferred over print statements in a production system?
  1. there's no real difference
  2. logs can be leveled (info/warning/error), timestamped, and reviewed after the fact without needing the program running in front of you
  3. print statements are faster in every case
  4. logging is required by all programming languages
What is a 'minimal reproducible example'?
  1. the full original codebase
  2. the smallest possible piece of code that still reliably triggers the bug, with everything irrelevant removed
  3. a screenshot of the error
  4. a description of the bug in plain English only
Why is a minimal reproducible example valuable when debugging or asking for help?
  1. it isn't valuable, more context is always better
  2. it removes distractions and often reveals the actual cause during the process of shrinking it
  3. it's required by law for bug reports
  4. it makes the bug harder to understand
What's a common cause of a bug that only appears 'in production' but not locally?
  1. the production server is haunted
  2. differences in environment: data, configuration, dependency versions, or scale that don't match the local setup
  3. production servers are always slower
  4. it's always a hardware failure
Why verify a fix actually resolves the ORIGINAL reported symptom, not just that some error disappeared?
  1. any error disappearing means success
  2. a change can silence one symptom while leaving the real underlying bug (or introducing a new one) unaddressed
  3. it's an unnecessary extra step
  4. errors never relate to symptoms
