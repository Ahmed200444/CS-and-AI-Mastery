01The agent loop

What you will learn

  • Describe the observe-decide-act cycle an agent runs
  • Explain how tools changes the behavior, result, or engineering decision in a concrete example
  • Connect tools with function calling and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An agent is an LLM in a loop: it observes state, decides an action (often calling a tool), executes it, sees the result, and repeats until the task is done. Tools give it the ability to DO things, not just talk.

Key concepts

toolsfunction callingplanning loopstatecore agent loop

Example

while not done:
    action = llm(state, tools)
    result = run(action)
    state = update(state, result)
Common mistake: Assuming an agent's tool-calling is guaranteed safe -- the model decides which tool to call, but the code executing it must still validate and gate risky actions.

  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Tool use is what turns an LLM from 'a text generator' into 'a system that can act.' Function calling gives the model a defined list of available tools (name, description, expected arguments) and lets it choose to output a structured request to call one — your code executes the actual function and returns the result back to the model for the next step.

Key concepts

function callingtool definitionsmodel decides, code executestool definition

Example

tools = [{'name': 'get_weather', 'description': 'Get current weather for a city', 'parameters': {'city': 'string'}}]
# model outputs: {'tool': 'get_weather', 'args': {'city': 'Dubai'}}
# YOUR code executes get_weather('Dubai'), then feeds the result back to the model
Common mistake: Assuming the model directly executes actions itself — it only ever outputs a structured REQUEST to call a tool; your application code is what actually performs the action, which is exactly.

09When an agent is the right tool

What you will learn

  • Decide when agent overhead is actually justified
  • Explain how when to use an agent changes the behavior, result, or engineering decision in a concrete example
  • Connect when to use an agent with fixed script vs dynamic decisions and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

An agent is justified when a task genuinely requires multiple dynamic steps, tool calls, and decisions that can't be predetermined in a fixed script. For tasks with a known, fixed sequence of steps, a simple deterministic script is more reliable, cheaper, and easier to debug than an agent.

Key concepts

when to use an agentfixed script vs dynamic decisions

Example

# good agent fit: 'research this topic, decide which sources are credible,
# then summarize' -- the STEPS aren't knowable in advance
# poor agent fit: 'always run steps A, B, then C in that exact order' --
# just write a script; an agent adds cost and unpredictability with no benefit
Common mistake: Building an agent for a task with a known, fixed sequence of steps, when a simple deterministic script would be more reliable and far cheaper.
