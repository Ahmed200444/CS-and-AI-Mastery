Explanation

You already know conceptually why sub-word tokenization exists (from the Transformers and LLMs tracks) -- this lesson is about using the actual tokenizer object. Calling a tokenizer returns input_ids (the token IDs the model expects) and an attention_mask (marking real tokens vs padding, so the model ignores padded positions).

Key concepts

input_idsattention_maskpaddingtruncation

Example

tokenizer(['Hi', 'A much longer sentence here'], padding=True, truncation=True, return_tensors='pt')
# input_ids:      padded token ID sequences, same length across the batch

09Fine-tuning with Trainer

What you will learn

  • Fine-tune a pretrained model using the Trainer API
  • Explain how Trainer changes the behavior, result, or engineering decision in a concrete example
  • Connect Trainer with TrainingArguments and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The Trainer class wraps the training loop concepts you already know from PyTorch (forward pass, loss, backward, optimizer step) into a configurable, batteries-included API -- handling the loop, evaluation, checkpointing, and logging for you, driven by a TrainingArguments object specifying epochs, batch size, learning rate, and more.

Key concepts

TrainerTrainingArgumentsfine-tuning workflowfine-tuning on very few examples

Example

from transformers import Trainer, TrainingArguments

args = TrainingArguments(output_dir='./results', num_train_epochs=3, per_device_train_batch_size=16)
trainer = Trainer(model=model, args=args, train_dataset=tokenized['train'], eval_dataset=tokenized['test'])
trainer.train()
Common mistake: Fine-tuning on far too few epochs/examples and expecting strong results -- fine-tuning still needs a reasonable amount of representative labeled data; it adapts a pretrained model, it doesn't work miracles on a handful of examples.
10Evaluation & model cards

Explanation

The `evaluate` library provides standard metric implementations (accuracy, F1, BLEU, ROUGE) that plug directly into Trainer via a compute_metrics function, so you get real, comparable numbers rather than reinventing metric code.

Key concepts

evaluate librarycompute_metricsmodel cardknown limitations

Example

import evaluate
metric = evaluate.load('accuracy')

def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    predictions = predictions.argmax(axis=-1)
    return metric.compute(predictions=predictions, references=labels)
Common mistake: Publishing a model with no model card, or one that omits known limitations -- this leaves other users to discover a model's failure modes the hard way, in production, instead of being told upfront.

13Parameter-Efficient Fine-Tuning: LoRA and QLoRA

What you will learn

  • Explain LoRA and QLoRA conceptually, and choose between full fine-tuning, LoRA, and QLoRA for a given constraint
  • Explain how LoRA (rank, alpha, target modules, dropout) changes the behavior, result, or engineering decision in a concrete example
  • Connect LoRA (rank, alpha, target modules, dropout) with QLoRA (quantized-base training) and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Full fine-tuning updates every parameter in a model -- expensive in memory and compute, and requires storing a full new copy of the model per fine-tuned variant.

Key concepts

LoRA (rank, alpha, target modules, dropout)QLoRA (quantized-base training)full FT vs. PEFT trade-offadapter saving vs. merging

Example

# the core trade-off, without matrix derivations:
# full fine-tuning: EVERY parameter trains -- most capacity, most memory/compute cost
# LoRA: base model FROZEN, small adapter matrices train -- far less memory, a
# small extra file saved separately from the (unchanged) base model
# QLoRA: LoRA's adapter training, but the FROZEN base model is also quantized
# during training specifically to fit in less memory -- this is TRAINING-time
# quantization of the base, not the same as quantizing a model for inference only
Common mistake: Assuming QLoRA and inference-time quantization are the same technique -- QLoRA quantizes the frozen base model specifically to make TRAINING fit in less memory, while inference quantization (already covered separately) reduces a model's precision purely to make serving cheaper/faster; the mechanisms and goals are genuinely different.

Explanation

A fine-tuning run needs a valid dataset, training configuration, and evaluation plan before you spend significant compute. This lesson shows how to prepare the inputs, validate the setup with a small check first, and use evaluation results to decide whether the full run is behaving correctly.

Key concepts

conversational dataset formattinglabel maskingcatastrophic forgettingadapter lifecycle (save/load/merge)

Example

# why label masking matters -- training on the WRONG tokens changes the task:
# unmasked (wrong): the model is trained to predict BOTH the prompt AND the
# response -- it partly learns to predict user questions, which isn't the goal
# masked correctly: the model is trained to predict ONLY the assistant's

  1. Nothing meaningful
