Explanation

A reproducible training run means anyone (including future you) can rerun the exact same training process and get the same model -- requiring a fixed random seed, a pinned, recorded version of the training data (not just 'the data as of whenever'), and pinned library/dependency versions.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: experiment tracking.

Key concepts

reproducibilityrandom seedsdata versioningdependency pinningexperiment tracking

Example

# reproducibility requires ALL of these fixed and recorded, not just one:
# random_seed = 42
# training_data_version = 'dataset-snapshot-2026-03-01'  -- not 'latest'
# library_versions = 'pinned in requirements.txt/lockfile'
# without ALL three, a training run genuinely cannot be reproduced later

08Measuring and Regression-Testing Inference Performance

What you will learn

  • Name the specific metrics used to measure inference performance, and design a regression check for a serving change
  • Explain how TTFT vs. tokens per second changes the behavior, result, or engineering decision in a concrete example
  • Connect TTFT vs. tokens per second with p50/p95/p99 latency and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Inference performance has its own specific vocabulary, distinct from general latency: time to first token (TTFT) measures how long a user waits before seeing any output at all, while tokens per second measures how fast generation proceeds once it starts -- a system can have excellent TTFT but slow tokens-per-second, or vice versa.

Key concepts

TTFT vs. tokens per secondp50/p95/p99 latencythroughput saturationtail-latency regression

Example

# TTFT and tokens-per-second measure genuinely DIFFERENT things:
# TTFT: how long before the user sees ANY output -- matters most for how
# responsive the experience FEELS at the start
# tokens/sec: how fast generation proceeds once started -- matters most for
# how long a LONG response takes to fully complete
# a system can excel at one while being mediocre at the other
Common mistake: Reporting only an average latency number for an inference service -- p95/p99 tail latency reveals a meaningfully worse experience for a real subset of users that an average alone hides.
09Shadow deployment & champion/challenger testing

What you will learn

  • Explain how shadow deployment changes the behavior, result, or engineering decision in a concrete example
  • Connect shadow deployment with champion/challenger testing and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Shadow deployment runs a new candidate model alongside the current production model on real traffic, but its predictions are only logged and compared -- never actually shown to users or acted on. This lets you observe real-world behavior with zero user-facing risk before trusting it with any real decisions.

Key concepts

shadow deploymentchampion/challenger testingsafe model evaluation

Example

# shadow deployment: challenger runs alongside champion, its output is
# logged and compared, but NEVER shown to users -- zero user-facing risk
# champion/challenger: challenger's predictions DO get used, but only for
# a small, controlled slice of real traffic -- some risk, but real signal
Common mistake: Assuming shadow deployment and champion/challenger testing are the same thing -- shadow deployment carries zero user-facing risk (predictions are never acted on); champion/challenger does.

11Data drift & concept drift

What you will learn

  • Distinguish data drift from concept drift, and explain why a drift signal is a warning, not proof
  • Explain how data drift changes the behavior, result, or engineering decision in a concrete example
  • Connect data drift with concept drift and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Data drift means the INPUT data a model sees in production has statistically shifted from what it was trained on (e.g. customer demographics changed) -- the model's own logic hasn't changed, but the world feeding it has.

Key concepts

data driftconcept driftdrift as a warning signaldistribution shift

Example

# same symptom (a drift score crossing a threshold), two different causes:
# data drift: the INPUTS changed (e.g. more mobile users than in training data)
# concept drift: the RELATIONSHIP changed (e.g. what 'fraud' looks like evolved)
# either way: drift is a signal worth INVESTIGATING, not proof the model is now wrong
Common mistake: Treating any detected drift as automatic proof the model has gotten worse -- drift is a signal that something changed and deserves investigation; it doesn't by itself confirm real-world.

Choose batch or online inference
