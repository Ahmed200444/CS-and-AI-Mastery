01Why transformers were created

What you will learn

  • Explain the core limitation of recurrent models that transformers solved
  • Explain how recurrence changes the behavior, result, or engineering decision in a concrete example
  • Connect recurrence with sequential bottleneck and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Before transformers, sequence models (RNNs/LSTMs) processed tokens one at a time, in order — token 100 couldn't be computed until token 99 was done. This made training slow (no parallelism across the sequence) and made it hard to connect distant tokens (information had to pass through every step in between, degrading over long distances).

Key concepts

recurrencesequential bottleneckparallelizationlong-range dependencies

Example

# RNN: token_100 depends on token_99 depends on token_98 ... -- inherently sequential, slow to train
# Transformer: every token can attend directly to every other token, all at once -- parallelizable
Common mistake: Assuming transformers are just 'a bigger RNN' — the architectural shift (parallel attention vs sequential recurrence) is the actual innovation, not just scale.
02Tokens, embeddings & positional encoding

What you will learn

  • Explain why transformers need explicit positional information
  • Explain how token embeddings changes the behavior, result, or engineering decision in a concrete example
  • Connect token embeddings with positional encoding and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Text is tokenized (as in the NLP track) and each token is converted to an embedding vector. But since a transformer looks at all tokens simultaneously rather than in sequence, it has no inherent sense of ORDER — 'dog bites man' and 'man bites dog' would look identical without help.

Key concepts

token embeddingspositional encodingorder-agnostic attention

Example

token_embedding = embed(token)          # what the token IS
position_embedding = position_encode(i)  # where the token IS in the sequence
final_input = token_embedding + position_embedding
Common mistake: Assuming attention alone preserves word order — it doesn't; positional encoding is a deliberately added mechanism to inject that information back in.
03Queries, keys & values

What you will learn

  • Explain the query/key/value framework attention is built on
  • Explain how query changes the behavior, result, or engineering decision in a concrete example
  • Connect query with value and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Every token produces three vectors: a Query (what am I looking for), a Key (what do I contain, for others to match against), and a Value (what I actually offer if selected). Attention compares each token's Query against every other token's Key to decide how much focus to put on each, then combines their Values weighted by that focus.

Key concepts

queryvaluedot-product attentiondot product intuitionmatrix multiplicationtensor shapes

Example

# conceptually, for one token's query:
# score_i = query . key_i   (how well this key matches what I'm looking for)
# attention_weights = softmax(scores)   (turn scores into a 0-1 distribution)
# output = sum(attention_weights_i * value_i)   (blend of others' values, weighted by relevance)
Common mistake: Trying to memorize Q/K/V as arbitrary labels instead of the underlying intuition (searching for X, offering to be matched on Y, giving Z if picked) — the intuition is what actually helps you reason about attention, not the letters.
04Self-attention & multi-head attention

What you will learn

  • Explain what self-attention computes and why multiple heads are used
  • Explain how self-attention changes the behavior, result, or engineering decision in a concrete example
  • Connect self-attention with context-aware representations and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Self-attention lets every token look at every other token in the SAME sequence to build a context-aware representation — 'bank' next to 'river' vs 'bank' next to 'money' end up with different representations because attention lets context flow in.

Key concepts

self-attentioncontext-aware representationsmulti-head attentionscaled dot-product attentionmatrix shape reasoning

Example

# self-attention: EVERY token attends to every other token in its own sequence
# multi-head: run this 8 (or more) times in parallel with different learned weights,
# then concatenate the results -- each head can specialize in a different pattern
Common mistake: Assuming one attention head captures everything relevant — different heads reliably specialize in different relationship types, which is exactly why using several matters.

Explanation

An encoder builds a rich representation of an entire input (good for understanding tasks, e.g. classification).

Key concepts

encoder-onlydecoder-onlyencoder-decodercausal maskingcausalmasked attention

Example

# masked self-attention during generation:
# when predicting token 5, the model can attend to tokens 1-4,
# but token 5's attention scores to tokens 6+ are masked to -infinity
# (so softmax gives them ~0 weight -- can't see the future)
Common mistake: Confusing masking (which prevents seeing future tokens during generation) with padding (which just marks unused positions in a batch) — they solve different problems and use different mask.
06Self-attention: a worked example

What you will learn

  • Compute a tiny self-attention pass by hand
  • Explain how worked example changes the behavior, result, or engineering decision in a concrete example
  • Connect worked example with softmax and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Working through a small, concrete attention calculation makes the mechanism tangible. Given query, key, and value vectors for a few tokens, computing the dot-product scores, applying softmax to get attention weights, then taking a weighted sum of values shows exactly how a token's representation gets updated using context from every other token.

Key concepts

worked examplesoftmaxattention weights

Example

# tiny worked example (2 tokens, 2-dim vectors):
# query for 'bank' = [1, 0], keys = [[1,0], [0,1]] for 'bank' and 'river'
# scores = dot products = [1, 0]
# softmax([1,0]) approx [0.73, 0.27] -- 'bank' attends mostly to itself here
# output = 0.73*value_bank + 0.27*value_river
Common mistake: Trying to reason about attention only abstractly without ever computing a concrete example -- the mechanism is much clearer once you've traced actual numbers through it.

08Inference, context windows & computational limits

What you will learn

  • Explain what a context window is and why attention is computationally expensive
  • Explain how context window changes the behavior, result, or engineering decision in a concrete example
  • Connect context window with quadratic attention cost and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

The context window is the maximum number of tokens a transformer can consider at once — anything beyond it is simply invisible to the model.

Key concepts

context windowquadratic attention costinference compute

Example

# attention cost scales as O(n^2) in sequence length n
# double the context window -> roughly 4x the attention compute
# this is why '1 million token context' is a genuinely hard engineering achievement, not just a bigger number
Common mistake: Assuming you can just keep feeding a model more and more context 'for free' — cost and latency scale non-linearly, and very long contexts can also dilute the model's effective attention over.
09Transformers beyond text: vision & multimodal models

What you will learn

  • Explain how the transformer architecture extends beyond text
  • Explain how vision transformer changes the behavior, result, or engineering decision in a concrete example
  • Connect vision transformer with ViT and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Vision transformers (ViT) apply the same self-attention mechanism to images, by splitting an image into patches and treating each patch like a token. Multimodal models combine text and image (or audio) understanding in one architecture, often using cross-attention so text tokens can attend to image patches and vice versa.

Key concepts

vision transformerViTmultimodalcross-attention

Example

# Vision Transformer (ViT) intuition:
# split a 224x224 image into 16x16 patches -> 196 'tokens'
# feed these patch embeddings through the SAME kind of transformer
# encoder used for text -- attention works the same way, just on patches
Common mistake: Assuming transformers only work for text -- the same core self-attention mechanism generalizes to images, audio, and combinations of modalities.
