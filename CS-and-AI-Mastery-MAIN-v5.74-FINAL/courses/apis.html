02REST fundamentals

What you will learn

  • Explain what REST means and its core principles
  • Explain how REST changes the behavior, result, or engineering decision in a concrete example
  • Connect REST with resource and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

REST (Representational State Transfer) is a style for designing web APIs around resources, identified by URLs, manipulated using standard HTTP methods. A REST API is typically stateless -- each request contains everything needed to process it, with no server-side session memory between requests.

Key concepts

RESTresourcestateless

Example

GET /users/42        # get user 42
POST /users          # create a new user
PUT /users/42        # update user 42 entirely
DELETE /users/42     # delete user 42
Common mistake: Designing an API where the server must remember previous requests to process a new one -- this breaks REST's stateless principle and complicates scaling.
03HTTP methods

What you will learn

  • Use GET, POST, PUT, PATCH, and DELETE correctly
  • Explain how GET changes the behavior, result, or engineering decision in a concrete example
  • Connect GET with POST and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

GET retrieves data without changing anything (safe to repeat). POST creates a new resource.

Key concepts

GETPOSTPUTPATCHDELETE

Example

GET /orders/5       # read only, safe to repeat
PATCH /orders/5      # update just one field, e.g. status
DELETE /orders/5     # remove it
Common mistake: Using GET for an operation that changes data (like deleting something) -- GET requests can be cached, prefetched, or retried automatically, causing unintended side effects.
04Status codes

What you will learn

  • Interpret common HTTP status codes
  • Explain how status code changes the behavior, result, or engineering decision in a concrete example
  • Connect status code with 200 and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

HTTP status codes tell a client what happened to a request. Codes in the 2xx range usually mean success, 4xx codes describe client-side problems such as invalid input or missing resources, and 5xx codes indicate server-side failures. Choose a status code that matches the real outcome so callers can handle the response correctly.

Key concepts

status code200201400401404500

Example

200 OK              -- success
201 Created          -- POST succeeded, new resource made
400 Bad Request      -- client sent invalid data
401 Unauthorized     -- missing/invalid authentication
404 Not Found        -- resource doesn't exist
500 Internal Server Error -- server-side failure
Common mistake: Returning 200 OK for a request that actually failed -- this misleads clients into thinking something succeeded when it didn't.
05Working with JSON

What you will learn

  • Explain how JSON changes the behavior, result, or engineering decision in a concrete example
  • Connect JSON with serialize and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

JSON (JavaScript Object Notation) is the standard format most REST APIs use to send and receive structured data -- objects with key-value pairs, arrays, strings, numbers, booleans, and null. Almost every language has built-in or standard-library support to parse JSON into native objects and serialize objects back into JSON.

Key concepts

JSONserializeparse

Example

{
  "id": 42,
  "name": "Ada",
  "active": true,
  "tags": ["admin", "beta"]
}
Common mistake: Forgetting to set the Content-Type header to application/json when sending a JSON body -- some servers won't parse the body correctly without it.

07Pagination

What you will learn

  • Explain why and how APIs paginate large result sets
  • Explain how pagination changes the behavior, result, or engineering decision in a concrete example
  • Connect pagination with offset-based and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Returning millions of rows in one response would be slow and memory-heavy for both server and client.

Key concepts

paginationoffset-basedcursor-based

Example

GET /orders?page=2&limit=20     # offset-based: skip 20, return next 20
GET /orders?cursor=abc123&limit=20  # cursor-based: continue from a specific point
Common mistake: Returning an entire unbounded dataset in one response with no pagination -- this becomes slow, memory-heavy, and fragile as the dataset grows.

09Rate limiting

What you will learn

  • Explain why APIs rate-limit requests and how clients should respond
  • Explain how rate limiting changes the behavior, result, or engineering decision in a concrete example
  • Connect rate limiting with 429 and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Rate limiting caps how many requests a client can make in a given time window, protecting the server from being overwhelmed (by mistake or by abuse). When the limit is hit, the API typically returns a 429 Too Many Requests status.

Key concepts

rate limiting429backoffRetry-Afterretrying immediatelyimmediately

Example

HTTP/1.1 429 Too Many Requests
Retry-After: 30

# a well-behaved client waits at least 30 seconds before retrying,
# and increases the wait further if still rate-limited
Common mistake: Retrying a rate-limited request immediately in a tight loop -- this makes the underlying problem worse and can extend how long you're limited for.
10API Versioning and Backward Compatibility

What you will learn

  • Distinguish backward-compatible changes from breaking changes, and choose a versioning strategy that protects existing clients
  • Apply the KHDA-benchmarked professional additions in a realistic company workflow: OpenAPI schema contracts, webhooks.
  • Explain how API versioning changes the behavior, result, or engineering decision in a concrete example
  • Connect API versioning with backward-compatible change and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Once an API has real clients, changing it is no longer just an internal decision -- a breaking change (renaming or removing a field, changing a field's type, changing what a status code means) can crash every client that depends on the old shape, often with no warning.

Professional benchmark addition: These company-use concepts were kept after comparing the course with public syllabi from KHDA-listed Dubai training providers: OpenAPI schema contracts, webhooks.

Key concepts

API versioningbackward-compatible changebreaking changeURL versioningheader-based versioningdeprecation periodmigration guidanceversion bumprenamed a fieldOpenAPI schema contractswebhooks

Example

# BREAKING: renaming an existing field silently
# /v1/users/42  ->  {"user_name": "asha"}
# becomes
# /v1/users/42  ->  {"username": "asha"}   # same version, field renamed
# any client reading response['user_name'] now crashes or gets undefined -- no warning, no migration window

# CORRECT: introduce the change in a new version instead
# /v1/users/42  ->  {"user_name": "asha"}     # unchanged, old clients keep working
# /v2/users/42  ->  {"username": "asha"}      # new clients opt in when ready
# /v1/ is deprecated with a stated end-of-life date, giving clients time to migrate
Common mistake: Treating a field rename or type change as a 'small' update that doesn't need a new version -- from a client's perspective, a renamed field is indistinguishable from a removed one, and.
