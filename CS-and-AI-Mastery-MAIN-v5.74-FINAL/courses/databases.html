01What a database actually is

What you will learn

  • Connect DBMS with durability and predict what changes when one assumption changes

Explanation

A database is software that stores data durably and lets many programs read/write it safely at once, with guarantees a plain file can't give you: concurrent access without corruption, crash recovery, and fast lookups even at huge scale.

Key concepts

DBMSdurabilityconcurrencySQL vs NoSQL

Example

# Without a DBMS: two processes writing to the same file
# can corrupt it, or clobber each other's writes.
# A DBMS enforces safe concurrent access + durability guarantees.
Common mistake: Assuming a database is 'just a fancy Excel file' — the concurrency and crash-safety guarantees are the whole point, not the storage format.
02Primary & foreign keys

What you will learn

  • Define primary key and foreign key
  • Explain what a foreign key enforces
  • Explain how primary key changes the behavior, result, or engineering decision in a concrete example
  • Connect primary key with foreign key and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A primary key uniquely identifies each row in a table (often an auto-incrementing id). A foreign key is a column in one table that references a primary key in another, and the database ENFORCES that the referenced row must exist — this is called referential integrity.

Key concepts

primary keyforeign keyreferential integrity

Example

-- orders.customer_id is a foreign key into customers.id
CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  customer_id INTEGER REFERENCES customers(id),
  total NUMERIC
);
Common mistake: Deleting a parent row (a customer) while orders still reference it — most databases block this by default unless you explicitly cascade or nullify.
03Data types & constraints

What you will learn

  • Connect data types with NOT NULL and predict what changes when one assumption changes

Explanation

Choosing the right data type (INTEGER, TEXT, NUMERIC, BOOLEAN, TIMESTAMP) isn't just style — it affects storage size, valid values, and what operations are even possible. Constraints (NOT NULL, UNIQUE, CHECK) let the database itself reject bad data, instead of relying on application code to catch every case.

Key concepts

data typesNOT NULLUNIQUECHECK

Example

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  age INTEGER CHECK (age >= 0)
);
Common mistake: Storing dates/money as raw TEXT — you lose sorting, range queries, and arithmetic; use proper TIMESTAMP/NUMERIC types.
04Normalization (1NF–3NF)

What you will learn

  • Explain what each normal form eliminates

  • Explain how 1NF changes the behavior, result, or engineering decision in a concrete example
  • Connect 1NF with 2NF and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Normalization is the process of structuring tables to eliminate redundant data. 1NF: every cell holds one atomic value (no comma-separated lists in a column).

Key concepts

1NF2NF3NFredundancy

Example

-- NOT normalized: customer_name repeated on every order row
-- (id, customer_name, customer_email, item, price)

-- Normalized: split into two tables
-- customers(id, name, email)
-- orders(id, customer_id, item, price)
Common mistake: Over-normalizing a reporting/analytics table — sometimes deliberate redundancy (denormalization) is the right call for read-heavy workloads.
05Indexes & how lookups get fast

What you will learn

  • Explain why an index speeds up lookups
  • Know the trade-off indexes carry
  • Explain how index changes the behavior, result, or engineering decision in a concrete example
  • Connect index with B-tree and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Without an index, finding a row means scanning every row (O(n)) — a full table scan. An index is a separate, sorted structure (usually a B-tree) that lets the database jump straight to matching rows (roughly O(log n)).

Key concepts

indexB-treefull table scanread/write trade-off

Example

CREATE INDEX idx_orders_customer ON orders(customer_id);
-- now: WHERE customer_id = 42 is fast
-- but every INSERT into orders now also updates this index
Common mistake: Indexing every column 'just in case' — this bloats storage and slows down writes for indexes that are never used by a query.
06NoSQL vs SQL: when to use which

What you will learn

  • Contrast document/key-value/relational models
  • Pick the right store for a given access pattern
  • Explain how document store changes the behavior, result, or engineering decision in a concrete example
  • Connect document store with key-value store and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

SQL databases enforce a fixed schema and strong relational integrity — great when your data has clear structure and relationships (orders, customers, inventory). NoSQL stores relax this: document stores (MongoDB) hold flexible JSON-like records; key-value stores (Redis, DynamoDB) trade query flexibility for extreme speed at massive scale.

Key concepts

document storekey-value storeschema flexibilityaccess patterns

Example

# SQL: 'give me all orders over $50 for customers in Dubai, joined with product names'
# -> relational, needs joins and constraints -> SQL

# Key-value: 'get this user's session by session_id, sub-millisecond'
# -> no relationships, pure lookup speed -> Redis/DynamoDB
Common mistake: Choosing NoSQL purely because it's trendy, then rebuilding joins and constraints in application code — usually a sign SQL was the right choice.

PostgreSQL is a specific, widely-used SQL database -- everything you've learned about schemas, keys, and normalization applies directly. Postgres adds practical tools on top: SERIAL/IDENTITY columns for auto-incrementing ids, RETURNING to get a row back from an INSERT in one round trip, and rich data types like JSONB and arrays that go beyond standard SQL.

Key concepts

PostgreSQLSERIALRETURNINGJSONBconnection strings

Example

CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  created_at TIMESTAMP DEFAULT now()
);

INSERT INTO users (email) VALUES ('a@b.com') RETURNING id;
Common mistake: Forgetting UNIQUE or NOT NULL constraints and only discovering the gap once duplicate or missing data has already been written in production.
08Transactions & ACID Properties

What you will learn

  • Explain why transactions exist and use commit/rollback to keep multi-step operations consistent
  • Explain how transaction changes the behavior, result, or engineering decision in a concrete example
  • Connect transaction with ACID and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A transaction groups multiple database operations into one all-or-nothing unit -- either every operation in it succeeds and is committed, or if anything fails partway through, the whole thing rolls back as if none of it happened.

Key concepts

transactionACIDatomicityconsistencyisolationdurabilitycommitrollbackrace conditiontry/catchun-transacted

Example

BEGIN TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- if the second UPDATE fails (or the app crashes between the two),
-- the transaction rolls back and account 1 keeps its original balance --
-- without a transaction, a crash here would silently lose
Common mistake: Performing a multi-step operation (like a funds transfer) as separate, un-transacted writes -- if anything fails between the steps, the database is left in a genuinely inconsistent state.
09Transaction isolation levels & anomalies

What you will learn

  • Explain dirty reads, non-repeatable reads, phantoms, and what isolation levels trade off
  • Explain how Read Committed changes the behavior, result, or engineering decision in a concrete example
  • Connect Read Committed with Repeatable Read and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Isolation controls how concurrent transactions can observe one another. Weak isolation improves concurrency but can expose anomalies; stronger isolation reduces anomalies at the cost of more coordination or retries.

Key concepts

Read CommittedRepeatable ReadSerializableMVCCanomalies

Example

Two transfers read the same balance of 100. If both independently decide that withdrawing 80 is allowed, a weakly coordinated implementation can overspend. A transaction must protect the invariant with appropriate locking, serializable behavior, or a conditional atomic update.
Common mistake: Assuming ACID means every transaction automatically behaves as if it ran alone.
10Optimistic vs pessimistic locking

What you will learn

  • Choose between optimistic version checks and pessimistic row locks for concurrent updates
  • Explain how SELECT FOR UPDATE changes the behavior, result, or engineering decision in a concrete example
  • Connect SELECT FOR UPDATE with optimistic locking and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Pessimistic locking reserves rows before changing them, which is useful when conflicts are likely but can block other work. Optimistic locking lets work proceed and rejects an update if a version changed, which is useful when conflicts are rare.

Key concepts

SELECT FOR UPDATEoptimistic lockingversion columndeadlocklock ordering

Example

Pessimistic pattern: BEGIN; SELECT balance FROM accounts WHERE id IN (...) FOR UPDATE; validate both rows; UPDATE accounts ...; COMMIT. Optimistic pattern: UPDATE accounts SET balance=?, version=version+1 WHERE id=? AND version=?; verify exactly one row changed.
Common mistake: Locking the same pair of rows in different orders in different code paths.

A database optimizer chooses a plan based on estimated cost. EXPLAIN shows operations such as scans, joins, and sorts so you can investigate slow queries instead of guessing.

Key concepts

EXPLAINsequential scanindex scanselectivitycomposite index

A useful candidate index might begin with user_id and then created_at, but the correct choice depends on real data distribution and workload.

12Redis caching & database consistency

What you will learn

  • Explain cache-aside and reason about stale-cache windows during database writes
  • Explain how Redis changes the behavior, result, or engineering decision in a concrete example
  • Connect Redis with cache-aside and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

Redis is often used as an in-memory cache because reads are fast and data structures are convenient. In cache-aside, the application reads the cache first, falls back to the database on a miss, then populates the cache.

Key concepts

Rediscache-asideTTLinvalidationeventual consistency

Example

Read: cache GET key -> on miss read DB -> SET key with TTL.
Write: commit DB transaction first -> invalidate cache key.
If invalidation fails, retry it and keep TTL finite so stale data cannot live forever.
Common mistake: Updating the cache first and then treating the database write as guaranteed.
13B+ trees & LSM trees: how storage indexes work

What you will learn

  • Compare B+ tree and LSM-tree trade-offs for reads, writes, and storage layout
  • Explain how B+ tree changes the behavior, result, or engineering decision in a concrete example
  • Connect B+ tree with LSM tree and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

B+ trees keep sorted keys in page-friendly tree nodes and are widely used for database indexes because they support point lookups and ordered range scans. LSM trees buffer writes and later merge sorted files through compaction, trading faster sequential writes for more complicated reads and background work.

Key concepts

B+ treeLSM treepagecompactionwrite amplification

Example

B+ tree intuition: follow a small number of page pointers to a sorted leaf, then scan neighboring leaves for a range. LSM intuition: write to memory/log first, flush sorted runs, and compact runs in the background.
Common mistake: Calling one structure universally faster.

15Schema migrations & safe database changes

What you will learn

  • Plan backward-compatible schema changes that can be deployed without breaking live services
  • Explain how migration changes the behavior, result, or engineering decision in a concrete example
  • Connect migration with backward compatibility and predict what changes when one assumption changes
  • Verify the idea with a normal case and an important edge, failure, or scale case

Explanation

A production schema change is a deployment problem, not just an ALTER TABLE statement. A safe pattern is expand-contract: first add a compatible new field/table, deploy code that can handle both old and new shapes, backfill data, switch reads/writes, then remove the old structure later.

Key concepts

migrationbackward compatibilityexpand-contractbackfillrollback

Example

Rename safely: add new column -> dual-write or backfill -> deploy readers using new column -> verify -> stop old writes -> remove old column in a later release.
Common mistake: Renaming or deleting a field in the same deployment that updates application code.

When to index

You have a `users` table queried constantly by email but rarely by signup_date. Which column(s) should be indexed, and why?

Hint

index email; skip rarely-queried columns

Design a schema

Design tables (with keys) for a many-to-many relationship: students can enroll in many courses, courses have many students.

Hint

needs a join/junction table with two foreign keys

SQL vs NoSQL call

A service needs sub-millisecond lookups of a shopping cart by session_id, no relationships, no reporting needs. SQL or NoSQL — justify it.

Hint

key-value store; access pattern has no relational need

Diagnose a lost-transfer bug

A funds-transfer feature runs two separate, un-transacted UPDATE statements: debit account A, then credit account B. During a load test, a server crash between the two statements causes account A to be debited with account B never credited. What's the actual fix, and why doesn't 'just add a try/catch' solve it?

Hint

wrap both UPDATEs in a single database transaction (BEGIN...COMMIT) -- a try/catch in the application only handles errors the app can see; it can't undo a write the database already committed, or recover from the process crashing entirely between the two statements

Diagnose a slow query with the wrong index

A `users` table has an index on `signup_date`, but the actual slow query filters by `email`, which has no index and triggers a full table scan on a million-row table. What's the mismatch here, and what should change?

Hint

the index exists on a column that isn't actually queried -- indexes only speed up lookups on the columns they cover, so an index needs to match the real query pattern (email, here), not just any column that seemed important when the schema was designed
